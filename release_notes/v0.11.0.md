# v0.11.0: Hevy import, and an export the server keeps for a manual import

Previous tag: v0.10.1 (heart_models 2.14.0, unchanged; heart_aws 1.1.0, internal).

## Compatibility

Every contract change since v0.10.1:

| Change | Kind |
|---|---|
| `POST /workouts/imports` takes `source=hevy`: Hevy's app export in all 17 app languages and the hevy.com export in English, through the same preview → consent → commit flow and the same report and preview shapes as Strong (heart-api#72, app side heart-of-yours#324) | additive: a new value of `source`; `strong` behaves as before |
| `POST /workouts/imports?source=hevy` answers `202 {"source", "status": "parked", "message", "reason"}` for a file in Hevy's layout none of whose rows' dates parse (a hevy.com export in another language): the file is kept for a manual import and the owner alerted. A file in no known layout is a `400` as before, for every source | additive: a new status on a value no shipped build sends |
| Import name resolution, every source: an incoming name is resolved through `import_names` (a title another app writes in another language → its English title) and then matched against the library's names **and aliases**; a custom is created under the English name where a translation was known. The library carries no aliases Hevy would hit yet (heart-api#141), so today only translated Hevy titles behave differently | widening: more names match instead of becoming customs; what matched before matches the same |
| An import that skipped rows is kept in the content bucket (`imports/partial/…`) and announced on the monitoring topic | server-side only, no contract |
| `import_names` table (`2026-10-08.import-names.sql`), loaded from Hevy's catalog by `scripts/import_names.py` | database only |

Oldest app served correctly: **1.12**, as before. The floor stays mobile **1.13** against API
v0.9.0; nothing here changes what any build sends or reads. A shipped build sends only
`source=strong`, which answers exactly as in v0.10.1. `MIN_APP_VERSION` stays 1.0.0.
