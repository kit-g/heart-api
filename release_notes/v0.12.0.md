# v0.12.0: moving an exercise's history, Heart's own CSV, hevy.com in every language

Previous tag: v0.11.0 (heart_models 2.14.0 → 2.15.0; heart_aws 1.1.0, unchanged).

## Compatibility

Every contract change since v0.11.0:

| Change | Kind |
|---|---|
| `POST /exercises/:exerciseId/moves` with body `{"targetId"}` re-keys the caller's workouts, routines, preferences and goals from one exercise onto another, and deletes the source when it is the caller's own custom; `?dryRun=true` answers the same report and writes nothing. Refusals: `400 same_exercise`, `404 unknown_exercise` (heart-api#140, app side heart-of-yours#338) | additive: a new route |
| `ExerciseMoveReport` in heart_models 2.15.0, the route's answer | additive: a new package member |
| `POST /workouts/imports` takes `source=heart`: the app's own CSV export (heart-api#175) | additive: a new value of `source` |
| `source=hevy` reads the hevy.com export in all 13 of its languages. Such a file used to answer `202 parked`; it now imports like any other. A file in Hevy's layout whose dates are in no known form still parks | widening: files that were parked are read |
| The minimal-version gate turns away only a version it can read as below the floor. A request with no `X-App-Version`, or an unreadable one, goes on to authentication | widening; no installed build sends a request without the header once started |
| 103 Hevy titles as aliases on 99 library exercises (heart-api#141, tier 1), published to the CDN library with the tag | additive: values under the existing `aliases` key |
| `_move_exercise_history` (`2026-10-10.move-exercise-history.sql`) | database only |

Oldest app served correctly: **1.12**, as before. Nothing here changes what a shipped build sends
or reads. `MIN_APP_VERSION` is now **1.13.0** in both environments but not enforced
(`enforce_app_version = false`): 1.9.0 installs are still in the field and 1.13 is not yet in
both stores. Enforcing it is a separate, announced step.
