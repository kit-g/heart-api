# v0.14.0: suspicious entries, MCP cards and template writes

Previous tag: v0.13.0 (heart_models 2.37.0 → 2.39.0; heart_aws 1.1.0, unchanged).

## Compatibility

Every contract change since v0.13.0:

| Change | Kind |
|---|---|
| Suspicious entries: `GET /anomalies` (`?status=`, paged), `PUT /anomalies/:anomalyId` with `status` `valid` or `invalid`; new code `invalid_status` (heart-api#42) | additive: new routes |
| A set or a workout's time the user marks `invalid` stops counting in every count the server makes (volume, balance, goal progress, records, exercise history). Nothing is marked until a build that offers it ships | additive |
| Workouts take and return each set's `target`. A set sent without the key keeps the stored one; `null` or `{}` clears it; a target the server can't read is left out and the workout still saves (heart-api#286) | widening; additive in responses |
| `POST /programs` adopts a session whose `id` is one of the caller's own templates, linking it in place at its `order`, and returns it in `sessions`. Such a session used to come back unlinked; an id that belongs to someone else is still `403 id_taken` (heart-api#244) | widening |
| A presigned image upload refuses an object over 25 MiB. Installed builds upload phone photos of 2–8 MB, far below it (heart-api#205) | tightening |
| `POST /workouts/imports` keeps an end time more than 24 hours after the start, as the file has it; it used to drop it. The nightly sweep flags such a workout for the user (heart-api#42) | widening |
| OAuth adds the scope `write:templates`, granted on the MCP server only and by default there. `/me` answers `403 insufficient_scope` to a token without `read`; no such token exists | additive |
| MCP: new tools, widget pages and output fields (Developers, below) | additive |
| 2 migrations: suspicious entries and their sweep; workout set targets | database only, beyond the rows above |

heart_models 2.38.0 and 2.39.0 add members only (`Anomaly`, `AnomalyStatus`, `AnomalyService`,
`ExerciseSetField`, `ExerciseSet.clearMeasurements`, `firstWeekday` on `WorkoutAggregation`).
`ExerciseSet.toRow` now always carries its category's measurements, a null one included; checked
against the app's local database writes. `Searchable` and `Exercise.contains` are deprecated and
still work.

Oldest app served correctly: **1.12**, as before. `MIN_APP_VERSION` stays **1.13.0**, not
enforced.

## Developers

New on the token surface (`/me`, same limits as before) and on MCP. Detail:
https://heart-of.me/developers.html, and the design docs under
https://github.com/kit-g/heart-api/tree/main/docs.

- `GET /me/anomalies` (`?status=pending|valid|invalid`, paged): entries in your log that look
  suspicious, such as a timer left running or a weight far from the exercise's typical one, and
  what you made of each. Nothing is corrected.
- `GET /me/volume`, `GET /me/balance`, `GET /me/goals/progress`, `GET /me/records` and exercise
  history add `warnings` when something they count is still unchecked. Entries you marked invalid
  are left out of the counts.
- Workouts carry each set's `target`.
- MCP adds `list_anomalies`, and the counting tools add `warnings`. `get_workout` adds each
  exercise's `category` and each set's target; `list_templates` adds `quotedFrom` on a template
  another account assigned you.
- MCP cards: `get_workout`, `get_exercise_history` and `get_personal_records` name a widget page
  (MCP Apps), and the server answers `resources/list` and `resources/read`. Claude and ChatGPT
  draw the result as a card; other clients get the same text and data as before.
- MCP template writes, for assistants connected by signing in: `create_template_folder`,
  `create_template` and `update_template`. `preview: true` checks everything and saves nothing.
  Connecting grants `read write:templates`. A connection made for `read` alone is refused a
  write with `insufficient_scope`. Personal tokens stay read-only and don't list the writes.
