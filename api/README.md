# Heart API

Dart 3 backend running on AWS Lambda behind API Gateway via the [Lambda Web Adapter](https://crates.io/crates/lambda_web_adapter). Postgres (Supabase) for storage. Uses [relic](https://pub.dev/packages/relic) for HTTP, no ORM (raw SQL).

## Writing a route

A route is `Future<Model?> Function(Request)`. Pull inputs off `request`, call services, return a `Model` (or throw an `ApiException`).

```dart
Future<Workout> getWorkout(final Request request) async {
  final workoutId = request.pathParameters.raw[#workoutId]!;
  return request.workoutsService.getWorkout(
    userId: request.userId,
    workoutId: workoutId,
    imageUrl: request.config.cdnAssetUrl,
  );
}
```

Then register in `routes/index.dart`:

```dart
('/workouts/:workoutId', .get): workouts.getWorkout,
```

`bin/main.dart` walks the registry and wraps each handler in error translation (`ApiException` → JSON body + status code, `NoContent` → 204).

### Inputs available on a Request

| What                                               | Where it comes from                                                                                            |
|----------------------------------------------------|----------------------------------------------------------------------------------------------------------------|
| `request.userId`, `request.user`                   | `RequestUser` extension in `globals/globals.dart`. Set by `authentication` middleware (Firebase token verify). |
| `request.config`                                   | `AppConfig`, set by `configuration` middleware. Reads env vars.                                                |
| `request.awsConfig`                                | `AwsConfig` (credentials + region), set by `awsConfig` middleware.                                             |
| `request.profileService`, `.workoutsService`, etc. | Set by per-path DB middleware (`profilesDb`, `workoutsDb`, …) defined in `middleware/database.dart`.           |
| `request.imageStorageService`                      | S3-backed `ApiImageStorageService`, set by `imageStorageDb` middleware.                                        |
| `request.pathParameters.raw[#workoutId]`           | Provided by relic's router for `:workoutId`-style segments.                                                    |
| `request.queryParameters.raw['cursor']`            | Query string. Typed query params via `IntQueryParam('limit')`.                                                 |
| `await request.json()`                             | Parses the JSON body. From `core/request.dart`.                                                                |

### Returning errors

Throw, don't return. The wrapper in `bin/main.dart` maps these:

| Throw            | Status |
|------------------|--------|
| `NoContent`      | 204    |
| `BadRequest`     | 400    |
| `Forbidden`      | 403    |
| `NotFound`       | 404    |
| `NotImplemented` | 501    |

All defined in `lib/models/errors.dart`. They `implement Model` so their `toMap()` is the response body.

### Multi-action endpoints

`PUT /accounts` switches on `body['action']` to handle `upsert`, `undoAccountDeletion`, `uploadAvatar`, `removeAvatar`. Pattern-match on the body, fall through to the default for the no-action upsert. Keep return type as `Future<Model>` since branches return different shapes.

## Database layer

No ORM. SQL strings in `db/queries.dart`, executed against a `Pool` from the `postgres` package. Each resource (`profiles`, `workouts`, …) gets a mixin in its own file, all `part of 'db.dart'`. The `Database` class assembles them.

```dart
mixin _Profiles on _DatabaseBase implements ApiProfileService {
  @override
  Future<User> upsertProfile(User user) async {
    final rows = await _pool.execute(
      _updateAccount.toSql(),
      parameters: { ... },
    );
    return User.fromRow(rows.first.toColumnMap());
  }
}
```

### SQL conventions

- **Single-roundtrip CTEs** for anything that touches more than one table. Most write operations look like `WITH _x AS (...), _y AS (...) SELECT ... FROM _x JOIN _y ...`. Avoids round-trips and keeps logic in the planner.
- **`forbidden` sentinel** for read endpoints with auth checks:
  ```sql
  WITH _auth AS (SELECT (...) AS allowed)
  SELECT cols..., false AS forbidden FROM table WHERE (SELECT allowed FROM _auth) AND ...
  UNION ALL
  SELECT NULL, NULL, ..., true FROM _auth WHERE NOT allowed
  ```
  Empty result = 404. One row with `forbidden = true` = 403. Otherwise = the data.
- **Partial updates with `COALESCE`**: `SET col = coalesce(@col, col)` lets you pass `null` for fields you want unchanged.
- **Always `RETURNING`** the columns you need — `Future<Void>` queries that don't return are fine but losing the chance to round-trip the new state is usually a bug, not a feature.
- **Triggers for snapshots**: `BEFORE DELETE` triggers can copy data into an archive table while the deleted row is still readable (and `_workout_exercises(OLD.id)` and similar SQL functions work because cascade deletes haven't fired yet).

### Adding a new resource

1. Create `lib/db/<name>.dart` with `mixin _<Name> on _DatabaseBase implements <NameService>`.
2. Add `part '<name>.dart'` to `lib/db/db.dart` and add the mixin to `Database`'s `with` list.
3. Add SQL strings to `lib/db/queries.dart`.
4. Define `<NameService>` interface in either `api/lib/models/` (api-specific) or `shared/heart_models/lib/src/services/` (shared with client).
5. Wire middleware in `lib/middleware/database.dart` and apply it in `bin/main.dart` for the relevant path prefix.

## AWS integration

Everything AWS lives in `shared/heart_aws`. The package is shaped like a tiny boto3 — generic methods, no domain knowledge.

```
shared/heart_aws/lib/
├── heart_aws.dart        # library root, parts:
└── src/
    ├── signer.dart       # Signer mixin wraps AWSSigV4Signer; provides get/put/post/delete
    ├── s3.dart           # S3Api mixin: presignUpload, getObject, copyObject, deleteObject
    ├── sqs.dart          # SqsApi: sendMessage, sendJsonMessage
    ├── sns.dart          # SnsApi: publish
    └── scheduler.dart    # SchedulerApi: createSchedule, getSchedule, deleteSchedule
```

### Pattern

Each service is `abstract class XApi with Signer { ... }` plus a concrete `class X extends XApi { credentialsProvider, region }`. Construct the concrete class per-request (cheap):

```dart
final scheduler = Scheduler(
  credentialsProvider: request.awsConfig.credentialsProvider,
  region: request.awsConfig.region,
);
await scheduler.createSchedule(name: 'foo', groupName: 'bar', ...);
```

### Generic vs domain-specific

Keep AWS clients generic. Domain-specific names live at the call site:

```dart
// good — heart_aws stays boto3-shaped
scheduler.createSchedule(name: 'account-deletion-$userId', groupName: ..., ...)

// bad — would couple the package to our domain
scheduler.createAccountDeletionSchedule(userId: ...)
```

### AWS quirks worth remembering

- **`ClientToken`**: EventBridge Scheduler `CreateSchedule` and `DeleteSchedule` both require a `clientToken` for idempotency despite docs saying optional. Pass the schedule name; same input produces same token, retries are safe.
- **409 on `createSchedule`**: schedule already exists. We return `null` from `createSchedule` and fall back to `getSchedule` to fetch the existing ARN.
- **404 on `deleteSchedule`**: schedule never existed (e.g. user undoes deletion before any was scheduled). Caller can pass `throwIfMissing: false`.
- **AWS service hosts**: `sns.<region>.amazonaws.com`, `scheduler.<region>.amazonaws.com`, `sqs.<region>.amazonaws.com`, `<bucket>.s3.<region>.amazonaws.com`.
- **Content types**: SNS/SQS use `application/x-amz-json-1.0` with `X-Amz-Target` header (JSON protocol). Scheduler uses plain `application/json` (REST). S3 uses XML / signed URL form fields.
- **`AWSHttpException` has no `.message`** — read `e.underlyingException.toString()`. The signer wraps response status + body in there.

## /events — internal async pipeline

Lambda Web Adapter forwards every Lambda invocation as an HTTP request to the Dart server. Direct Lambda invokes (SQS triggers, EventBridge Scheduler targets) come in as `POST /events` with the AWS event payload as the body and **no `x-amzn-request-context` header** (API Gateway sets it for real HTTP traffic).

```
S3 upload ─► EventBridge rule ─► SQS events queue ─► Lambda ─► POST /events ─► imageUpload()
EventScheduler ─► SQS events queue ─► Lambda ─► POST /events ─► accountDeletion()
```

`/events` reads `x-amzn-request-context` to gate non-HTTP events; absent or `null` means the invocation came from a non-API-GW source.

### Adding a new event type

1. Decide the event source (S3 → EventBridge rule, scheduled job → EventBridge Scheduler, etc.) — it sends to the existing `events` SQS queue.
2. Add a `case` in the `switch` in `lib/routes/events.dart` matching either the EventBridge `detail-type`, a custom `Event` field, or any other discriminator.
3. Implement the handler in `lib/events/<your_event>.dart` taking `(Request, …extracted args)`. Pull services off the request via the existing context-property extensions.
4. Errors caught by the handler should call `onError(e, st)` to ship them to the DLQ.

### Tag-based dispatch (image uploads)

Multiple S3 upload flows share one EventBridge rule. The handler fetches object tags and pattern-matches on the tag map:

```dart
switch (tags) {
  case {'user-id': String userId, 'workout-id': String workoutId, 'image-id': String imageId}
       when [userId, workoutId, imageId].every((a) => a.isNotEmpty):
    // workout image
  case {'kind': 'avatar', 'user-id': String userId} when userId.isNotEmpty:
    // avatar
}
```

Tags are written when the presigned upload URL is issued (`presignUpload(tags: [...])`).

### Mocking services

`test/mocks.dart` declares `@GenerateMocks([…])` for the service interfaces. Run `dart run build_runner build --delete-conflicting-outputs` to generate `mocks.mocks.dart`. CI does this automatically.

```dart
// test/mocks.dart
import 'package:heart_models/heart_models.dart' hide ExerciseService, WorkoutService, TemplateService;
@GenerateMocks([
  AppConfig,
  ApiProfileService,
  ApiImageDbService,
  ApiImageStorageService,
  ApiWorkoutService,
  ApiTemplateService,
  ExerciseService,        // server-side, from heart/models/exercises.dart
  ChartPreferenceService,
  ConnectionsService,
])
void main() {}
```

**Gotcha**: `ExerciseService` exists in both `heart/models/exercises.dart` (server) and `heart_models` (client, totally different shape). Mockito can't disambiguate. Use the `hide` clause above. Same trick for `WorkoutService`/`TemplateService`.

### Stubbing a Request

`relic` hides `RequestInternal` from its public barrel. Add `relic_core` as a `dev_dependencies` and import directly:

```dart
import 'package:relic_core/relic_core.dart';

Request _request() =>
  RequestInternal.create(Method.post, Uri.parse('http://localhost/events'), Object());
```

Then set context properties via the public extension setters:

```dart
final req = _request()
  ..imageDbService = mockImageDb
  ..imageStorageService = mockImageStorage
  ..profileService = mockProfileService
  ..config = mockConfig;

await accountDeletion(req, 'u1');

verifyInOrder([
  mockImageStorage.deleteObject(key: 'workouts/abc/img1.jpg'),
  mockProfileService.deleteAccount(userId: 'u1'),
]);
```

### Stubbing return values that aren't used

When a mocked method returns a typed `Future<T>` but the caller doesn't use the value, mockito still requires a real `T`. Construct minimal real instances:

```dart
final dummyImage = WorkoutImage.fromJson({'id': 'i', 'workoutId': 'w', 'key': '/k', 'url': '...'});
final dummyUser = User(id: 'u1');
when(imageDb.recordImage(...)).thenAnswer((_) async => dummyImage);
```

### `verifyInOrder` quirk

`verifyInOrder` only matches **unverified** calls. If you `verify(...).called(1)` first, the call is consumed and `verifyInOrder` won't see it. Use `verifyInOrder` alone if you care about sequence.

```bash
# install deps for both packages
cd api && dart pub get
cd ../shared/heart_aws && dart pub get

cd api && dart run build_runner build --delete-conflicting-outputs

# run tests
dart test

# analyze
dart analyze

# run the server locally (needs env vars — see globals/config.dart for required set)
ENV=dev REGION=us-east-2 FIREBASE_PROJECT_ID=heart-of-yours-dev \
  CONTENT_BUCKET=... MEDIA_DISTRIBUTION=... ... \
  ALLOW_NON_HTTP_EVENTS=true \
  dart run bin/main.dart
```

`ALLOW_NON_HTTP_EVENTS=true` lets you `curl POST /events` from your local machine for testing the SQS-driven flows without going through Lambda/SQS.

### Path conventions

- Module sources between siblings: relative paths like `../../stacks/api`. Uniform; survives directory restructures.
- Repo references inside a stack: `${path.module}/../../../api`. Three levels up from `infrastructure/stacks/<stack>/` reaches the repo root.
- ACM cert ARNs are **passed as variables**, not managed in TF. ACM cross-region (us-east-1 for CloudFront) provider aliases get fiddly; skip the headache.

### Naming

Resources use `${var.name_prefix}-<thing>`. In dev: `name_prefix = "heart-api"` produces `heart-api-events`, `heart-api-events-dlq`, `heart-api-function-role`, etc. Lambda function name itself is bare `heart-api`.

### IAM scoping

EventBridge Scheduler resource ARNs use `schedule/<group>/<name>` (note the format — different from `schedule-group/<group>`). The `scheduler:CreateSchedule` policy must scope to `arn:aws:scheduler:<region>:<account>:schedule/<group>/*`, **not** the schedule-group ARN.

Cross-service `iam:PassRole` is required when the API Lambda creates a schedule that targets SQS via the scheduler IAM role.

## CI / deploy

`.github/workflows/deploy-v2.yml` runs on push to `main`, `connections`, `postgres`. Pipeline:

1. **Lint** — `dart analyze` after `dart pub get` + `dart run build_runner build`.
2. **Test** — `dart test` (same setup).
3. **Build & Deploy** — `make build-ApiFunction` produces `bootstrap`, zipped and pushed to Lambda via `aws lambda update-function-code`.
4. **Smoke test** — hits `/version` and asserts the response's `commit` matches the just-deployed SHA.

Path filters trigger CI only on `api/**`, `shared/**`, or workflow file changes. AWS auth via OIDC role.

## Conventions

- **No comments unless the WHY is non-obvious.** Naming carries the WHAT.
- **No backwards-compat shims** in api code — the client and server ship together.
- **Trust internal code.** Validate at system boundaries (HTTP body, AWS event payload), not between modules.
- **Errors propagate** — handlers throw `ApiException`, the wrapper translates. No try/catch unless you can do something useful.
- **Single source of truth for shapes.** Anything the client ever sees lives in `heart_models`. Server-only types stay in `api/lib/models`.
- **Boto3-shaped AWS package** — generic `createSchedule(name, groupName, ...)`, never `createAccountDeletionSchedule(userId, ...)`.
- **Migrations are forward-only.** No `down` migrations. If a schema change is wrong, write a new migration that reverses it.
