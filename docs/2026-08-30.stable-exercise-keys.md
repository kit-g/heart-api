# Stable exercise keys — slugs in content, uuids on the wire (heart-go backend)

Shipped. This is a record of what exists and why, not a task brief.

Exercise identity used to be the **English display name**, welded in four places at once: the
content YAML's map key, the database's sync conflict target (`ON CONFLICT (name)`), the app→API
wire reference (`exercise_name`), and the asset pipeline's S3 stems. Renaming an exercise's
English copy therefore forked its identity — new row, new uuid, old row archived, history split —
and once the library was localized, name-as-identity became structurally wrong: the name is copy.

Identity is now split by concern:

| concern                          | identity                                                    |
|----------------------------------|-------------------------------------------------------------|
| content (YAML, assets, fixtures) | `key` — kebab-case slug (`bench-press-barbell`), env-stable |
| database + wire (app ↔ API)      | `id` — the row's uuid (v7)                                  |
| display                          | `name` — localized, renamable copy                          |

```
content/exercise_library.yml       exercises: keyed by slug; en name lives in i18n.en.name
content/i18n/<locale>.yml          overlays keyed by the same slugs
content/exercise_movement.yml      sidecar keyed by the same slugs
content/assets/<slug>.gif          asset stems are slugs
        │  sync: ON CONFLICT (key) → renames update in place, same uuid
        ▼
exercises (id uuid PK, key unique among globals, name = copy)
        │  GET /exercises: id + key + localized name
        ▼
app: saves reference exercises by id (exercise_id); POST /exercises persists
the client-minted v7 id, so offline-created customs keep identity through sync
```

## Design decisions (settled — do not re-litigate)

1. **Hard cutover, no dual lookup.** The app has not shipped to stores; there are no legacy
   clients to keep alive. The name-based `_exercise_lookup` CTEs are gone; a missing or
   malformed `exercise` reference in a workout/template body is a 400, not a silent drop (a
   wholly absent `exercise` still means "emptied editor row" and is skipped). The
   `DISTINCT ON (name) … NULLS LAST` user-over-global tie-break disappeared with the name
   lookup — ids are unambiguous.

2. **Slug and uuid, not one or the other.** They solve different halves. The uuid is minted
   per-database, so it can never appear in content or fixtures (dev and prod disagree); the slug
   is authorable and env-stable, but making it the wire reference would have added a second
   identifier to every save. Wire = uuid, content = slug, both carried in the library payload.

3. **The slug is minted once and never re-derived.** `key` is *derived from* the en name at
   introduction, then frozen — renaming the en copy does not move the slug (that's the point).
   The validator asserts slug format (schema `propertyNames` pattern), never
   `key == slugify(name)`. The migration's SQL backfill mirrors the content slugs exactly; if
   the two slugifies ever drifted, the next sync fails loudly on the name unique index.

4. **`name` is mutable copy everywhere.** The sync upserts on `key` and updates `name` from the
   fallback localization (`i18n.en.name` — no longer shadowed dead weight); archives are decided
   by key set-difference. `heart_models 2.0.0` flips `Exercise ==`/`hashCode` from name to a
   now-required `id`, so two locales' views of one exercise compare equal.

5. **User-created exercises carry no key.** Their identity is the uuid (client-minted v7,
   persisted by `POST /exercises`; a collision is a 400 via the shared client-id mapper), their
   name is the owner's to change, and a DB CHECK pins the split: globals must have a key,
   user rows never do.

6. **Deliberate exceptions — matching, not identity.** CSV imports still match by
   case-insensitive name (external exports offer nothing else), and template shares still
   resolve into the student's library by name (they copy customs across users). Both are
   server-internal resolution, not identity.

7. **Assets ride the slug too.** S3 stems (`exercise-uploads/<slug>.<ext>` →
   `exercises/<slug>/…`), the processed-event payload (`key`), and `_setExerciseMedia`
   (`WHERE key = @key`) all moved off the name. Existing S3 objects migrate via
   `scripts/migrate_asset_keys.py`, which uses the pipeline itself as the migration tool: copy
   sources under slug stems → the Lambda reprocesses → the event flow rewrites the DB links.
   No hand-edited CDN URLs.

## Rollout order (per environment)

1. Apply the DB migration (`2026-08-30.exercise-keys.sql`: adds + backfills `key`).
2. Merge → dev sync upserts by key; deploy API + assets Lambda.
3. Run `scripts/migrate_asset_keys.py --bucket <content-bucket> --dry-run`, then for real.
4. App side ships against `heart_models 2.0.0` (see the handoff ticket).

## Coupled release

`heart_models 2.0.0` is a coordinated **breaking** release (the exception CLAUDE.md reserves for
an app migration done in lockstep): `Exercise.id` required and identity-bearing,
`TemplateExerciseRequest.exerciseId`, new `Exercise.key`, unicode-aware search. The app must
adopt it in the same release window that the API deploys, since the old app's name-referencing
saves stop working the moment the new API is live.
