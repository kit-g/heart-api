# Progression on a program you built, and by effort

A coach testing Heart asked how a program they build themselves can suggest
progression, by weight and by effort. This is the answer, and it is also what
became of the first item of heart-api#37, "progression suggestions". The effort
rule below is built (heart-api#495). The trend reading is designed here and not
built.

## Decisions

Made with the user on 2026-11-26.

1. **A suggestion is the user's own rule, read back.** Heart has no opinion
   about the next weight. A program's exercise grows by the rule someone chose
   for it, and the "describe, don't predict" line of
   `docs/2026-10-13.programs.md` holds.
2. **A template outside a program gets no suggestion.** It gets Previous, and
   the trend below, which only describes. A rule lives on a program, and
   "make a program from a folder" (heart-api#244) is the way to one.
3. **Effort enters the rules twice.** As the signal: the rating the lifter
   gave a set (`rpe`) decides whether the weight moves. And as the thing
   asked: the reps in reserve a set aims for (`rir`) can change by program
   week.
4. **A rating is never guessed.** A set that asks for an effort and wasn't
   rated holds the weight. Someone who never rates never progresses under
   this rule, and that is the rule working: it reads effort, so it needs it.

## What already worked, and what didn't

Every program takes a growth rule per exercise, whoever made it:
`PUT /programs/:id` validates `rules` the same way for a library copy, a
program made from the user's own templates, and a coach's. The server had no
gap for progression by weight.

The gap was in two places:

- **Nothing in the app chooses a rule.** Rules arrive with a library program,
  and a session added later inherits the program's most common weight rule. A
  program built from the user's own templates starts with no rules and runs as
  written. That is heart-of-yours#765.
- **No rule read effort.** A set logs `rpe`, and a set target can ask for
  `rir`, but `Progression.next` looked only at reps.

## The effort rule

An eighth kind, `effortThenWeight`:

```jsonc
{
  "kind": "effortThenWeight",
  "step": 2.5,               // kg, as on the other weight rules
  "rir": [3, 2, 1, 0, 4],    // optional: reps in reserve by program week
  "miss": {"after": 3, "cut": 0.1}  // optional, and `amrap`: as on the other weight rules
}
```

The weight goes up by `step` once every working set reaches the top of its rep
range, rated at or under the effort its target asks for.

- **The effort asked** is the set target's `rir`. Like a rep range, it comes
  from the session's sets, unless the rule names it by week (below).
- **The effort given** is the set's own rating, as reps in reserve:
  `10 - rpe`.

What one session does (`Progression.next`), over its working sets: ticked, not
warm-ups, not supplemental.

| The session                                                        | The base                 |
|--------------------------------------------------------------------|--------------------------|
| every set at the top of its range, each rated at or under its `rir` | grows by `step`, or by the AMRAP table |
| a set rated harder than asked                                      | holds                    |
| a set that asks for an effort and wasn't rated                     | holds                    |
| a set inside its range, short of the top                           | holds                    |
| a set short of its range                                           | a miss; cut after `miss.after` in a row |
| a lighter week                                                     | holds, and counts for nothing |

A set that asks for no effort is judged on its reps alone, so a rule whose
sets name no `rir` anywhere reads like `rangeThenWeight`. The author chooses
which sets are rated by which sets ask.

A session harder than asked that made its reps is not a miss. It holds, and
the streak of misses breaks, as it does on any session that made its reps.

Half points work both ways: `rir` 1.5 is met by an `rpe` of 8.5 or less. The
easiest rating, an `rpe` of 1, says nine in reserve, so a target asking for
more than nine is read as nine.

### The effort asked, by week

`rir` on the rule is a list with one entry per program week, repeating the way
a wave does: week 6 of a five-week list is its first week again. Each entry is
0 to 9 in halves, and the list has 1 to 52 entries (`400 invalid_rule`
otherwise). A list that should line up with the program's lighter weeks
includes them, the way `waves` include a deload: `[3, 2, 1, 0, 4]` beside
`deload: {"every": 5}`.

`PlannedSession.of` sets each plain working set's `rir` to the week's, in
place of whatever the set stored:

- Warm-ups and supplemental sets take none. Neither do failure and drop sets,
  which name their own effort.
- A test session keeps its sets as written: a test finds a max.
- A lighter cycle asks for the easiest effort the list names, whichever week
  it falls on. A lighter week the user takes on the hardest week must not plan
  sets to failure.

```jsonc
// nextSession, week 2 of [3, 2, 1, 0, 4]
"sets": [{"target": {"reps": {"min": 8, "max": 12}, "rir": 2}, "weight": 30}]
```

The logged set carries the target it was planned with, so the rule reads the
week's effort when the session is done. A plain set logged without one, in a
session that didn't start from its plan, is asked the rule's effort for the
week all the same: it can't add weight unrated.

Without the list, the sets keep their own `rir`.

### Why a new kind

`effortThenWeight` is `rangeThenWeight` with one more condition, and a key on
the existing kind would have been less to add. It would also have been read
wrongly by every installed build: a build keeps a rule field it doesn't know
and runs the kind it does know, so it would add weight where the rule meant to
hold. A kind a build doesn't know is carried as it arrived and the exercise
runs as written (`Program.fromJson`), which is wrong in the safe direction.
That is the route `docs/2026-10-13.programs.md` planned for a new kind.

The by-week list lives on the rule for the same reason. `WaveSet.fromJson`
reads only what it knows, so an effort key on a wave set would be lost on an
older build's next save.

### What it costs

Nothing on the server but validation: `rules` is JSONB on the program row, the
engine runs on the device, and the plan is read per request as before. No
migration.

`scripts/programs_content.py` knows the kind too, and holds a library program
that uses it to three things:

- It has an effort to read: `rir` on the rule or on a working set, and not
  both, since the list would replace the sets' own.
- It says `min_app`, as any shape newer than the first library build must.
- That `min_app` is no older than the first app build that runs the rule
  (`FIRST_APP`). No build does yet, so until heart-of-yours#765 ships and its
  version is written there, no library program can use the rule.

## The trend (heart-api#37), designed and not built

A plateau and a suggestion are one reading of the same sessions: what an
exercise's last sessions did against what was asked. With a rule the reading
ends in a step, and a run of misses that ends in a cut is already a plateau
being answered. Without a rule it can only describe. So #37's "plateau and
regression" becomes one fold with two inputs, not a detector of its own.

**The fold.** One exercise's sessions, oldest first, each a time and a value.
It answers with numbers:

- `sessions` in the window;
- `best`, and when it was set;
- `stalled`: the sessions in a row, at the end, without a new best, and the
  days they span;
- `recent` against `earlier`: the median of the last three sessions and of the
  three before them.

**The value it folds.**

- Under a rule: the exercise's base. `stalled` is then "held four sessions",
  misses and cuts among them, read from the program's own bases and workouts.
- Without one: the session's estimated one-rep max for a lift logged by weight
  and reps, else the first measure its chart plots (`toSessionMetrics`).

**Where it shows.** On the exercise history in `/me` and MCP, and per exercise
on a program. In the app it belongs where a rule is offered or changed: "held
four sessions" is the moment to pick a rule, lower a base, or repeat a week.
Those are requests for heart-of-yours when this is built.

**It draws no conclusion on the server.** Like `/me/balance`, it carries no
threshold of its own. Whether "no new best in five sessions" is called a
plateau is copy, and the app's.

Rest between sets and training load stay in #37 as they were. They are folds
over the same sets and share nothing with this one.

## Compatibility

All additive under the compatibility floor.

- A build before heart_models 2.67.0 carries `effortThenWeight` untouched and
  runs the exercise as written: the weights its template stores, no growth. A
  coach's program sent to a client on such a build reads the same way.
- The base's bump is written by the device that saved the workout, so two
  devices on different builds can't disagree about one session: the older one
  writes nothing.
- `GrowthRule` is sealed. The app's own switches over it need the new case
  when it takes 2.67.0.

Health rule: nothing here is health-shaped. `rpe` is a rating the lifter
types into the log, and it was already stored on a set.

## Open

- **How many sets must be rated.** Every working set that is asked for an
  effort, as built. Under a by-week list that is every plain working set. If
  rating each set proves too much to ask, the choices are to lay the week's
  effort on the last working set only, or to let one rated set speak for the
  exercise.
- **A bigger step for a session far easier than asked.** The AMRAP table does
  this for reps. Nothing does it for effort yet.
- **The trend's numbers.** The window, three against three, and whether days
  or sessions name a stall.
