# Reads that survive a newer vocabulary

How `heart_models` 2.11.0 reads a payload carrying a value the reading build
doesn't know, and why it carries that value instead of dropping or fixing it
(heart-api#125). Written from the code as it stands.

## Why

An app version in the stores stays installed for months, and shipped apps
can't be patched. The server and the CDN add values on their own schedule — a
category, a set type, a goal metric, a movement word — and until now one
unknown word failed the whole response that carried it: `Category.fromString`
threw on `Weighted Distance`, so a 1.11 install downloading the library got no
catalog at all. Every addition on the server was a breaking change for every
phone.

Two promises follow, and they are the whole design:

1. A response containing a value the reading build doesn't know still yields
   everything else in it.
2. An older build never deletes or rewrites what it could not read. A workout
   carrying a set type the app doesn't know survives that app editing the
   workout.

The second is the hard one. Dropping an unknown item satisfies the first and
breaks the second: the next save would send the workout without it, and the
server's replace would delete it. Mapping it to a known value also breaks the
second: `SetType.lenient` read an unknown type as `normal`, and the next save
wrote `normal` back.

## What stays strict

The `fromString` parsers throw on an unknown word, as before. They are what the
server validates request bodies and query strings with (`json.parsed('metric',
GoalMetric.fromString)` and friends), and a bad word in a request is a 400,
not a vocabulary problem. Nothing here touches them; leniency lives in the
readers (`fromJson`, `fromRow`) and at the list edge.

The server reads its own rows through the same `fromRow` constructors. It
knows every value it stored, so the tolerant paths are no-ops for it; they
cost one try/catch per item.

## Shape

Three moves, chosen by what the unknown value sits on.

### A list is read item by item: `readEach`

```dart
final goals = readEach(json['goals'] as List, Goal.fromJson);
goals.items;   // what this build read
goals.unread;  // the raw items it could not, in order
```

An item the reader rejects — an unknown word (`ArgumentError`), a field of a
shape this build predates (`TypeError`), a malformed date or number
(`FormatException`) — is set aside in `unread` instead of failing the list.
Anything else the reader throws is a bug, not a vocabulary, and propagates; so
does an item that isn't a JSON object at all.

This is for the lists a client parses itself: the library, workouts,
templates, goals, preferences. A dropped *top-level* item is safe under the
second promise because the client never writes it back: goals and preferences
are written one at a time by id, and a workout or template the client never
loaded is one it never edits.

### A container keeps its unread children: `Workout.unread`, `Template.unread`, `WorkoutExercise.unread`

Inside a workout, dropping is not safe — the client replaces the whole
exercise list on save. So `Workout.fromJson`/`fromRow` read exercises with the
same item-by-item rule and keep the ones it couldn't read as the raw JSON they
arrived as, remembering where each sat. `WorkoutExercise.fromJson` does the
same for sets. `Template` does the same for its exercises.

`toMap` writes them back in place. An unread exercise is spliced at its
original index among the exercises the build can see (approximate once those
were reordered or removed; the item itself is untouched), and the workout's
`order` sequence is assigned over the merged list — the server refuses a
repeated `order`, and the unread exercise arrived with one. A template's
exercises carry no `order`; position is the whole of it.

Emptiness is widened to match. `Workout.toMap` and `removeEmptySets` drop an
exercise only when it has neither a readable set nor an unread one, and an
exercise whose every set is unread still names its exercise in `toMap`. An
emptied editor row — no exercise, no sets — serializes as before, because the
server tells it from a malformed one by exactly that absence.

What a copy does with them follows from what the copy is for. `copy(sameId:
true)` and `Template.copyWith` carry them: the same record, edited. A same-id
workout copy is the session as it is — every exercise and set keeps its id and
state, and each exercise's unread sets come along with the workout's unread
exercises (heart-api#131), so a save of the copy carries exactly what a save of
the original would. A fresh-id `copy()` and `Template.toWorkout()` leave them
behind: a repeat or a new session starts from what this build can see, and the
raw items carry ids that must not be minted twice.

Why the whole exercise, not a carried category word on `Exercise`? Because
`ExerciseSet`'s constructor keeps only the measurements the category calls
for. Reading a Weighted Distance set under a stand-in category would drop its
weight and distance at parse time, and the next save would write the loss.
An opaque exercise loses nothing.

### A set with an unknown type carries the word: `ExerciseSet.setTypeValue`

A set's type is the one field where a stand-in is useful: the set's
measurements are all readable, and hiding the set would misreport the
exercise's volume and records. So an unknown `set_type` still reads as
`SetType.normal` — the set shows and counts, as it did under `SetType.lenient`
— but the set now keeps the word it arrived with, and `toMap` and `copy()`
write that word, not `normal`. Assigning `setType` replaces it: the user chose
a type this build knows.

`setTypeValue` is the word a writer carries. A writer that persists a set's
type from `setType.value` would still rewrite the newer type as `normal` on
the way through its own store; it keeps `setTypeValue` instead.

### Annotations read as absent: `Movement`, `Health`

`Movement.fromJson` with an attribute word this build doesn't know reads the
whole annotation as `Movement.empty()`: no substitutes offered, no movement
filter matched. Reading a bad axial load as "unloaded" would hand a lifter
avoiding spinal load exactly the exercise they are avoiding; failing the
exercise would make it vanish from the library. "Nothing claimed" is the
honest reading of an annotation the build cannot interpret.

`Health.fromJson` with an unknown activity reads as no annotation, so
`Health.resolve` falls back by category — never a guess at the word.

Both used to throw so bad content would fail loudly. Content validity is the
publishing pipeline's job (`scripts/validate_library.py` checks the library
against its schema before it is published); a reader seeing a word it doesn't
know is seeing a newer vocabulary, not bad content.

## What the client has to do

The package carries unread items through its own `toMap`; the client has to
carry them through everything else of its own.

- Read lists with `readEach` (or its own equivalent) wherever it maps a JSON
  array through a `fromJson`: library, workouts page, templates, goals,
  preferences.
- Persist `unread` for workouts and templates in its local store, and feed it
  back into `fromJson` on read, or a workout edited from the local mirror
  loses them between the download and the save.
- Store a set's type from `setTypeValue`, not `setType.value`.
- Decide whether a workout whose exercises are all unread counts as "has
  detail" for its own refetch logic; it iterates as empty.
- Optionally tell the user: "N items need a newer version of Heart".

heart-of-yours#277 is the ticket.

## Gaps

- Enum fields that remain fail-the-item: an `Exercise` with an unknown
  `category`, `target` or `unit_system` is unread wherever it appears, and a
  `Goal` with an unknown `metric` or `cadence`, a `ChartPreference` with an
  unknown `type`, an `ExercisePreference` with an unknown unit are dropped at
  the list edge by `readEach`. All of these are safe under the second promise
  (nothing writes them back) but the user sees nothing of them.
- `Template.fromWorkout` and `Workout.fromExercises` build from readable
  exercises only; a template saved from a workout with unread exercises does
  not inherit them.
- Position of a spliced-back exercise is approximate after the user reorders
  or removes exercises around it.
- The server's own `fromRow` paths carry the try/catch for no benefit; it is
  one per item and was not worth a second constructor.
