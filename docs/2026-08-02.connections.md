# Connections

How the social graph works and what it gates. Written from the code as it stands — nothing here is a
proposal unless it says so.

The five defects this study turned up have since been fixed; they are kept below with their evidence
because the shape of each explains why the code now looks the way it does.

A **connection** is one relationship between two users, in one domain, with a role on each side. It
is the only social primitive in the system: comments, shared workouts and template assignment are
all gated on it, and it has no other job.

## The data model

```sql
connections (
  initiator_id   TEXT NOT NULL REFERENCES profiles (id) ON DELETE CASCADE,
  target_id      TEXT NOT NULL REFERENCES profiles (id) ON DELETE CASCADE,
  initiator_role TEXT NOT NULL,
  target_role    TEXT NOT NULL,
  domain         TEXT NOT NULL,
  status         TEXT NOT NULL DEFAULT 'pending',
  status_by      TEXT REFERENCES profiles (id) ON DELETE SET NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (initiator_id, target_id, domain),
  CHECK (initiator_id <> target_id),
  CHECK (initiator_role IN ('COACH', 'STUDENT', 'PEER')),
  CHECK (target_role    IN ('COACH', 'STUDENT', 'PEER')),
  CHECK (status IN ('pending', 'active', 'declined', 'severed', 'blocked', 'paused'))
  -- domain is deliberately unconstrained; see below
)
```

Three properties follow from that shape and explain most of the code:

**One row, two perspectives.** A relationship is stored once, with *both* roles on it. Neither user
owns it. Every read normalises to the caller's point of view — you always see the other person as
`targetId` and your own role as `role`:

```sql
-- _getConnection
SELECT CASE WHEN initiator_id = @userId THEN target_id      ELSE initiator_id END AS target_id,
       CASE WHEN initiator_id = @userId THEN initiator_role ELSE target_role  END AS role,
       domain, status, created_at
```

`_listConnections` does the same with a `UNION ALL` of the two directions. Writes are direction-blind
in the other way — `_deleteConnection` and `_updateConnectionStatus` both match
`(initiator, target, domain) IN ((@a,@b,@d), (@b,@a,@d))`, so either party addresses the same row.

**Roles are reciprocal and stored, not derived.** `ConnectionRole.reciprocal` maps coach↔student and
peer↔peer, and `createConnection` writes both columns at once. So a coach's list shows
`role: COACH` and the student's shows `role: STUDENT` for the same row — no join, no inference.

**Domain is part of the key.** The same two people can be coach/student in `fitness` and peers in
`running` at the same time; those are two rows. Roles and status are per-domain, not per-pair.

### The id is synthetic

There is no surrogate key. `Connection.id` is computed:

```dart
String get id => '$targetId|${role.value.toUpperCase()}|${domain.value.toUpperCase()}';
```

and `Connection.fromId` parses it back for `DELETE`/`PUT /connections/:connectionId`. A malformed id
raises `ArgumentError`, which the route turns into a 400.

The consequence worth knowing: **the id is viewer-relative.** The coach and the student hold
different ids for the same relationship (`student|COACH|FITNESS` vs `coach|STUDENT|FITNESS`). It is
an addressing scheme, not an identity — don't store it, don't compare two users' ids, and don't
expect it to survive a role change.

### Vocabulary

| enum               | values                                                          | wire form                                                |
|--------------------|-----------------------------------------------------------------|----------------------------------------------------------|
| `ConnectionRole`   | `coach`, `student`, `peer`                                      | `COACH` / `STUDENT` / `PEER`                             |
| `ConnectionDomain` | `fitness`, `swimming`, `running`, `general`                     | `FITNESS` … (uppercased on output, **stored lowercase**) |
| `ConnectionStatus` | `pending`, `active`, `declined`, `severed`, `blocked`, `paused` | lowercase                                                |

All three `fromString` factories are case-insensitive and **throw** on anything outside their
vocabulary.

**Roles and statuses are also constrained in the schema; domain deliberately is not.** The code
*branches* on role and status — reciprocal mapping, the transition table, the `IN ('COACH', 'PEER')`
gate lists, every `status = 'active'` check — so those vocabularies are load-bearing, and adding a
value to either means touching code anyway. Pinning them in the database is free.

Domain is an opaque partition key: **not one gate filters on it.** It exists so the same pair can
hold separate relationships for separate activities. Adding "cycling" is a product decision, and a
`CHECK` would turn it into a schema migration for no protection the input layer does not already
give — `ConnectionDomain.fromString` rejects unknown values before they reach the column. The cost of
that choice is that a direct SQL write *can* put an unknown domain in the column, and `fromRow` would
then throw on read; that is the same exposure as any hand-corrupted data.

Domain is also the odd one out on case: `toMap()` uppercases it while the column holds lowercase —
harmless because parsing is case-insensitive, but it means you cannot compare a wire value to a
column value without normalising.

### The status machine

`ConnectionStatus.canTransitionTo` is the whole of it:

| from       | may become                      |
|------------|---------------------------------|
| `pending`  | `active`, `declined`, `blocked` |
| `active`   | `paused`, `severed`, `blocked`  |
| `paused`   | `active`, `severed`, `blocked`  |
| `declined` | `pending`, `blocked`            |
| `severed`  | `pending`, `blocked`            |
| `blocked`  | `severed`                       |

Same-to-same is always rejected, so a no-op `PUT` is a 400.

**The transitions live only in Dart**, but the *vocabulary* is now enforced by
`connections_status_check`, so a value outside the enum cannot reach the column. Two of these
transitions are further restricted by who is asking — see defects 2 and 3.

## API surface

All four routes are authenticated; `request.userId` is always one side of the relationship.

### `GET /connections`

Every connection the caller is party to, either direction. Optional `?role=` filters on **the
caller's own** role — `?role=COACH` lists the people you coach, not your coaches.

```jsonc
// 200
{"connections": [
  {"id": "u-2|COACH|FITNESS",
   "targetId": "u-2",
   "role": "COACH",          // the caller's role
   "domain": "FITNESS",
   "status": "active",
   "createdAt": "2026-07-01T09:00:00.000Z"}
]}
```

Unpaginated and ordered `created_at DESC`. An unknown `role` value is a 400.

### `POST /connections`

```jsonc
// request
{"targetId": "u-2", "role": "COACH", "domain": "FITNESS"}
// 200 → the Connection, status "pending"
```

`role` is **the role the caller is claiming for themselves**; the reciprocal is written to the other
column. Idempotent in a useful way: `ON CONFLICT DO NOTHING` followed by a `UNION ALL` that reads the
existing row back, matching on *either* direction. So re-posting returns the existing connection, and
posting when the other person already asked returns their row rendered from your perspective —
you never end up with two rows for one pair in one domain.

A `targetId` that is not a profile → 404. Connecting to yourself, a missing `targetId`, or an
unknown `role`/`domain` → 400 from `ConnectionCreateIn`.

### `PUT /connections/:connectionId`

```jsonc
// request
{"status": "active"}
// 200 → the updated Connection
```

400 on a missing or unknown `status`, a malformed id, or an illegal transition (the `StateError`
from `canTransitionTo` becomes a `BadRequest`). **403** when the transition is legal but not yours to
make: accepting or declining belongs to the person who received the request, and only the blocker
lifts a block.

### `DELETE /connections/:connectionId`

204, from either side. Deleting something already gone is a silent no-op. **403** while a block
stands and you are the party it is against — a hard delete would otherwise make you re-requestable,
which is unblocking yourself.

## What connections gate

Four call sites. Three now agree; the fourth is dead code.

| gate                            | where                                             | roles required  | status required |
|---------------------------------|---------------------------------------------------|-----------------|-----------------|
| commenting                      | `_areConnected` via `routes/comments.dart`        | any             | **`active`**    |
| assigning a template or folder  | `_shareTemplates` `_allowed` CTE                  | `COACH`, `PEER` | **`active`**    |
| reading another user's workouts | `_listWorkouts` / `_getTargetWorkout` `_auth` CTE | `COACH`, `PEER` | **`active`**    |
| `Connection.allows()`           | `heart_models`                                    | `coach`, `peer` | none            |

The workouts gate required no status until 2026-08-02 and template assignment until 2026-08-01 —
both are described under "Defects, fixed" below. `Connection.allows()` still has no callers at all:
the model's opinion about permission, written and never wired up. It should either be deleted or
become the one place the rule lives; leaving a fourth, subtly different answer lying around is how
the other three drifted apart in the first place.

## Defects, fixed

Each was confirmed by running it against a live Postgres before being fixed, and each now has a
regression test. All five landed on 2026-08-02 alongside
`2026-08-01.folders-and-connection-guards.sql`.

**1. Reading another user's workouts ignored connection status.** The `_auth` CTE in `_listWorkouts`
and `_getTargetWorkout` checked only that a row existed with the right role. A **pending** request —
one the other person had never seen, let alone accepted — granted full read access to their workout
history, including images. So did a `declined`, `severed` or `blocked` one.

> Probe: user B has one workout. A sends a coach request; `areConnected(A, B)` is `false`.
> `getWorkouts(userId: A, targetUserId: B)` returned **1 workout**.

Both CTEs now require `status = 'active'`, matching `_areConnected` and `_shareTemplates`. Covered by
a case per non-active status in `workouts_db_test.dart`.

**2. The requester could accept their own request.** `changeConnectionStatus` resolved the row with
`_getConnection`, which matches from either side, then updated it. Nothing checked that the caller
was the *target* of a pending request rather than its author.

> Probe: A creates a pending connection to B, then A alone calls `changeConnectionStatus(→ active)`.
> Result: `active`, and `areConnected(A, B)` became `true`. B was never involved.

Combined with defect 1 this was the sharp one: a stranger could self-approve and then read your
history. The rule is now in the `UPDATE`'s own `WHERE`, not in Dart, so it cannot be raced past:

```sql
AND (@newStatus NOT IN ('active', 'declined') OR status <> 'pending' OR initiator_id <> @actorId)
```

Note it is scoped to `status = 'pending'`, so *resuming* a paused connection stays either party's
call — the restriction is specifically on answering a request.

**3. Deleting a connection unblocked the person who was blocked.** `DELETE` matched the pair in
either direction with no regard for status, so the blocked party could remove their own block and
re-request.

> Probe: blocker sets `blocked`; the blocked user calls `deleteConnection`; the row is gone.

Fixing this needed schema: the table recorded *that* a row was blocked but not *by whom*, so there
was nothing to authorise against. `connections.status_by` now records who last set the status, and
both the delete and the `blocked → severed` transition require it to be the caller. The delete
statement returns `(deleted, existed)` so a refusal (403) stays distinguishable from deleting
something already gone (still a silent no-op, as it has always been).

**4. Unknown enum values were silently coerced.** `ConnectionRole.fromString`,
`ConnectionDomain.fromString` and `ConnectionStatus.fromString` all ended in `orElse:` rather than a
throw:

> `role "sensei" → peer`, `domain "yoga" → general`, `status "nonsense" → pending`.

A client asking to be someone's coach and typo'ing the role got a peer connection and a 200. All
three now throw `ArgumentError`, which the `.parsed()` input helper turns into a 400 naming the bad
field — matching `GoalMetric` and the rest of the newer enums. `connections_initiator_role_check`,
`connections_target_role_check` and `connections_status_check` mirror the role and status
vocabularies in the database; domain is left unconstrained on purpose (see "Vocabulary" above).

**5. A user could connect to themselves.** Nothing rejected `targetId == req.userId`, so the insert
succeeded and produced a pending self-connection. Now rejected in `ConnectionCreateIn` with a 400,
and backstopped by `connections_no_self_check`.

## What changed in the code

- **`initiatorId` → `actorId`** on `getConnection`, `deleteConnection` and `changeConnectionStatus`.
  The old name was actively misleading: it meant "the authenticated caller", who is frequently *not*
  the row's initiator, and reading it as the latter is what let defect 2 through. `createConnection`
  keeps `initiatorId`, where it is accurate.
- **A typed input layer** — `lib/inputs/connections.dart` with `ConnectionCreateIn`,
  `ConnectionStatusIn`, `ConnectionListQuery` and `ConnectionRef` (which owns the composite-id
  parsing). This was gap 1; connections was the last resource still doing
  `body['targetId'] as String`.
- **Optimistic locking on status.** The `UPDATE` carries `AND status = @expectedStatus`, so a
  concurrent change loses instead of silently overwriting. The read-then-write in
  `changeConnectionStatus` survives only to produce a friendly message for an illegal transition.

## Gaps

1. **`getConnections` is unpaginated.** Fine at current scale, out of step with every other list
   endpoint, and it will need a cursor before a coach has a real roster.
2. **No status history.** `status_by` records *who* moved it last, but not what it was before or
   when. Status is still overwritten in place and `DELETE` is still hard, so there is no record of a
   block having existed once it is lifted. Anything resembling abuse handling needs one.
3. **`Connection.allows()` is dead code** with a fourth opinion about permission. Delete it or make
   it authoritative.
4. **The domain case mismatch stands** — `toMap()` uppercases while the column holds lowercase.
   Harmless because parsing is case-insensitive, but it means wire values and column values cannot be
   compared without normalising.
5. **`status_by` is backfilled by guess** for pre-existing rows (see the migration comment). Safe
   today only because no deployed environment can have a blocked row predating the column. If that
   assumption ever breaks, the block guard is trusting a guess.

## On generating an OpenAPI spec

Worth recording while it is fresh, since this subsystem is a good stress test for it.

What is already machine-readable:

- **Routes.** `routes/index.dart` is a literal `Map<(String, Method), ModelHandler>` — path, verb and
  handler for every endpoint in one table, including the `:param` segments.
- **Inputs.** The `…In` / `…Query` classes (`lib/inputs/`) are one class per endpoint with typed
  fields and a single `fromRequest`. Their field types *are* the request schema.
- **Errors.** Every failure is an `ApiException` subclass with a fixed `statusCode` and `toMap()`, so
  the error responses are enumerable.

What is not:

- **The link from a route to its input class** exists only inside the handler body. Nothing declares
  that `POST /templates` consumes a `TemplateCreateIn`.
- **Response schemas.** Handlers return `Future<Model>`, and `Model` is just `toMap()` — the shape is
  whatever that method builds at runtime, with null-aware keys (`'folderId': ?folderId`) that make
  fields conditionally absent. There is no static description of a response body anywhere.
- **Connections' `id`** is viewer-relative and composite rather than a uuid, so it needs prose a
  schema cannot carry. `ConnectionRef` at least names the parsing in one place now.

So the cheap first step is a convention, not a tool: make handlers declare their input and output
types in a way a generator can read — a typedef, an annotation, or a registry beside `routes`. Every
resource is now on `lib/inputs/` (connections was the last holdout), so the input half is ready; the
response half is the work.
