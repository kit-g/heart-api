# MCP Apps widgets

Three read tools gain a rendered view (heart-api#183, rollout step 5 of
`2026-10-04.mcp.md`). A host that supports MCP Apps shows a card. A host that doesn't still gets
the text and structured result, which is unchanged. Written from the code as it stands.

| Widget            | Tool                   | Resource                              |
|-------------------|------------------------|---------------------------------------|
| Workout card      | `get_workout`          | `ui://heart/workout.v1.html`           |
| Exercise progress | `get_exercise_history` | `ui://heart/exercise-progress.v1.html` |
| Records           | `get_personal_records` | `ui://heart/records.v1.html`           |

## The spec followed

**MCP Apps, SEP-1865, stable revision 2026-01-26** (`specification/2026-01-26/apps.mdx` in
the `modelcontextprotocol/ext-apps` repo; the SDK was at v2.0.3 when this was written, and its
`LATEST_PROTOCOL_VERSION` is still `2026-01-26`). ChatGPT's side is OpenAI's "MCP Apps
compatibility in ChatGPT" page: it renders the standard keys and still honours
`openai/outputTemplate` and `window.openai` as aliases.

What the server does with it:

- **Capabilities.** `initialize` adds `resources: {listChanged: false}` next to `tools`, and
  `server/discover` adds `resources: {}`. Nothing else is advertised. The extension is negotiated
  by the *client* (`capabilities.extensions["io.modelcontextprotocol/ui"]`). A server that
  declares MCP Apps tools just carries `_meta`, which is also what the reference SDK does.
- **Tools.** The three tools carry, in `tools/list`:
  `_meta: {ui: {resourceUri}, "ui/resourceUri": …, "openai/outputTemplate": …}`, all naming the
  same URI. `ui.resourceUri` is the standard key. The flat `ui/resourceUri` is the deprecated
  form the SDK still writes for early hosts, and `openai/outputTemplate` is ChatGPT's older key.
  The `_meta` goes out to every host, whatever it declared. The server is stateless, a 2025
  client names its capabilities only in `initialize`, and a host that doesn't render apps ignores
  the key. `visibility` is left at its default (model and app).
- **Results.** `tools/call` returns what it returned before: `content` (the JSON as text),
  `structuredContent` and `isError`. The widget reads `structuredContent`. Nothing is added for
  the widget alone, so what the model sees and what the card draws are the same data.
- **Resources.** `resources/list` lists the three pages, and `resources/read` serves one by URI.
  `resources/templates/list` answers with an empty list, because some clients ask for it once
  `resources` is advertised, and this server answers an unknown method with HTTP 404.
  Each has `mimeType: "text/html;profile=mcp-app"` and `_meta.ui.prefersBorder: false`, because the
  page draws its own card. There is no `csp` key, so the host's restrictive default applies:
  `connect-src 'none'`, scripts and styles inline only. An unknown URI is `-32602` with
  `data.uri`, the code 2026-07-28 gives a missing resource. 2026-07-28 clients also get
  `ttlMs`/`cacheScope: public` on both, since the pages are the same for every account.
- **Counting.** `resources/*` needs the same token as everything else, but doesn't count
  against the rate limit. The pages hold no account data, and a host may fetch them once per
  conversation.

**The URI is the cache key.** OpenAI says so outright, and hosts may prefetch and cache. A change
that a cached copy mustn't be mixed with, such as a different reading of the result, ships as
`.v2` with the tool pointing at it. The old URI stays listed and served until no host could hold
it. A fix that reads the same result the same way can stay at `.v1`. The shared shell (tokens,
formatting, bridge) is part of all three pages, so a shell change that needs a new URI bumps
all three.

## The pages

Static HTML, one per widget, kept as Dart string constants under `api/lib/mcp/widgets/` (parts
of `api/lib/mcp/widgets.dart`). The Lambda zip is the compiled `bootstrap` and the CA bundle, and
nothing else ships, so the pages live inside the binary. A page is inline CSS and script with no
external reference. A test holds each page to that and to 50 KB gzipped (`widget pages` in
`api/test/mcp/server_test.dart`).

Every card is a Jaspr component in `pages/lib/cards/` (heart-api#303): `WorkoutCard`,
`ProgressCard`, `RecordsCard` and `TemplateCard`, with no browser imports so a share page can
render them on a server, and `McpAppsBridge`, the bridge below in Dart. Their styles sit beside
them in `styles.dart`, on top of the design system's tokens (`package:heart_design`). Each page's
script is `pages/cards/<name>.dart`, compiled by dart2js `-O4` (`make cards`,
`pages/tool/emit_cards.dart`) into the gitignored `api/lib/mcp/widgets/cards.g.dart` with its
styles: about 135 KB a page, 43 KB gzipped. `make bootstrap`, the api's `build-ApiFunction` and
every CI job that analyzes or tests the api run `make cards` first.

Two things the Dart bridge must keep doing, both found the hard way: compare the message source
with `strictEquals(window.parent)`, not `==`, which under dart2js `-O3` and up reads a property
off the cross-origin parent and dies on a sandbox `SecurityError`; and measure right after
each draw, as below.

**The bridge** is the view's half of the spec with no SDK (`McpAppsBridge`):

1. `ui/initialize` with `appInfo`, `appCapabilities.availableDisplayModes: ["inline"]` and
   `protocolVersion: "2026-01-26"`. The answer's `hostContext` gives `theme`, `locale` and
   `timeZone`.
2. `ui/notifications/initialized`.
3. `ui/notifications/tool-result` (a `CallToolResult`) draws the card. `tool-input` is ignored,
   since the result is the whole input.
4. `ui/notifications/size-changed` goes back up after each draw and whenever the content's
   size changes. It is measured synchronously, not on the next animation frame as the SDK does,
   because a browser may throttle frames for a cross-origin iframe that is still a few pixels
   tall. `host-context-changed` re-themes and redraws. `ui/resource-teardown` and `ping` are
   answered with `{}`, and any other request with method not found, so a host never waits on
   the page.
5. Under ChatGPT's older runtime, `window.openai.toolOutput` and the `openai:set_globals` event
   feed the same renderer.

Every string from a result goes into the page through `textContent`, never as markup. A
result the page can't draw shows a line pointing at the text answer, and a tool error shows its
own message.

**Design.** The Ink preset of the Heart design system, the tokens `site/assets/site.css`
mirrors from the app's `tokens.dart`, light and dark. The OS setting decides unless the host
sends `theme`. No shadows, 12px cards, 8px buttons. The accent is a fill only (the chosen metric
chip), and accent-ink is used for text and lines. The faces are IBM Plex Sans and Literata, named
but never fetched: the default CSP blocks font hosts, so a host without them shows the system
face. Host style variables (`--color-*`, `--font-sans`) are not adopted. The card reads as
Heart, not as the host.

- **Workout card**: the design system's workout card, which the app's done screen ends on
  (`WorkoutItem`): title, date and time, hero stats, hairline, then each exercise with every set.
  The stats are duration (`end − start`), total volume, distance, and `caloriesEstimate`
  labelled **"Calories, estimated"**, with a hover line saying it is an estimate and not a
  measurement. Volume is Σ weight × reps over done sets that aren't warm-ups. Assisted
  bodyweight is left out, because its weight is help, not load. To tell which exercises are
  assisted, `get_workout` now names each exercise's `category`, an additive field the model
  gets too. Warm-up, drop
  and failure sets show `W`/`D`/`F`, numbered sets count from 1, and a set not done is faint.
- **Exercise progress**: the app's progress chart, a point per session from oldest to newest,
  plotted by index. The axis shows one label per day, thinned to about six. Under the chart is
  the app's one-line summary ("Top set, 9 Sept to 14 Oct: 102.5 kg, up from 92.5 kg."), then the
  sessions newest first. Chips switch between the metrics `toSessionMetrics` returned, in its
  order. A key the page doesn't know shows under its own name. The page notes when more sessions
  are paged out ("There are older sessions than these.") and when pending anomalies are among
  them.
- **Records**: a card per exercise, with sessions and last trained, then each record (heaviest,
  estimated 1RM, best set volume, most reps, lightest assistance, longest distance, longest
  duration, best pace, the rep maxes), its date and what it beat ("was 107.5 kg × 1"). Totals
  close the card.

**Health.** The three results carry no health data, so neither do the pages. The workout card
shows the MET estimate only, labelled as one, and nothing a watch measured.

## Looking at one locally

```
cd api && dart run tool/widget_harness.dart [out-dir]    # default ../build/widgets (gitignored)
```

This writes `<widget>.html` per widget: a page that plays the host. It frames the widget in an
`allow-scripts` sandbox (no same origin, like a real host), answers `ui/initialize` with
`en-GB`/`Europe/London`, posts a sample result shaped like the tool's, and fits the frame to the
size the widget reports. Open it in a browser, with `?theme=dark` or `?theme=light` to set the
host's theme. Headless Chrome screenshots it too:
`"…/Google Chrome" --headless=new --window-size=480,900 --virtual-time-budget=3000 --screenshot=out.png "file://…/records.html?theme=dark"`.
Now and then the shot fires before the cross-process messages land, which shows an empty
frame. Taking it again is the fix. A frame stuck at its first height is the same throttling:
`?height=900` holds it open. `?units=imperial` sends an imperial user's result, and `?width=760`
frames the card as wide as a desktop host's column.

### Units and layout (2026-10-21)

Every result a card draws carries the user's `unitSystem`, as `get_profile` names it, added
where the tool call is answered. The tools still measure in kg and km at three decimals, so a
weight entered in pounds converts back whole. The cards show pounds and miles for an imperial
user, pace per mile included, and the note beside the result asks the model to answer in those
units too.

The workout card collapses sets in a row that read the same into one line (`1–3  130 lb × 14`;
`W ×2` for tagged ones), and its exercises flow into columns of at least 220px, so a wide host
column holds three side by side instead of one long list.

## Gaps

- **Claude Code's fallback to text** still needs a look by hand. ChatGPT draws the cards (seen on
  prod, 2026-10-21).
- **ChatGPT draws a card of its own too.** Under ours it wrote its own summary of the same
  workout. Every result a card draws carries a second text item saying that a host showing the
  card has the model answer the question rather than restate it. The server can't tell whether
  a host draws cards, so the note is conditional. It is a request, not a switch: the model
  may still restate.
- **Duration is `end − start`**, as `list_workouts`' `minutes` is. The app takes pauses off, and
  `get_workout` doesn't return them.
- **ChatGPT plan availability** is still the open question from `2026-10-04.mcp.md`.
- The template preview widget came with the writes: `ui://heart/template.v1.html` on
  `create_template` and `update_template`, in `2026-10-18.mcp-template-writes.md`.
