# Anonymous → account upsync: idempotent replay 

How the server behaves when the app replays an anonymous user's local store through the
existing write endpoints on sign-in (heart-of-yours#89, heart-of-yours#96). This is artifact
one of the handoff to heart-of-yours#96 — the frontend ticket covers the replay loop itself,
the uid rekey, and the progress UI; this document covers only what the server now guarantees.

## The two cases

1. **Link** — a Google/Apple credential is linked to the anonymous Firebase user. The uid is
   the same before and after linking; the first authenticated call creates the profile, and
   the replay then runs into an account with no history.
2. **Sign in to an existing account** — linking fails (`credential-already-in-use`), the app
   signs the user in instead, the uid changes, the app moves its local rows onto the new uid,
   and the replay runs into an account that **already has history**. Nothing anonymous ever
   reached the server, so the only things that can collide are the account's *natural keys* —
   a custom exercise or a template folder with a name the account already uses.

In both cases the replay can be interrupted (killed app, dropped connection, backgrounded
mid-loop) and re-run from the top. Every write below is safe to repeat for that reason, not
just for case 2.

## The contract

**Every create in the replay accepts an optional client `id`.** `POST /exercises`,
`/workouts`, `/templates`, `/template-folders`, `/goals` all take the same v7 uuid the app
already mints for local-first identity (`isUuidV7`-validated; a present-but-malformed one is a
`400`). Send it — the whole idempotency contract keys on it.

- **A create whose `id` already exists *for this account* is not an error.** It returns that
  existing row, unchanged, with `200` instead of failing. The response body is the current
  server state of that row — if the retried payload differs from what's stored, the difference
  is ignored. The id wins; use `PUT` if you actually want to change what's there.
- **A create whose `id` already exists for *someone else's* row is a `403`** with
  `code: "id_taken"`. This should not happen in a normal replay (ids are v7-random-enough, and
  a signed-in account's own rows are never anonymous-uid rows), but it is the server's answer
  if it does — never someone else's data.
- **A name collision resolves to the existing row, not an error** — only for the two resources
  that have a natural key (see the table). A custom exercise or a folder whose name (compared
  case-insensitively) the account already has returns `200` and **that existing row's `id`**,
  which will not be the id you sent. **Rewrite every reference to the id actually returned**
  before replaying anything that points at it — see "References to rewrite" below. Templates
  and workouts have no natural key: two rows with the same name are just two rows, replayed
  independently.
- **Freshly-created vs already-there is the status code, not a body field.** `201` means this
  call inserted the row; `200` means it already existed, whether matched by id or by name. Sum
  the 201s and 200s across the whole replay for the "n uploaded, n already there" line — this
  contract is exactly what heart-of-yours#96 needs to compute it, nothing else to parse.
- **Content is never merged.** A retry's id match returns the stored row as-is; a retry's name
  match returns the stored row as-is. There is no field-by-field diff — the point is "don't
  create a duplicate on a repeat," not "reconcile two versions."

## Per resource

| Resource         | Endpoint                     | Natural key            | `201`              | `200` (idempotent)                                                                   | `403 id_taken`                | Other                                                                                                                                                     |
|------------------|------------------------------|------------------------|--------------------|--------------------------------------------------------------------------------------|-------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| Custom exercise  | `POST /exercises`            | name, case-insensitive | new row            | same `id` retried, **or** name already used (returns the pre-existing custom's `id`) | id belongs to another account | —                                                                                                                                                         |
| Unit preferences | `POST /exercise-preferences` | — (upsert)             | n/a — always `200` | n/a                                                                                  | n/a                           | Already idempotent; see "Unit preferences" below                                                                                                          |
| Template folder  | `POST /template-folders`     | name, case-insensitive | new row            | same `id` retried, **or** name already used (returns the pre-existing folder's `id`) | id belongs to another account | Replaces the old `400 "you already have a folder called…"`                                                                                                |
| Template         | `POST /templates`            | none                   | new row            | same `id` retried (content ignored)                                                  | id belongs to another account | Two templates may legitimately share a name — not a collision                                                                                             |
| Workout          | `POST /workouts`             | none                   | new row            | same `id` retried — the exercises/sets in the retry are never re-applied             | id belongs to another account | A **child** id (an exercise/set id nested in the payload) reused under a *different* workout id is still a `400` — that is a real client bug, not a retry |
| Goal             | `POST /goals`                | none                   | new row            | same `id` retried (content ignored)                                                  | id belongs to another account | The active-goal cap (50) still applies to a genuinely new goal; a retry never counts against it — see "Goals keep their cap" below                        |

## Replay order — part of the contract

Replay in this order, because later resources reference earlier ones and a name-merge (a
custom exercise or folder resolving to a pre-existing id) changes what those references must
point at:

1. **Custom exercises** — everything else that references an exercise id needs the merge
   outcome first.
2. **Unit preferences** — no dependency on the above; ordered here only because it's cheap and
   independent.
3. **Template folders** — before templates, for the same reason exercises come first: a
   folder's merge outcome changes which folder id a template's `folderId` should carry.
4. **Templates** — reference exercises (rewritten per step 1) and folders (rewritten per step
   3).
5. **Workouts** — reference exercises (rewritten per step 1).
6. **Goals** — last: goals reference exercises, and nothing references goals.

## References to rewrite after a name-merge

When a custom exercise or a folder create comes back `200` with an id that differs from the
one you sent (the name-merge case), rewrite every local reference to that id **before**
replaying anything downstream that points at it:

- A merged **custom exercise** id: rewrite it in any workout's exercise references and any
  template's exercise references that haven't replayed yet.
- A merged **folder** id: rewrite it in any template's `folderId` that hasn't replayed yet.

Because customs replay before folders, folders before templates, and templates before
workouts (see "Replay order"), a straightforward top-to-bottom pass — rewrite as each merge
outcome comes back, before moving to the next resource — needs no backtracking.

## Unit preferences: local wins

No change from today. `POST /exercise-preferences` is already an upsert on
`(user_id, exercise_id)`; the replay's write is last-write-wins over whatever the account
already had. The anonymous device is where the user has been training, so its preference is
the most recent intent — always overwrite, never merge or skip.

## Goals keep their cap

The 50-active-goal limit applies to the replay exactly like any other create: the 51st
*new* goal is the existing `400` with `code: "goal_limit"`, and the app should surface it the
same way it does today. A **retry** of a goal id already on the account never counts against
the cap — the cap check only runs on the insert path, which an idempotent retry never reaches.
Stages arrive with their own `achievedAt` already set where applicable, so achievements need no
separate replay step.

## Out of scope here

- The app-side replay loop, the uid rekey, the progress UI, and the "n uploaded, n already
  there" line itself — heart-of-yours#96.
- Workout images taken while anonymous: the presign path is unchanged by this contract;
  whether the app re-uploads them is #96's call.
- A bulk replay endpoint — a per-resource loop of a few hundred requests once per account is
  fine on Lambda. If real users show up with thousands of workouts,
  `POST /workouts/imports?source=heart` can reuse the CSV-import machinery later; nothing here
  precludes it.
