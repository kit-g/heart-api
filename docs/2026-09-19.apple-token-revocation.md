# Revoking Sign in with Apple on account deletion

Shipped. This is a record of what exists and why, not a task brief. Nothing here
is a proposal unless it says so. heart-api#78.

## The gap

Apple requires an app offering Sign in with Apple to call the revocation endpoint
when a user deletes their account — App Store Review Guideline 5.1.1(v), enforced
since 30 June 2022. Heart did not. A deleted account left Heart listed under
**Settings → Apple ID → Sign-In & Security → Apps Using Apple ID** forever, and a
Hide My Email relay stayed live and routed to the user.

This was never a security hole. Once the account is gone, an Apple token cannot
authenticate into anything of ours — the uid, the rows and the objects are gone.
What it buys is the review gate, which a reviewer checks in thirty seconds, and the
user's own control over their Apple ID — which "permanently deleted" ought to mean.

## Why the server owns it

Deletion is scheduled, not immediate: `deleteAccount` creates a one-shot EventBridge
schedule at `now + accountDeletionOffset` (2 days in dev, 30 in prod), leaving a
window in which the deletion can still be called off. That splits the work across
two moments days apart, and a caller is present for only the first:

|              | who is there                    | what reaches the server    |
|--------------|---------------------------------|----------------------------|
| confirmation | a caller, with the user         | a fresh authorization code |
| execution    | `accountDeletion()`, on a timer | a `user_id`                |

An Apple authorization code is single-use and expires in about five minutes, so it
cannot be carried across that gap. Revoking at confirmation instead is wrong in the
other direction: a user who then cancels has had their Apple link severed — and
their Hide My Email relay deactivated — while their account still exists.

So the code is exchanged at confirmation for a long-lived refresh token, and *that*
is revoked at execution. The exchange needs a client secret JWT signed with our
Apple private key, which must never leave the server. Hence the server.

## The shape

`DELETE /accounts` takes an optional JSON body:

```json
{"appleAuthorizationCode": "c1a2…", "appleClientId": "me.heart-of.ios"}
```

`AppleDeletionGrant` in `heart_models` 2.4.0. Both fields or neither — half a grant
is `400 incomplete_apple_grant`, because a code with no client cannot be exchanged
and dropping it silently would leave the app listed under the user's Apple ID with
nothing to show for it. A bodiless `DELETE` is unchanged and is what Google and
password accounts send.

### The client id

Apple issues a code against whichever client asked for it, and the client secret's
`sub` must name that same client or the exchange is refused with `invalid_client`.
Two are live, one per environment.

That would fit in a single config value, and does not: the client is a property of
the code Apple issued, not of this deployment. The exchange and the revoke are
thirty days apart, so the client is stored with the token it belongs to rather than
read from config twice — a config edit inside that window would otherwise break a
revoke silently, and silently is the one way this can fail.

`APPLE_CLIENT_IDS` is the allowlist the exchange checks against, comma-separated,
each entry optionally `client_id=redirect_uri` where the exchange needs one. An id
outside it is refused the way an Apple failure is: logged, and not a reason the
account survives.

## Ordering, and why it is what it is

At confirmation (`routes/account.dart`), the exchange happens *before* the schedule
is created, and the resulting grant is written in the same statement that records
the schedule ARN and timestamp.

At execution (`events/account_deletion.dart`):

1. read the grant
2. delete the account's S3 images
3. **revoke**
4. delete the profile row
5. publish `account.delete` to the Firebase queue

The grant lives on the profile row step 4 deletes, so it is read up front rather
than returned from that delete's `RETURNING`. The whole handler is an SQS message
that can be retried: reading first means every attempt before step 4 still finds a
token, and a handler that died between a `RETURNING` delete and the revoke would
have had nothing left to retry with. Revoking immediately before the row goes keeps
the irreversible Apple call as late as possible while still inside the window where
a retry can repeat it — which is safe, because Apple treats an already-revoked
token the same as a fresh one.

`delete_user` stays the last irreversible step, as it was.

## Failure is silent by design, and loud in the logs

Every acceptance criterion points the same way: a deletion must go through whatever
Apple says. An expired code, an already-revoked token, an Apple 5xx, a client id
nobody configured, a network failure — none of them can stop an account being
deleted, and none can be retried once it is.

So `AppleIdentity` throws nothing. Every failure returns null and logs at `SEVERE`,
which the monitoring stack already alarms on: `aws_cloudwatch_log_metric_filter.severe`
matches `{ $.level = "SEVERE" }` and feeds the `severe_log_events` alarm. No new
infrastructure — but without the log line the feature could fail for every user and
look exactly like success, since the only symptom is an entry in a list on someone
else's phone.

The token, the code and the signed secret never reach a log line. Only Apple's own
`error` field is quoted back.

## Storage

Two nullable columns on `profiles`: `apple_refresh_token` and `apple_client_id`
(`2026-09-19.apple-deletion-grant.sql`). They are read by exactly one caller, and
live from confirmation until the schedule fires or the user cancels — `undoAccountDeletion`
nulls them, since nothing was revoked, the link survives, and there is no reason to
sit on a credential with no remaining purpose.

Not Secrets Manager. A per-user secret costs ~$0.40/month plus a lifecycle to
manage, for a value that lives 30 days; and the token's only powers are "mint an
id_token for this user at our client id" and "revoke", neither of which works
without our `.p8`-signed client secret. The repo has never used Secrets Manager.
The discipline that matters is that the columns are on no `RETURNING` list, absent
from `User.fromRow`, and never logged.

## Key material

`secrets/apple.json` in the account's static bucket, the same prefix as every other
credential. Terraform reads it and passes it to the api stack, which sets
`APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` and `APPLE_CLIENT_IDS` as
Lambda environment variables — the path `PG_PASSWORD` already takes.

The `.p8` is stored exactly as Apple issues it, PEM-wrapped PKCS#8, so rotating the
key is pasting a file rather than converting one. `AppleSignInKey` parses it
(`apple/key.dart`): PKCS#8 wraps an `ECPrivateKey` document in an OCTET STRING,
hence two ASN.1 parses to reach the scalar. Signing is pointycastle ECDSA with
RFC 6979 deterministic `k` — a Lambda has no entropy worth trusting at cold start,
and a repeated `k` leaks the key. Both packages were already resolved transitively
through `openid_client`; neither `jose` nor a JWK conversion step is involved.

`AppConfig.apple` is null unless all four variables are present. An environment
without them runs `UnconfiguredAppleIdentity`, whose every call is a logged no-op,
so the deletion path is identical minus the revocation and there is no null branch
in a handler.

## Gaps

- **Nothing has sent this endpoint an authorization code.** Until a caller does,
  every deletion takes the bodiless path and the revocation is dead weight.
  Ticketed separately in heart-of-yours.
- **Nothing here has spoken to Apple.** Every test uses an injected transport. The
  client secret is verified against the public point `openssl` reports for a
  throwaway key, which proves the parse and the signature, not that Apple accepts
  the result. First real exchange is the acceptance test.
- **The exchange adds a round trip to a user-facing `DELETE`.** Acceptable for a
  once-per-account action; noted in case the endpoint ever gets busier.
- **The client plumbing carries more than two ids can justify.** A list, a
  `=redirect_uri` suffix for a flow nothing uses, and a field on the wire — all of
  which collapse to one config value for as long as exactly one client per
  environment is live. Storing the client with the token earns its place (above);
  the allowlist and the wire field are the part to delete if they are still
  unexercised when this ships.
