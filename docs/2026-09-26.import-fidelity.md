# Import fidelity: set types, RPE, notes, rest timers, and re-import enrichment

How the Strong import keeps more than the numbers, and how importing the same history again
adds to what is already stored instead of being a no-op (heart-api#84). Also how those fields
reach the app and come back from it: the wire model, the workout note, and set types on
templates (heart-api#83). Written from the code as it stands. Hevy (heart-api#72) is built on
the same columns.

## What an import stores

| Strong export                          | Stored as                                                                                                |
|----------------------------------------|----------------------------------------------------------------------------------------------------------|
| `Set Order` `W` / `D` / `F` / a number | `exercise_sets.set_type` `w` / `d` / `f` / `NULL`, read back as `warmup` / `drop` / `failure` / `normal` |
| `RPE`                                  | `exercise_sets.rpe`, 1–10 in half steps                                                                  |
| `Notes`                                | `workout_exercises.note`: distinct notes of the exercise's rows, in order, one per line                  |
| `Workout Notes`                        | `workouts.note` (new, max 1000 chars)                                                                    |
| `Rest Timer` rows                      | `exercise_preferences.rest_timer`, per exercise (below). Never a set                                     |

- **A `NULL` set type is a normal set.** That covers every row from before this change,
  anything written by a client that doesn't know the field, an export without a `Set Order`
  column, and every set nobody marked. `normal` on input is stored as `NULL`, and `NULL` reads
  back as `normal`. A later, richer import can still mark a normal set as a warm-up, drop or
  failure set.
- **Storage is compact; the API speaks words.** `set_type` is one letter (`CHAR(1)`, two
  bytes) on the sets that have a type. A normal set stores nothing. Everything outside the
  database carries `normal`/`warmup`/`drop`/`failure` (`heart_models`' `SetType`), and only
  the database knows the letters: `_set_type_code` maps a word to its letter on write, and
  `_set_type_name` maps it back on read. An unknown word raises rather than being stored as a
  normal set. `rpe` is `REAL` (four bytes), and half steps are exact in binary.
- **The columns validate, never restrict.** RPE and set type are valid on any set of any
  category, cardio and warm-ups included. Where a picker appears is the app's decision.
- **Bad values don't cost the set.** An RPE off the scale (`8.3`, `11`, `hard`) is imported
  as `NULL`, and the set itself imports as usual. Notes longer than their column are cut at
  the bound, counted in code points, so an emoji is never split.
- **RPE is not health data.** It is the lifter's own rating, not a body reading, so the
  device-only health rule does not touch it.

## Rest timers are a preference, not history

Strong's timer is a per-exercise setting, and so is Heart's (`exercise_preferences.rest_timer`,
the value the app's timer reads). A `Rest Timer` row follows the set whose timer ran. Its
`Seconds` is the length, and every other measurement is 0. For each exercise:

- **Which session:** the most recent workout in the file that ran a timer for the exercise.
- **Which value:** the most frequent timer in that session. A timer nudged mid-rest leaves a
  one-off value (95, 105, 25) beside the configured one. A tie goes to the longer timer.
- **Warm-ups are ignored:** a timer after a `W` set is Strong's separate warm-up timer.
- **Bad values are ignored:** a timer that isn't a finite number, or is longer than an hour,
  sets nothing.
- **Case-variant names are one exercise:** the same latest-session rule applies across
  spellings.
- **Existing preferences win:** the timer is written only where the user has no rest timer
  for that exercise. A preference row holding only a unit gains one. An exercise the user
  declined to create gets none.

No per-set rest history is stored. If it is ever wanted, a new column starts `NULL`
everywhere, and re-importing (below) fills it.

## Re-importing enriches

A workout's import identity (`import_id`, derived from Strong's `Date` and `Workout Name`) is
the same in both of Strong's export layouts and whatever else the export includes. A
re-import of a workout that is already stored no longer skips it. It **fills gaps and nothing
else**:

- **Filled only where the stored value is `NULL`:** `workouts.note`, `workout_exercises.note`,
  `exercise_sets.set_type`, `exercise_sets.rpe`, and the rest timer preference above.
- **Never overwritten:** a value that is already there, whether the user wrote it or an
  earlier import did. A poorer export takes nothing away.
- **Never touched:** measurements, names, times, and which exercises and sets exist. A
  correction the user made (say, a 630 kg leg press fixed to its real weight) survives.
- **Which stored set is "the same set":** matched by position *and* numbers. That means the
  same workout, the same exercise at the same order, the same set order, and equal
  weight/reps/duration/distance. A set the user edited, or one shifted into a deleted
  neighbour's place with different numbers, matches nothing and is left alone.

This covers workouts imported before these columns existed: their `NULL`s are gaps, so
importing the same file again fills them in.

### What the report says

`POST /workouts/imports` responses gain three counts. The dry run (`dryRun=true`) reports the
same three from the same SQL, without writing anything:

| Field              | Meaning                                                                                                   |
|--------------------|-----------------------------------------------------------------------------------------------------------|
| `workoutsEnriched` | already-imported workouts that gained at least one value                                                  |
| `setsEnriched`     | stored sets that gained a type or an RPE                                                                  |
| `restTimersSet`    | exercises whose rest timer preference the import set. The preview counts every unmatched name as approved |

`workoutsSkipped` is now `workoutsFound − workoutsCreated − workoutsEnriched`: an enriched
workout is not a skipped one. A workout that was already there with nothing to fill is still
skipped.

## Writing sets: a missing key keeps the stored value

`POST /workouts` and `PUT /workouts/{id}` accept `set_type` and `rpe` on each set, in the
set's existing snake_case keys, validated at the edge:

- **Invalid values are a `400`:** `code: invalid_set_type` or `invalid_rpe`, naming the set.
- **An id named twice in one body is a `400`** (`code: duplicate_id`). Because the replace
  updates in place, a repeated id would otherwise have one entry win and the other's sets
  vanish silently.
- **Exercise notes are measured in characters (code points)**, as the column measures them.
  Before this, the input counted UTF-16 units, so an imported note with emoji could be one the
  app was then refused to save back.
- **A missing key keeps the stored value.** On `PUT`, a set whose id round-trips and whose
  payload leaves out `set_type` or `rpe` keeps what is stored. That is what today's app does:
  it doesn't know the fields yet, and without this rule any edit would erase what an import
  stored.
- **An explicit `null` clears.** A client that knows the fields sends them every time, with
  `null` to clear. This is why heart-api#83 serializes both with an explicit `null`, never
  leaving the key out.
- **A new set id with no keys** records nothing (`NULL`).
- **The rule is only for these new fields.** Today's `heart_models` omits null
  weight/reps/duration/distance, so for those a missing key still means null.

### The workout note

`POST`, `PUT` and `PATCH /workouts/{id}` accept `note`: trimmed, blank meaning none, at most
1000 characters (code points), otherwise a `400` with `code: workout_note_too_long`. It
follows the same rule as the set fields. On `PUT`, a missing `note` key keeps the stored note,
even on a shallow `PUT` without `exercises`, and `null` or a blank string clears it. `PATCH`
is partial anyway: no key leaves the note alone, and `null` or blank clears it. It is the only
`PATCH` field that can be cleared. Every workout read and every write response returns it.

### The replace no longer deletes what it keeps

Before this change, `PUT /workouts/{id}` deleted every exercise and set and re-inserted them
under their round-tripped ids. A deleted exercise's `ON DELETE CASCADE` fires at the end of
the statement, after the re-insert, so it also removed the re-inserted sets and the comments
on them. The response, built from `RETURNING`, still showed the sets, but the database had
none. That happened on every edit from the app since the id round-trip shipped (`7af24f2`,
2026-08-30). The replace now updates the exercises and sets the body still names in place,
inserts new ids, and deletes only what the body dropped. An id held by another workout is
still refused, as before.

## On the wire

`heart_models` 2.5.0 carries all of it:

- **`ExerciseSet.setType`:** a `SetType`, `normal` by default, never null.
- **`ExerciseSet.rpe`:** `double?`.
- **`Workout.note`:** `String?`.

`toMap` always writes all three, with an explicit `null`. That makes a client that knows them
a client that can clear them, which is what the keep-if-absent rule above assumes. RIR is a
display setting in the app (`10 − rpe`) and never reaches the server.

- **Warm-ups are left out of an exercise's best set and volume** (`WorkoutExercise.best`,
  `total`, and so `Workout.total`). Drop and failure sets count like any other set. Neither
  `failure` nor RPE 10 implies the other.
- **Copies:** a set copy keeps its type and starts unrated. Copying a workout for the same
  session keeps its RPEs and note. A repeat under a fresh id drops them, as it drops calories,
  because they describe the original session.

## Templates

A template set has a type too (`template_exercise_sets.set_type`, same letters, same
`_set_type_name`), so a template can lay out its warm-ups. There is no RPE on a template: a
program prescribes a target, often a range, not a rating, and that is a field of its own when
programs come (heart-api#86). Starting a workout from a template copies the set types and
never an RPE. Assigning a template to a student copies the set types into the student's copy.

Template exercises and sets now **round-trip their ids**, as workouts do, and a replace is
the same in-place update:

- rows the body names are updated;
- new ids are inserted;
- rows the body dropped are deleted.

`set_type` follows the same rules: absent keeps the stored type, and a value, `normal`
included, sets it. Two differences from workouts:

- **An id another template already holds is re-minted, not refused.** A template saved from a
  workout carries the workout's ids, so saving the same workout as a template twice would
  otherwise fail.
- **An id held in another table never collides.** Templates and workouts keep their ids in
  separate tables, so a template may share ids with the workout it came from.

An id named twice in one template body is a `400` (`duplicate_id`), as on workouts. So are two
exercises at the same `order` in a workout or template body (`duplicate_order`): sets find
their exercise by its order, so a repeated one would hang one exercise's sets under both.

## Gaps

- **The app's local mirror must keep the fields before it adopts 2.5.0.** `toMap` always
  sends them, and `toRow` doesn't store them, because a new key there breaks the app's local
  inserts. A build on 2.5.0 that re-saves a workout read back from its mirror would send
  `normal`/`null` and clear what an import stored. `heart_models`' CHANGELOG says so to the app
  side.
- **Identical sets can't be told apart.** The match is position plus numbers, so if a user
  deletes the first of three identical 45×18 sets, a re-import can give that set's RPE to the
  one that moved into its place. Nothing better is possible without a per-set identity in
  the export, and Strong has none.
- **`NULL` can't tell "never recorded" from "cleared".** A user who clears an imported RPE or
  note, or turns an imported warm-up back into a normal set, and then re-imports the same file
  gets the old value back. Telling the two apart would need a separate marker. That isn't worth
  it until someone actually does this.
- **A re-export in the other unit enriches notes, not sets.** 45 kg exports as 99.21 lb,
  which converts back to 45.0014 kg. That isn't the same set by its numbers, so it is left
  alone rather than guessed at. Re-export in the unit of the first import.
- **A deleted workout comes back.** Its import identity goes with the row, so re-importing the
  file recreates it.
- **Enrichment never adds structure.** A custom exercise declined on the first import and
  approved on a second one is not added to the workouts already imported.
- **Hevy** reuses all of this once its parser exists (heart-api#72).
