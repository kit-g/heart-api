# Task: goals — staged targets for frequency, strength and volume (heart-go backend)

You are in the heart-go API project (`/Users/kitg/mine/heart-go`), a Dart (relic) server.
The Flutter app is at `/Users/kitg/apps/heart`; both share `heart_models`.

First user-requested feature. A **goal** is a thing the user is measuring (workouts per week,
bench press top-set weight, monthly volume) plus a **ladder of stages** — targets with their own
deadlines: *"bench two plates by Christmas, three plates by next Christmas."*

## Design decisions (settled — do not re-litigate)

1. **The server stores goal definitions. It does not compute progress.**
   The app already computes every stat locally in SQLite (`heart_db/lib/src/parts/stats.dart`,
   `heart_db/lib/src/metrics.dart`) to save traffic, and that is the only thing that is correct
   offline. Goals follow suit: the API is a CRUD slice over definitions, with **no aggregation
   SQL** (`api/lib/db/queries.dart` has no `SUM`/`COUNT`/`MAX` today — keep it that way).

2. **The server does record achievement.** When the app first observes a stage's target being
   met, it `PUT`s `achievedAt` for that stage. This makes achievement stable across devices and
   reinstalls, and gives a later push-notification ("you hit three plates") something to hang on.
   The server trusts the client's timestamp — it is the user's own data.

3. **One `goals` table; stages are a JSONB array.** Not a `goal_stages` child table.
   Consequence to design around: a stage must carry a **stable `id` inside the JSON**, so
   `PUT /goals/:goalId/stages/:stageId` can address it after the ladder is reordered, and so
   achievement is not tied to array position. Updates are read-modify-write of the blob
   (`jsonb_set` at the matching index); last write wins across devices, which is acceptable for
   single-user data.

4. **The metric vocabulary already exists — reuse it, don't reinvent.**
   `ChartPreferenceType` (`heart_models/lib/src/models/charts.dart`) enumerates the 11 per-exercise
   quantities the app can already compute, each with a query in `heart_db/lib/src/metrics.dart`.
   `GoalMetric` is that set **plus `workouts`** (the frequency metric, served by the existing
   `StatsService.getWeeklyWorkoutCount`). Identical string values, so the app maps
   `goal.metric` → its existing metric query with no translation table.

5. **Targets are stored metric (kg / km), like everything else.**
   `set_item.dart:614-629` converts to kg on input; display converts back. A goal target is a
   number in the same canonical unit — there is **no unit column on a goal**.

6. **Two goal shapes, one table**, distinguished by `cadence`:
   - `cadence IS NOT NULL` (`'week'`/`'month'`) — a **cadence** goal. Recurring, progress resets
     each period, never "done". Exactly **one** stage.
   - `cadence IS NULL` — a **milestone ladder**. Each stage achieved once, optional per-stage
     deadline. This is the staged case. Rungs are a timeline, ordered by `dueOn`, **not** by
     target — targets may rise or fall (a deload ladder is a real plan), so no direction is
     enforced. `Goal.inDeadlineOrder` puts them in due-date order (undated rung last) for display.

7. **v1 ships all three kinds** — frequency, strength, volume. They are one code path; scoping
   down would not save work.

## Out of scope (deliberately)

- **Body-measurement goals.** No body metrics are collected. Revisit when they are — it lands as
  another `GoalMetric` + a source table, not a new feature.
- **Server-side progress.** Would duplicate `metrics.dart` in Postgres. Goal *definitions* are
  connection-visible via `GET /accounts/:targetUserId/goals` (same auth as workouts), so a coach can
  see *what* a student is working toward; computing *how far along* they are stays on the client
  (the coach's app already reads the student's workouts to render it). Revisit only if a
  server-computed progress number is actually needed.
- **Streaks.** Derived from local history; the app can compute them with no backend support.
- **Push on achievement.** `device_tokens` + `api/lib/notifications/` exist, so this is cheap
  later; decision 2 is what unblocks it.

## History backfill (already solved — no new endpoint needed)

Local-only progress needs local history, and a fresh install has none. That is already handled:
`GET /accounts/:targetUserId/workouts` accepts **your own id** — `_listWorkouts`
(`api/lib/db/queries.dart:236`) opens its auth CTE with `@requesterId::text = @targetUserId::text`,
so self-access is the first allowed case, cursor-paginated via `since`. The app rehydrates its
SQLite mirror from there; no goals-specific endpoint is required.

## 1. Migration

`database/migrations/2026-07-12.goals.sql` + its pgtap test. Use the `add-migration` skill for
file-naming, SQL style and the `plan(N)` rule.

```sql
CREATE TABLE IF NOT EXISTS goals
(
    id          UUID                 DEFAULT uuidv7() PRIMARY KEY,
    user_id     TEXT        NOT NULL REFERENCES profiles (id) ON DELETE CASCADE,
    metric      TEXT        NOT NULL,
    exercise_id UUID                 REFERENCES exercises (id) ON DELETE CASCADE,
    cadence     TEXT,
    stages      JSONB       NOT NULL,
    archived    BOOLEAN     NOT NULL DEFAULT false,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT goals_metric_check CHECK (metric IN (
        'workouts', 'topSetWeight', 'estimatedOneRepMax', 'totalVolume', 'totalReps',
        'maxConsecutiveReps', 'averageWorkingWeight', 'assistanceWeight',
        'cardioDistance', 'cardioDuration', 'averagePace', 'totalTimeUnderTension'
    )),
    CONSTRAINT goals_cadence_check CHECK (cadence IS NULL OR cadence IN ('week', 'month')),
    -- the frequency metric is whole-workout scoped; every other metric is per-exercise
    CONSTRAINT goals_scope_check CHECK ((metric = 'workouts') = (exercise_id IS NULL)),
    CONSTRAINT goals_stages_check CHECK (
        jsonb_typeof(stages) = 'array' AND jsonb_array_length(stages) > 0
    ),
    -- a recurring goal has a single standing target; ladders are for milestones
    CONSTRAINT goals_cadence_stages_check CHECK (
        cadence IS NULL OR jsonb_array_length(stages) = 1
    )
);

CREATE INDEX IF NOT EXISTS goals_user_id_idx ON goals (user_id) WHERE NOT archived;
```

- `exercise_id` cascades: deleting an exercise deletes goals about it (same call as
  `exercise_preferences`).
- Structural validation of stage *objects* stays in Dart (typed `GoalStage`), per the `Settings`
  precedent — Postgres guards the array, Dart guards the shape.
- Add `COMMENT`s on the table and on `metric` / `exercise_id` / `cadence` / `stages`, consistent
  with the rest of the schema.

### Stage shape (inside `stages`)

```json
[
  {"id": "0198...", "target": 100, "dueOn": "2026-12-25", "achievedAt": "2026-11-02T18:00:00Z", "achievedBy": "0198-workout-uuid"},
  {"id": "0198...", "target": 140, "dueOn": "2027-12-25", "achievedAt": null}
]
```

Array order **is** ladder order — no `order` field. `id` is a UUID minted by the server on write
(the app does not need to invent one). `dueOn`, `achievedAt`, and `achievedBy` are all nullable.

`achievedBy` is the id of the **workout** credited with meeting the rung — posterity, and a link the
client renders from the goal detail back to that session. It attributes to the workout, never a set,
on purpose: no single set achieves a total-volume or total-reps goal (the whole workout, or the
week, did), and a set id is a client-minted timestamp (`ExerciseSet` uses `UsesTimestampForId`), so
a server-owned goal pointing at one would be a dangling cross-device reference. A workout id is a
server-minted UUID, stable everywhere. Peak metrics (topSetWeight, estimatedOneRepMax,
maxConsecutiveReps) could additionally carry a set id later; not designed for now. The server stores
`achievedBy` **opaquely** — it does *not* check the workout exists or is owned. Workouts are written
local-first with server-minted ids, so the attributed session may not have synced when the rung is
stamped; validating would reject legitimate attributions, and — worse — block the *achievement* over
a broken *link*, when `achievedAt` is the durable fact and `achievedBy` is only enrichment. Nor does
anything clean up after a workout deleted later: `achievedBy` lives inside the JSONB blob with no FK,
the delete does not cascade, and cleanup wouldn't reach the user's other devices anyway. If the id
dangles — unsynced, or deleted — the link simply goes stale and the client renders it as unavailable;
the achievement never depends on it. (An earlier version validated ownership at write and 400'd
`goal_workout_unknown`; that broke exactly the local-first case above and was removed.)

## 2. heart_models

New `lib/src/models/goal.dart`:

- `enum GoalMetric` — the 12 values above, `fromString` throwing `ArgumentError` on unknown,
  matching the `ChartPreferenceType` string values exactly. Give it
  `bool get isWholeWorkout => this == GoalMetric.workouts;` and
  `bool get lowerIsBetter => this == GoalMetric.averagePace;` — pace is the one metric where
  progress means going *down*, and the app needs to know that to render a ring correctly.
- `enum GoalCadence { week, month }` with `fromString`.
- `abstract interface class GoalStage implements Model` — `String id`, `num target`,
  `DateTime? dueOn`, `DateTime? achievedAt`, `String? achievedBy` (attributed workout id — see
  "Stage shape" above for why it's the workout, not the set).
- `abstract interface class Goal implements Model` — `String id`, `GoalMetric metric`,
  `String? exerciseId`, `GoalCadence? cadence`, `List<GoalStage> stages`, `bool archived`,
  `DateTime createdAt`.
- Public interface + private impl + redirecting factory, `toMap()` with null-aware entries
  (`'dueOn': ?dueOn`), `fromJson` (camelCase, request/wire) and `fromRow` (snake_case, DB row,
  `stages` arriving as a decoded JSONB list). House style — see `exercise_preference.dart`.

New `lib/src/services/goals.dart`:

```dart
abstract interface class GoalService {
  // Reads follow the workouts visibility model: owner or an active connection.
  // `archived` picks a slice, never a union: false → live goals, true → the achieved surface.
  Future<Iterable<Goal>> getTargetUserGoals({
    required String requesterId,
    required String targetUserId,
    bool archived = false,
  });
  Future<Goal> createGoal(Goal goal, String userId);
  Future<Goal> updateGoal(String goalId, Goal goal, String userId);
  Future<void> deleteGoal(String goalId, String userId);
  // `achievedBy` (optional) credits the workout that met the rung; validated as owned by `userId`.
  Future<Goal> markStageAchieved(
    String goalId, String stageId, String userId, DateTime achievedAt, {String? achievedBy});
}
```

Export both from `lib/heart_models.dart`.

**Validation rules** (enforced in the input layer, §4 — mirrored by the DB CHECKs):
- `metric == workouts` ⇔ `exerciseId == null`. Reject both violations with 400.
- `cadence != null` ⇒ exactly one stage.
- `stages` non-empty; every `target > 0`.
- Stage targets are **not** direction-constrained — a later rung may be weaker (a deload ladder),
  so the input layer no longer checks that they climb. The client stopped enforcing this too.
- A user may hold at most **50 active (non-archived) goals**. The cap is enforced inside the
  `INSERT` (a `WHERE count(...) < 50` guard), not read-then-write, so concurrent creates can't
  both land a 51st; a full table returns no row, which the db layer turns into a 400.

**Machine-readable error codes.** Every error body now carries a stable `code` alongside the human
`reason`/`message`, so the client branches on identity, not prose:
`{"error":"bad request","code":"goal_limit","reason":"you can have at most 50 active goals…"}`.
`code` always defaults to the category (`bad_request`, `not_found`, …) and is overridden for cases
the app must act on. This matters most for `goal_limit`: it's the one rejection a *valid* create
can hit on server state the app can't see (a goal made on another device, not yet pulled), so the
app needs to tell it apart from a client-bug 400 or an outage. Goal codes: `goal_limit`,
`goal_scope`, `goal_cadence_stages`, `goal_not_found`, `goal_stage_not_found`. The code taxonomy
is general (not goals-only); other routes still emit the category default until they adopt specifics.

## 3. api — db layer

`api/lib/db/queries.dart` — new `const` SQL strings:

- `_listTargetGoals` — an `_auth` CTE (owner-or-active-connection, mirroring `_listWorkouts`) gates
  a `_goals` CTE `WHERE ... AND user_id = @targetUserId AND archived = @archived::boolean ORDER BY
  created_at`; a `UNION ALL` sentinel row (`... true AS forbidden`) fires when auth fails, which the
  db layer turns into `403`. The `@archived` bind selects the live (`false`) or achieved (`true`)
  slice — it never widens visibility, which lives entirely in `_auth`.
- `_createGoal` — `INSERT ... VALUES (@userId, @metric, @exerciseId::uuid, @cadence, @stages::jsonb) RETURNING *`
- `_updateGoal` — `UPDATE goals SET metric = ..., stages = @stages::jsonb, ... WHERE id = @id::uuid AND user_id = @userId RETURNING *`
- `_deleteGoal` — `DELETE FROM goals WHERE id = @id::uuid AND user_id = @userId`
- `_markStageAchieved` — the read-modify-write. Address the stage by its `id`, not its index:

```sql
UPDATE goals
SET stages = jsonb_set(
        stages,
        ARRAY[(
            SELECT (ordinality - 1)::text
            FROM jsonb_array_elements(stages) WITH ORDINALITY AS s(stage, ordinality)
            WHERE stage ->> 'id' = @stageId
        )],
        -- merge the stamp onto the whole element; strip_nulls keeps achievedBy out
        -- of the blob when the rung is unattributed
        (SELECT stage || jsonb_strip_nulls(
                 jsonb_build_object('achievedAt', @achievedAt::text, 'achievedBy', @achievedBy::text))
         FROM jsonb_array_elements(stages) AS stage WHERE stage ->> 'id' = @stageId)
    )
WHERE id = @goalId::uuid
  AND user_id = @userId
  AND EXISTS (
      SELECT 1 FROM jsonb_array_elements(stages) AS stage
      WHERE stage ->> 'id' = @stageId
  )
RETURNING *
```

The `EXISTS` guard matters: without it, an unknown `stageId` makes the `ARRAY[...]` subquery return
`NULL`, and `jsonb_set` then raises `path element at position 1 is null` — a 500. With the guard,
no match means zero rows updated ⇒ the route throws `NotFound`. (Verified against PG 18: the
unguarded query errors rather than corrupting the column, but it is still the wrong response.)

`achievedBy` is merged into the stage as sent — no ownership or existence check (see "Stage shape"
for why: local-first sync means the workout may not be on the server yet, and a broken link must not
block the achievement). `jsonb_strip_nulls` keeps it out of the blob when absent.

`api/lib/db/goals.dart` — `part of 'db.dart'`; `mixin _Goals on _DatabaseBase implements GoalService`.
Encode stages with `jsonEncode(goal.stages.map((s) => s.toMap()).toList())`, mint stage ids
server-side on create/update.

`api/lib/db/db.dart` — three edits: `part 'goals.dart';`, `_Goals` in the `with` clause,
`GoalService` in the `implements` clause.

## Data contract the Flutter app relies on

- `GET /accounts/:targetUserId/goals` → `{"goals": [...]}`, each goal:
  `{id, metric, exerciseId?, cadence?, stages: [{id, target, dueOn?, achievedAt?, achievedBy?}], archived, createdAt}`.
  Visible to the owner and to active connections (same auth as `/accounts/:id/workouts`); the app
  reads its **own** goals by passing its own id. A non-connection gets `403 forbidden`.
  - `?archived=true` selects the achieved surface — *only* the archived goals (the flip side of a
    completed card), never a union with the live ones. Default (`false`) returns the live slice
    that counts against the 50 cap. The flag toggles the slice only; the connection auth is
    identical either way, so a coach sees a student's achieved goals exactly when they see the
    live ones. Completing a goal archives it (via `PUT`), which frees a cap slot and moves it here.
- `POST /goals` `{metric, exerciseId?, cadence?, stages: [{target, dueOn?}]}` → the created `Goal`
  **with server-minted stage ids**.
- `PUT /goals/:goalId` — full replace of the definition + ladder. Stage ids are preserved when the
  client sends them back, minted when absent.
- `DELETE /goals/:goalId` → 204.
- `PUT /goals/:goalId/stages/:stageId` `{achievedAt, achievedBy?}` → the updated `Goal`. Idempotent:
  re-sending overwrites the timestamp rather than erroring. `achievedBy` is an optional workout id
  crediting the session that met the rung; it is stored as-sent (no ownership/existence check, so it
  survives a workout that hasn't synced yet) and degrades to a stale link if it never resolves.
- Targets are **metric** (kg, km). `metric` values match `ChartPreferenceType` exactly, so the app
  routes each goal to the `heart_db/metrics.dart` query it already has; `workouts` routes to
  `StatsService.getWeeklyWorkoutCount`.
