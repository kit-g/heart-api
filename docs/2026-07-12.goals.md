# Task: goals — staged targets for frequency, strength and volume (heart-go backend)

You are in the heart-go API project (`/Users/kitg/mine/heart-go`), a Dart (relic) server.
The Flutter app is at `/Users/kitg/apps/heart`; both share `heart_models`.

First user-requested feature. A **goal** is a thing the user is measuring (workouts per week,
bench press top-set weight, monthly volume) plus a **ladder of stages** — targets with their own
deadlines: *"bench two plates by Christmas, three plates by next Christmas."*

## Design decisions (settled — do not re-litigate)

1. **The server stores goal definitions. It does not compute progress.**
   The app already computes every stat locally in SQLite (`heart_db/lib/src/parts/stats.dart`,
   `heart_db/lib/src/metrics.dart`) to save traffic, and that is the only thing that is correct
   offline. Goals follow suit: the API is a CRUD slice over definitions, with **no aggregation
   SQL** (`api/lib/db/queries.dart` has no `SUM`/`COUNT`/`MAX` today — keep it that way).

2. **The server does record achievement.** When the app first observes a stage's target being
   met, it `PUT`s `achievedAt` for that stage. This makes achievement stable across devices and
   reinstalls, and gives a later push-notification ("you hit three plates") something to hang on.
   The server trusts the client's timestamp — it is the user's own data.

3. **One `goals` table; stages are a JSONB array.** Not a `goal_stages` child table.
   Consequence to design around: a stage must carry a **stable `id` inside the JSON**, so
   `PUT /goals/:goalId/stages/:stageId` can address it after the ladder is reordered, and so
   achievement is not tied to array position. Updates are read-modify-write of the blob
   (`jsonb_set` at the matching index); last write wins across devices, which is acceptable for
   single-user data.

4. **The metric vocabulary already exists — reuse it, don't reinvent.**
   `ChartPreferenceType` (`heart_models/lib/src/models/charts.dart`) enumerates the 11 per-exercise
   quantities the app can already compute, each with a query in `heart_db/lib/src/metrics.dart`.
   `GoalMetric` is that set **plus `workouts`** (the frequency metric, served by the existing
   `StatsService.getWeeklyWorkoutCount`). Identical string values, so the app maps
   `goal.metric` → its existing metric query with no translation table.

5. **Targets are stored metric (kg / km), like everything else.**
   `set_item.dart:614-629` converts to kg on input; display converts back. A goal target is a
   number in the same canonical unit — there is **no unit column on a goal**.

6. **Two goal shapes, one table**, distinguished by `cadence`:
   - `cadence IS NOT NULL` (`'week'`/`'month'`) — a **cadence** goal. Recurring, progress resets
     each period, never "done". Exactly **one** stage.
   - `cadence IS NULL` — a **milestone ladder**. Monotonic, each stage achieved once, optional
     per-stage deadline. This is the staged case.

7. **v1 ships all three kinds** — frequency, strength, volume. They are one code path; scoping
   down would not save work.

## Out of scope (deliberately)

- **Body-measurement goals.** No body metrics are collected. Revisit when they are — it lands as
  another `GoalMetric` + a source table, not a new feature.
- **Server-side progress.** Would duplicate `metrics.dart` in Postgres. The one thing it buys is
  coaches seeing a student's goal progress (`connections` + `/accounts/:targetUserId/workouts`
  exist) — revisit if coaches ask.
- **Streaks.** Derived from local history; the app can compute them with no backend support.
- **Push on achievement.** `device_tokens` + `api/lib/notifications/` exist, so this is cheap
  later; decision 2 is what unblocks it.

## History backfill (already solved — no new endpoint needed)

Local-only progress needs local history, and a fresh install has none. That is already handled:
`GET /accounts/:targetUserId/workouts` accepts **your own id** — `_listWorkouts`
(`api/lib/db/queries.dart:236`) opens its auth CTE with `@requesterId::text = @targetUserId::text`,
so self-access is the first allowed case, cursor-paginated via `since`. The app rehydrates its
SQLite mirror from there; no goals-specific endpoint is required.

## 1. Migration

`database/migrations/2026-07-12.goals.sql` + its pgtap test. Use the `add-migration` skill for
file-naming, SQL style and the `plan(N)` rule.

```sql
CREATE TABLE IF NOT EXISTS goals
(
    id          UUID                 DEFAULT uuidv7() PRIMARY KEY,
    user_id     TEXT        NOT NULL REFERENCES profiles (id) ON DELETE CASCADE,
    metric      TEXT        NOT NULL,
    exercise_id UUID                 REFERENCES exercises (id) ON DELETE CASCADE,
    cadence     TEXT,
    stages      JSONB       NOT NULL,
    archived    BOOLEAN     NOT NULL DEFAULT false,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT goals_metric_check CHECK (metric IN (
        'workouts', 'topSetWeight', 'estimatedOneRepMax', 'totalVolume', 'totalReps',
        'maxConsecutiveReps', 'averageWorkingWeight', 'assistanceWeight',
        'cardioDistance', 'cardioDuration', 'averagePace', 'totalTimeUnderTension'
    )),
    CONSTRAINT goals_cadence_check CHECK (cadence IS NULL OR cadence IN ('week', 'month')),
    -- the frequency metric is whole-workout scoped; every other metric is per-exercise
    CONSTRAINT goals_scope_check CHECK ((metric = 'workouts') = (exercise_id IS NULL)),
    CONSTRAINT goals_stages_check CHECK (
        jsonb_typeof(stages) = 'array' AND jsonb_array_length(stages) > 0
    ),
    -- a recurring goal has a single standing target; ladders are for milestones
    CONSTRAINT goals_cadence_stages_check CHECK (
        cadence IS NULL OR jsonb_array_length(stages) = 1
    )
);

CREATE INDEX IF NOT EXISTS goals_user_id_idx ON goals (user_id) WHERE NOT archived;
```

- `exercise_id` cascades: deleting an exercise deletes goals about it (same call as
  `exercise_preferences`).
- Structural validation of stage *objects* stays in Dart (typed `GoalStage`), per the `Settings`
  precedent — Postgres guards the array, Dart guards the shape.
- Add `COMMENT`s on the table and on `metric` / `exercise_id` / `cadence` / `stages`, consistent
  with the rest of the schema.

### Stage shape (inside `stages`)

```json
[
  {"id": "0198...", "target": 100, "dueOn": "2026-12-25", "achievedAt": null},
  {"id": "0198...", "target": 140, "dueOn": "2027-12-25", "achievedAt": null}
]
```

Array order **is** ladder order — no `order` field. `id` is a UUID minted by the server on write
(the app does not need to invent one). `dueOn` and `achievedAt` are both nullable.

## 2. heart_models

New `lib/src/models/goal.dart`:

  Future<Goal> updateGoal(String goalId, Goal goal, String userId);

**Validation rules** (enforced in the input layer, §4 — mirrored by the DB CHECKs):
- `metric == workouts` ⇔ `exerciseId == null`. Reject both violations with 400.
- `cadence != null` ⇒ exactly one stage.
- `stages` non-empty; every `target > 0`.
- For a milestone ladder, targets must be **strictly increasing** along the array (or strictly
  decreasing when `metric.lowerIsBetter`) — a ladder that goes backwards is a client bug, not a
  goal.

## 3. api — db layer

`api/lib/db/queries.dart` — new `const` SQL strings:

- `_listGoals` — `SELECT ... FROM goals WHERE user_id = @userId AND NOT archived ORDER BY created_at`
- `_createGoal` — `INSERT ... VALUES (@userId, @metric, @exerciseId::uuid, @cadence, @stages::jsonb) RETURNING *`
- `_updateGoal` — `UPDATE goals SET metric = ..., stages = @stages::jsonb, ... WHERE id = @id::uuid AND user_id = @userId RETURNING *`
- `_deleteGoal` — `DELETE FROM goals WHERE id = @id::uuid AND user_id = @userId`
- `_markStageAchieved` — the read-modify-write. Address the stage by its `id`, not its index:

```sql
UPDATE goals
SET stages = jsonb_set(
        stages,
        ARRAY[(
            SELECT (ordinality - 1)::text
            FROM jsonb_array_elements(stages) WITH ORDINALITY AS s(stage, ordinality)
            WHERE stage ->> 'id' = @stageId
        ), 'achievedAt'],
        to_jsonb(@achievedAt::text)
    )
WHERE id = @goalId::uuid
  AND user_id = @userId
  AND EXISTS (
      SELECT 1 FROM jsonb_array_elements(stages) AS stage
      WHERE stage ->> 'id' = @stageId
  )
RETURNING *
```

The `EXISTS` guard matters: without it, an unknown `stageId` makes the `ARRAY[...]` subquery return
`NULL`, and `jsonb_set` then raises `path element at position 1 is null` — a 500. With the guard,
no match means zero rows updated ⇒ the route throws `NotFound`. (Verified against PG 18: the
unguarded query errors rather than corrupting the column, but it is still the wrong response.)

`api/lib/db/goals.dart` — `part of 'db.dart'`; `mixin _Goals on _DatabaseBase implements GoalService`.
Encode stages with `jsonEncode(goal.stages.map((s) => s.toMap()).toList())`, mint stage ids
server-side on create/update.

`api/lib/db/db.dart` — three edits: `part 'goals.dart';`, `_Goals` in the `with` clause,
`GoalService` in the `implements` clause.

## Data contract the Flutter app relies on

- `GET /goals` → `{"goals": [...]}`, each goal:
  `{id, metric, exerciseId?, cadence?, stages: [{id, target, dueOn?, achievedAt?}], archived, createdAt}`.
- `POST /goals` `{metric, exerciseId?, cadence?, stages: [{target, dueOn?}]}` → the created `Goal`
  **with server-minted stage ids**.
- `PUT /goals/:goalId` — full replace of the definition + ladder. Stage ids are preserved when the
  client sends them back, minted when absent.
- `DELETE /goals/:goalId` → 204.
- `PUT /goals/:goalId/stages/:stageId` `{achievedAt}` → the updated `Goal`. Idempotent: re-sending
  overwrites the timestamp rather than erroring.
- Targets are **metric** (kg, km). `metric` values match `ChartPreferenceType` exactly, so the app
  routes each goal to the `heart_db/metrics.dart` query it already has; `workouts` routes to
  `StatsService.getWeeklyWorkoutCount`.
