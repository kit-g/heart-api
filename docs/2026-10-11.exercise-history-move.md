# Moving an exercise's history

How one user moves everything logged under one exercise onto another, in one action. Written from
the code as it stands; nothing here is a proposal unless it says so. Ticket: heart-api#140; landed
in PR #188 (`f4f9a3a`, `6a68034`, `940664b`). The app side is heart-of-yours#338. The wire model
is `ExerciseMoveReport` in `heart_models` 2.15.0.

## Why it exists

Import resolves exercise names by lookup, and a lookup can guess wrong: three translated Hevy
titles stand for two different exercises each (`docs/2026-10-08.hevy-import.md`), and the catalog
mapping that turned Hevy titles into aliases (heart-api#141) folds some Hevy pairs onto one Heart
exercise. The same happens without any import: a lifter creates a custom before finding the
catalog entry, or keeps two customs that are the same movement. Before this, a wrong guess was
permanent. Now the importer may guess, and the user fixes it in one action.

## The data model

Nothing new is stored. Everything of a user's that is keyed on an exercise moves:

| Table                  | Rows moved                                                           | Note                                                     |
|------------------------|----------------------------------------------------------------------|----------------------------------------------------------|
| `workout_exercises`    | of the user's workouts (`workouts.user_id`), deleted workouts included | FK `ON DELETE RESTRICT`                                  |
| `template_exercises`   | of the user's templates (`templates.user_id`), shared ones included  | FK `ON DELETE RESTRICT`; students' copies are their own  |
| `exercise_preferences` | the user's row on the source                                          | unique per (user, exercise): see *Target wins*            |
| `goals`                | the user's goals on the source                                        | no unique index, so all of them move                      |

Then, when the source is the user's own custom (`exercises.user_id = user`), the source row is
deleted. A library exercise (`user_id IS NULL`) is never deleted. The delete runs last, after every
row of the user's was re-keyed, so the two `RESTRICT` foreign keys fail the move on anything the
updates missed instead of a cascade erasing it.

The whole thing is one plpgsql function, `_move_exercise_history(user, source, target, dry_run)`
(`database/migrations/2026-10-10.move-exercise-history.sql`), returning one row of counts.

### Target wins

`exercise_preferences` is unique per (user, exercise). Where the user has a preference row on both
exercises, the target's row is kept and the source's dropped, whole: its rest timer, unit override
and pinned note go with it, even where the target's row leaves those NULL. The drop is counted
(`preferencesDropped`, 0 or 1) so a preview can say what the move loses. It is the one thing a move
loses, and the one thing that makes a move irreversible: moving back does not bring the row back.

Everything else moves whole. A workout or routine that held both exercises holds the target twice
afterwards, in the order it had; a goal on each stays two goals.

### The preview is the move

A dry run runs the same code path: the writes execute inside a block and are counted, then the
function raises out of the block, which rolls the writes back and keeps the counts. The preview
therefore cannot disagree with the move it predicts. It holds the same row locks for the duration
of one call.

### Visibility and locking

Both exercises must be the library's or the user's own. Someone else's custom raises
`no_data_found` exactly like a missing id, with the id in `DETAIL`, so the call confirms nothing
about other people's exercises. The source row is locked `FOR UPDATE` for the call: a workout
saved meanwhile that still names the source waits for the move, then meets the moved rows (or the
deleted custom) instead of slipping in between the re-key and the delete. An archived library
exercise is accepted as a target; visibility is ownership, nothing else.

## The API surface

`POST /exercises/:exerciseId/moves` — bearer token as for every route. The path exercise is the
source; the body names the target. `?dryRun=true` previews. Catalog → catalog, custom → catalog
and custom → custom are all allowed.

```jsonc
// POST /exercises/019def00-0000-7000-8000-000000000001/moves?dryRun=true
{ "targetId": "019def00-0000-7000-8000-000000000002" }
```

```jsonc
// 200, dry or real (from api/test/routes/exercises_test.dart)
{
  "sourceId": "019def00-0000-7000-8000-000000000001",
  "targetId": "019def00-0000-7000-8000-000000000002",
  "dryRun": true,
  "workoutExercises": 12,     // logged exercises re-keyed, across the user's workouts
  "templateExercises": 2,     // routine entries re-keyed, shared routines included
  "preferences": 1,           // preference rows re-keyed
  "preferencesDropped": 0,    // 0 or 1: the source's preference row, dropped because the target had one
  "chartPreferences": 0,      // of `preferences`, the ones carrying a chart setting
  "goals": 1,
  "sourceDeleted": true       // the user's own custom: deleted (or, dry, would be); a library exercise: false
}
```

Errors, in the shape every route uses:

| Status | `code`             | When                                                                                        |
|--------|--------------------|---------------------------------------------------------------------------------------------|
| 400    | `same_exercise`    | `targetId` equals the path id; refused at the input, before any database call               |
| 400    | `bad_request`      | `targetId` missing or not a UUIDv7; the path id not a UUIDv7                                 |
| 404    | `unknown_exercise` | either id is not the library's nor the user's own (missing and someone else's look the same) |

```jsonc
// 404
{ "error": "not found", "code": "unknown_exercise", "message": "Exercise #019d… not found" }
// 400
{ "error": "bad request", "code": "same_exercise", "reason": "source and target are the same exercise" }
```

Both ids are UUIDv7: the library's are (the loader takes the table default), and so are the
app-minted ids of customs. Additive: a new route and two new error codes.

## What a client sees afterwards

- **Workouts.** Re-keying a workout's exercises stamps the workout (`updated_at`, `changed_xid`;
  `2026-10-07.workout-change-xid.sql`), so every moved workout appears in the change feed as
  changed. A deleted workout's rows move too and stay deleted.
- **Templates, preferences, goals.** No change feed covers them; a client that caches them holds
  rows keyed on the source until it reads them again.
- **The source custom.** Gone from `GET /exercises?owned=true`. A save that still names it answers
  `404 unknown_exercise`. A client that mirrors the user's customs holds the deleted id until it
  refetches.
- **Duplicates by design.** A workout or routine that had both exercises now lists the target
  twice; nothing merges the two blocks.

## Gaps

- Target-wins drops the source's whole preference row. A per-field fill-in (keep the target's
  values, take the source's where the target has NULL) would be one more statement; not built,
  since the decision on the ticket was target wins.
- Archived library exercises are valid targets. Nothing server-side stops a move onto one.
- A move is not an event: nothing notifies other devices of the same account beyond the change
  feed's workout rows. A second device learns about the templates, preferences, goals and the
  deleted custom on its next full read.
- Two Hevy titles that both resolve to one Heart exercise (heart-api#141) merge on import, and
  this move cannot split a merged history: it moves everything under an exercise, never a subset.
