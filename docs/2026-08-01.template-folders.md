# Template folders

Decision record for the folder feature shipped in `2026-08-01.template-folders.sql`, plus the two
template fixes that came with it (`2026-08-01.template-ordering.sql`). Written after the fact — the
schema, endpoints and behaviour described here are what is in the repo.

A **folder** is a flat, per-user bucket for templates. A coach with a roster wants their masters
filed by student or by training block ("Alice", "Off-season", "Beginners"); an individual wants
theirs filed by split. Both are the same object, so there is one concept, not two.

## Design decisions (settled)

1. **A folder is a name and a position. Nothing else.**
   No `student_id`, no `domain`, no coaching semantics. A folder-bound-to-a-student was considered
   and rejected: it would make every folder write go down the sharing path and inherit its
   permission surface, to encode a convention a coach can already express by naming the folder
   after the student. Binding can be added later without a data migration; unpicking it could not.

2. **Flat, not nested.** A template has zero or one folder. No `parent_id`, so no cycle checks, no
   recursive CTEs, no rule for what happens to children when a parent is deleted. Listing stays the
   single keyset query it already was.

3. **Deleting a folder never deletes templates.** `templates_folder_fk` is
   `ON DELETE SET NULL (folder_id)`, so the templates inside come back unfiled. Filing is
   organisation, not ownership, and losing a training block because a folder was tidied away would
   be unforgivable.

4. **The FK is composite — `(folder_id, user_id) → template_folders (id, user_id)`.**
   A single-column FK would happily let a template be filed into someone else's folder. The
   composite version makes that structurally impossible, which is why `template_folders` carries an
   otherwise-redundant `UNIQUE (id, user_id)`. `SET NULL` names its column because `templates.user_id`
   is `NOT NULL` and an unqualified `SET NULL` would try to null it too (PG 15+).

5. **A template nests its whole folder, not a bare `folderId`.** Rendering a list of templates then
   needs no second request. It is the same call `assignedBy` already makes (a nested `Profile`, not
   an `assignedById`), and the join is a nested-loop index lookup on
   `template_folders_id_user_key` — the composite key from decision 4, doing double duty — which is
   nothing next to the `_template_exercises(t.id)` call already on every row.

   The nested copy has **no `templateCount`**: it would be duplicated on every template and correct
   on none. `templateCount` is nullable for exactly this reason, so "nobody counted" is
   distinguishable from "counted, and it's zero".

   This does **not** retire `GET /template-folders`. An empty folder appears in no template's
   payload, so a sidebar or a move-to-folder picker still needs the list; and templates are
   paginated, so the folders derivable from page 1 are a subset. Nesting optimises the common read;
   the endpoint remains the only complete view.

6. **Sharing a folder is shorthand for sharing every template in it.** A folder is never shared as
   an object — there is no folder-share ledger, and the recipient does not get a folder. This
   follows from decision 1: if a folder is just the owner's filing, it is not a thing to hand over.

7. **The student's copies arrive unfiled.** The coach's filing is the coach's business. The student
   files their own library, and now can — templates take a `folderId` on write.

8. **Folder names are unique per user, case-insensitively.** "Push" and "push" side by side in a
   list read as a bug. Enforced by a functional unique index, surfaced as a 400 rather than a 500
   (see "Error shapes" below).

## What was fixed along the way

**The assignment permission gate ignored connection status.** `_shareTemplate`'s `_allowed` CTE
checked only that a `connections` row existed with the right role — so a `pending` request, a
`declined` one, or a `severed` or `blocked` relationship all satisfied it. Anyone who had ever sent
you a connection request, or whom you had explicitly blocked, could push templates into your
library. `_shareTemplates` now requires `status = 'active'`, matching `_areConnected`, which has
always required it. Covered by a case per non-active status in `templates_db_test.dart`.

**`Template` dropped its coaching metadata.** `source_template_id`, `assigned_by` and `sync_enabled`
were selected by every template query and then discarded — the fields were commented out in
`Template.fromRow`. The client could not tell a coach-assigned template from its own. They are now
surfaced as `sourceTemplateId`, `assignedBy` (a `Profile`) and `syncEnabled`, plus a derived
`isAssigned`. A folder UI that cannot distinguish "mine" from "my coach's" is half-blind.

## Schema

```sql
template_folders (id uuidv7 PK, user_id → profiles ON DELETE CASCADE,
                  name TEXT NOT NULL, order_index INT NOT NULL DEFAULT 0,
                  created_at TIMESTAMPTZ,
                  CHECK (length(trim(name)) > 0),
                  UNIQUE (id, user_id))

UNIQUE INDEX template_folders_user_name_idx ON template_folders (user_id, lower(name))

templates.folder_id UUID
  FOREIGN KEY (folder_id, user_id) REFERENCES template_folders (id, user_id)
    ON DELETE SET NULL (folder_id)
INDEX templates_folder_id_idx ON templates (folder_id) WHERE folder_id IS NOT NULL
```

Re-runnable like the rest of the migrations: the column is dropped and re-added
(`ALTER TABLE templates DROP COLUMN IF EXISTS folder_id, ADD COLUMN IF NOT EXISTS folder_id UUID`),
and the FK likewise, so applying it twice lands in the same place.

## HTTP surface

| Route                                            | Purpose                                                 |
|--------------------------------------------------|---------------------------------------------------------|
| `GET /template-folders`                          | every folder the caller owns, each with `templateCount` |
| `POST /template-folders`                         | create — `{name, order?}`                               |
| `PUT /template-folders/:folderId`                | rename / reorder — `{name, order?}`                     |
| `DELETE /template-folders/:folderId`             | 204; the templates inside survive, unfiled              |
| `POST /accounts/:targetUserId/folders/:folderId` | assign every template in the folder                     |

`GET /templates` gains `?folder=`: a folder id lists that folder, the literal `folder=none` lists
the templates in no folder, and omitting it lists everything — which is what the app receives today,
so the existing call is unchanged.

`POST /templates` and `PUT /templates/:templateId` accept `folderId` — a scalar on the way in, a
nested object on the way out, the usual REST asymmetry. On an update the three cases are distinct
and deliberate:

| body                   | effect            |
|------------------------|-------------------|
| no `folderId` key      | filing left alone |
| `"folderId": null`     | unfiled           |
| `"folderId": "<uuid>"` | filed there       |

That is what the `movesFolder` parameter on `_replaceTemplate` is for.

## Data contract

```jsonc
// TemplateFolder, from GET /template-folders — templateCount only ever appears here
{"id": "0198…", "name": "Push", "order": 0, "templateCount": 3, "createdAt": "2026-08-01T…Z"}

// Template — the four new fields are all optional and omitted when absent
{"id": "0198…", "name": "Push day", "order": 0, "exercises": [...],
 "folder": {"id": "0198…", "name": "Push", "order": 0, "createdAt": "…"},  // absent when unfiled
 "sourceTemplateId": "0198…",    // absent unless assigned by a coach
 "assignedBy": {"id": "…", "username": "…", "avatar": null},
 "syncEnabled": true}

// TemplateShare — masterTemplateId is new
{"id": "0198…", "masterTemplateId": "0198…", "studentTemplateId": "0198…",
 "templateName": "Push day", "assignedTo": {…}, "assignedAt": "…"}

// POST /accounts/:id/folders/:id
{"shares": [ …one TemplateShare per template assigned… ]}
```

### heart_models is shared with the app — additive only

`heart_models` is pulled from git `ref: main`, so anything landing here
reaches the app on its next `pub get`. Templates are live, so the `Template` changes are strictly
additive: new optional fields, no removals, no renames.

**`Template.toRow()` was deliberately not touched.** The app spreads it straight into a SQLite
insert (`heart_db/lib/src/parts/templates.dart:89`), so every key it returns must be a column in the
app's local `templates` table. Adding one breaks writes at runtime, not at compile time. `toRow()`
stays `{id, name, order_in_parent}`; the new fields live on `toMap()` (the wire shape) only. Filing
a template locally needs an app-side `heart_db` migration first.

`TemplateShare` was changed freely — nothing in the app consumes shares yet.

## Assignment: one statement, two endpoints

`_shareTemplate` became `_shareTemplates`, taking `@masterTemplateIds::uuid[]` **or** `@folderId`
(the folder wins when both are set). Assigning one template passes an array of one; assigning a
folder passes the folder. There is no second copy of the copy-the-template-and-its-exercises logic.

The rewrite made three things per-master that were previously per-call:

- `_to_share` — a master already shared with this student is skipped individually, so re-assigning a
  folder after adding one template to it sends only the new one. Verified.
- `_master_exercises` carries `master_id`, and `_new_exercises` joins on
  `(master_id, exercise_order)` rather than `exercise_order` alone — without that, two templates in
  a folder would cross-wire each other's sets.
- The final `SELECT` returns one row per master, and `forbidden` is now simply
  `NOT EXISTS (_allowed)`. Previously an existing share suppressed the flag, so a coach whose
  connection had been severed could keep re-assigning. They now get a 403.

Assignment remains a **copy**, not a reference: the student gets their own templates, exercises and
sets, plus copies of any exercise their library was missing. Nothing the coach edits later mutates a
plan the student is mid-way through.

A folder assignment is a **snapshot, not a subscription** — templates added to the folder afterwards
do not follow on their own; the coach assigns the folder again, which is safe because assignment is
idempotent per template. Making it a subscription is what a `template_folder_shares` ledger would
buy, and it is what would finally give the long-unused `sync_enabled` column a job. Not done here.

## Error shapes

Every failure is a returned row or an empty result set, never a caught Postgres exception — the
house style is that the statement decides, and no query in `api/lib/db/` catches a driver error.

| situation                              | mechanism                                                 | response              |
|----------------------------------------|-----------------------------------------------------------|-----------------------|
| duplicate folder name on create        | `ON CONFLICT (user_id, lower(name)) DO NOTHING` → no rows | 400                   |
| duplicate folder name on rename        | `_conflict` CTE → `name_taken` flag on the row            | 400                   |
| folder is not yours (rename/delete)    | no rows                                                   | 404                   |
| filing into a folder that is not yours | the `INSERT`/`UPDATE` selects no row                      | 404                   |
| assigning a folder that is not yours   | no rows, then one diagnostic query                        | 404                   |
| assigning an empty folder              | no rows, then one diagnostic query                        | 200, `{"shares": []}` |
| no active connection                   | `forbidden` flag on every row                             | 403                   |

The diagnostic query (`_diagnoseEmptyFolderShare`) runs only when an assignment shared nothing,
because that is the one case the main statement cannot explain on its own — unknown folder, unknown
student, and empty folder all look like zero rows. The happy path stays at one round trip.

## Template ordering (`2026-08-01.template-ordering.sql`)

`templates.order_index` had been written since the initial schema and never read: `_listTemplates`
ordered by `id DESC` because that is what its keyset cursor walked, so a user's arrangement of their
own templates never survived a round trip.

The app has always sorted by `(order, id)` ascending — `heart_state` holds templates in a
`SplayTreeSet<Template>`, so `Template.compareTo` decides display order and the server's ordering is
discarded on arrival. That is why nobody noticed: with a handful of templates, one page holds all of
them and the local sort hides the disagreement.

It stops hiding it the moment a user has more than a page. The server was slicing pages by creation
while the app displayed by arrangement, so a template the user had dragged to the top could arrive
on page 2 — or, once the app starts paging, not arrive at all. Ordering the query the same way the
client orders the result is what makes the page boundaries mean something.

The listing now orders by `(order_index, id)` ascending and pages on the same pair:

```sql
AND (@cursorId::uuid IS NULL OR (t.order_index, t.id) > (@cursorOrder::int, @cursorId::uuid))
ORDER BY t.order_index, t.id
```

Row comparison, not `a > x OR (a = x AND b > y)` — Postgres pushes the whole `ROW(...) > ROW(...)`
into an `Index Cond` on `templates_user_order_idx`, so it is a range scan with no sort. Templates had
no index on `user_id` at all before this, so the old query was a seq scan *plus* a sort.

`order_index` is not unique, so the id rides along as a tie-break and the pair is a total order —
which is why the cursor had to grow. `OrderedCursor` (`heart_models/models/pagination.dart`)
serializes as `<order>:<id>`; it is still opaque to clients, who only echo back what the previous
page returned. Everything else in the API still pages on a bare id, which works there because uuidv7
is chronological; templates are the one list the user *arranges*.

No backfill: existing rows sit at the `0` default and the id tie-break resolves them into creation
order, which is the arrangement they have always effectively had.

## Typed inputs for the template endpoints

`routes/templates.dart` was one of the last handlers still doing `await request.json()` and passing
the raw map to `TemplateRequest`, which dug through it with `body['exercises'] as List? ?? []`. HTTP
shape-checking does not belong in the shared model package (`api/lib/inputs/README.md`), so:

- `api/lib/inputs/templates.dart` — `TemplateCreateIn`, `TemplateUpdateIn`, `TemplateListQuery`,
  which validate and build the request.
- `TemplateRequest` in `heart_models` is now a typed carrier — `name`, `order`, `folderId`,
  `movesFolder`, `List<TemplateExerciseRequest>` — with `toParams()` and no JSON in sight.
- `updateTemplate` gained the `…ById` split so tests can drive it without Relic's routing context.

**One deliberate behaviour change, with one carve-out.** An exercise that carries sets but no
resolvable name used to be silently dropped (`.where((e) => e['exercise_name'] != null)`) — you saved
five exercises and got four back, with no error. That is now a 400 naming the offending index.

The carve-out matters, and the first cut got it wrong. `WorkoutExercise.toMap()` writes `exercise`
null-aware off its *first set*, so an exercise the user emptied in the template editor — the editor
wires `onRemoveSet` straight through with no last-set guard — serializes as
`{id, start, sets: []}` with no `exercise` key at all. Rejecting that would turn "I deleted the last
set" into a failed save of the entire template. Entirely-empty entries are therefore dropped, as
before; only entries with content but no usable name are rejected.

Similarly, negative **weights** are accepted: assisted movements are logged against bodyweight and
the column has never constrained the sign, so the input layer must not start. Negative reps,
duration and distance are rejected, being meaningless.

Nothing else about the accepted shape changed: a bare name or the app's full exercise object, absent
`order` falling back to array position, and an empty template all still work. There is now a test
asserting the exact payload `template.toMap()` produces.

## Compatibility with the shipped app

Checked against the app's code rather than assumed:

- **The reordering is invisible to the app.** It holds templates in a `SplayTreeSet` and re-sorts on
  arrival, so the server's order was never what got displayed.
- **The cursor format change reaches nobody.** `RemoteTemplateService.getTemplates()` calls
  `GET /templates` with no query string at all — it never sends a cursor, so it cannot send a stale
  one. Had it paged, an old bare-uuid cursor would 400 against the new parser, which is the one
  genuinely breaking edge in this change and it is unreachable.
- **`Template.toMap()` is not a valid folder write.** The app posts `template.toMap()` verbatim as
  the request body, and that now emits a nested `folder` object while the writes read a scalar
  `folderId`. A round-trip therefore carries **no** `folderId` key, which lands on "leave the filing
  alone" — correct and safe, but it means the app cannot file a template by echoing a model back. It
  has to send `folderId` explicitly. Worth knowing before the folder UI is built.
- **`TemplateRequest` becoming typed touches nothing shipped** — it has no callers in the app.

## Known gaps

- **Reordering is a full-body `PUT` per template.** Dragging a template to a new position means
  replacing its whole body — exercises and sets included — just to change one integer. A
  `PATCH /templates/:id` accepting `{order}` alone, or a bulk reorder endpoint, would be the fix.
  The same applies to folders.
