# Locale API contract (for the Flutter client)

How the client gets localized backend content.  The backend design record behind it is
[2026-08-29.content-localization.md](2026-08-29.content-localization.md).

## The one rule

**Send `Accept-Language` on every API request, and nothing else.** Standard BCP-47 tags,
q-values allowed (`es-MX`, `en-CA, en;q=0.9`). There is no locale query parameter, no
per-user language setting on the server, and no endpoint that lists supported locales — the
client states what the user speaks, the server serves the best content it has. If the app ever
grows an in-app language override, express it the same way: put the chosen tag first in
`Accept-Language`.

The device's current locale is the right default value. Locale is resolved per request and
nothing is stored, so a device language change takes effect on the next request — just re-fetch.

## How the server resolves the header

Candidates are tried in q-value order; each candidate is tried three ways before moving to the
next: **exact tag → bare language → any supported regional variant of that language**. Matching
is case-insensitive. If nothing matches, content is English (`en`).

| `Accept-Language`      | served as | why                                            |
|------------------------|-----------|------------------------------------------------|
| `es`                   | `es`      | exact                                          |
| `es-MX` / `es-AR`      | `es`      | no `es_MX`; bare language matches              |
| `es-ES`                | `es_ES`   | exact (Castilian overlay over `es`)            |
| `fr-CA`                | `fr_CA`   | exact (Québécois overlay over `fr`)            |
| `fr-FR` / `fr-BE`      | `fr`      | no `fr_FR`; bare language matches              |
| `en-CA`                | `en_CA`   | exact                                          |
| `en-US`                | `en`      | bare language                                  |
| `de-DE, es;q=0.8`      | `es`      | no German; next candidate matches              |
| `de-DE` (alone)        | `en`      | nothing matches → default                      |

Supported today: `en` (default), `en_CA`, `ru`, `es`, `es_ES`, `fr`, `fr_CA`. **Do not hardcode this list** —
locales are added server-side with no client change; the resolution above means any device tag
degrades gracefully.

## What is localized

`GET /exercises` — the `name` and `instructions` fields of each exercise. **The wire shape does
not change per locale**; the same fields simply arrive in the resolved language. Everything else
(`category`, `target`, `muscles`, `movement`, `health`) is locale-independent.

Fallback is **per field and chained** (`es_ES → es → en`): an exercise may arrive with a
translated `name` and English `instructions` if that's all the translation has. Render what
arrives; never assume both fields share a language.

Consequences the client must respect:

- **`id` is the identity, `name` is display copy — and since the stable-keys cutover the wire
  enforces it.** Workout and template saves reference exercises by uuid: the server reads
  `exercise.id` from the nested object (a bare uuid string also works) and rejects a missing or
  malformed reference with a 400; there is no name-based lookup anymore. `POST /exercises`
  accepts the client-minted UUIDv7 `id`, so offline-created customs keep their identity through
  sync (a colliding id is a 400). Anything keyed, cached, or diffed by name breaks the moment
  the device language changes.
- **`key` is the env-stable content handle.** Each library exercise also carries `key` — its
  kebab-case content slug (`bench-press-barbell`), stable across renames and identical in every
  environment (uuids are not). `null` for user-created exercises. Use it for content references
  and fixtures; never send it as a save reference — saves go by `id`. Search may match against
  it so the canonical English wording keeps working under any display locale.
- **A locale change means a library re-fetch.** Cached library content is per-locale; treat the
  resolved language as part of the cache key or drop the cache on locale change.
- **User-created exercises are never translated** — they arrive exactly as the user wrote them,
  in every locale.

## The `validated` flag

Tri-state, and it describes **the copy actually served for the resolved locale**:

| value   | meaning                                       | client behavior            |
|---------|-----------------------------------------------|----------------------------|
| `true`  | a human reviewed this locale's copy           | plain rendering            |
| `false` | machine-authored, not yet reviewed            | show the machine-copy mark |
| `null`  | user-created exercise; flag takes no stance   | no mark                    |

The same exercise can be `true` in English and `false` in Spanish; the flag flips per locale as
reviewers work through translations. Don't cache it across locales.

## Push notifications (not live yet — forward-looking)

When pushes ship: device registration (`POST /devices`) resolves the same `Accept-Language`
header and stores the result **per device token**; push copy renders in that stored locale
(with the same regional chain, `es_ES → es → en`). Unlike content, this is a snapshot — the
client should re-register the device when the device language changes, or push copy stays in
the old language. Health-derived alerts remain contentless/silent pushes composed on device;
this section covers only server-composed copy (e.g. comment notifications).
