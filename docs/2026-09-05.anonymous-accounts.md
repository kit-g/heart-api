# Anonymous Firebase accounts 

Shipped. This is a record of what exists and why, not a task brief. The app side —
handling the 403, the purged-uid case — is heart-of-yours#91.

## What an anonymous account is

The app's anonymous mode (heart-of-yours#89, #91) signs a device into Firebase with
**anonymous auth** on first launch, before the person ever creates an account. That
produces a real Firebase user: a real `uid`, a real ID token that passes issuer and
signature validation exactly like any other. What marks it is a claim, not the
token's validity — `firebase.sign_in_provider` is `"anonymous"` instead of
`"google.com"` / `"apple.com"` / `"password"`, and there is no email and no provider
identity behind it.

Everything the app does in this mode stays on the device; no workout data reaches
this API until the person signs in for real. The account **may** later upgrade —
linking a Google or Apple identity keeps the same `uid` and the same `sub` now
arrives with a real `sign_in_provider`. Most anonymous accounts never upgrade.

## The 403 contract

An anonymous token at any authenticated endpoint is a client bug: the app is
supposed to keep its remote leg switched off while signed in anonymously. The
server treats a request that gets through anyway as exactly that — a bug to
surface, not a request to quietly honor — and rejects it in the `authentication`
middleware (`api/lib/middleware/authentication.dart`) with:

```
403 Forbidden
{"error": "forbidden", "code": "anonymous_account", "reason": "..."}
```

the existing `Forbidden` model (`api/lib/models/errors.dart`) with a new `code`.
Detection happens in `authenticate()` (`api/lib/globals/firebase.dart`), right
after the token's signature and issuer are validated: it reads the already-parsed
claims (`isAnonymousAccount`, a pure function of `OpenIdClaims`) and throws
`AnonymousAccountError` — a sibling of `AuthenticationError`, not a subclass, so
the middleware maps the two to different responses. A token whose `firebase`
claim is absent at all is **not** treated as anonymous — only an explicit
`anonymous` provider rejects — but it's unusual enough for a real Firebase token
that the authenticator logs it at warning level.

**Not 401.** The token is valid; a 401 is what the app's interceptor treats as
"refresh the token and retry," which would silently loop instead of surfacing
the bug. A 403 with a stable `code` is something the client can branch on
directly — check `code == 'anonymous_account'` and stop, don't retry.

Public routes are unaffected: `isPublicRoute` (`api/lib/routes/index.dart`,
consulted by `api/lib/core/app.dart` when wiring the `authentication`
middleware) still bypasses auth entirely, so a stray anonymous bearer on
`/version` is never read in the first place. Nothing on this API opens up for
anonymous tokens — the exercise library moving to the CDN (#65) means
anonymous mode doesn't need an authenticated call at all.

## Why profiles need no change

Rejecting in the middleware means no anonymous request reaches
`upsertProfile`, or any other handler — the first *authenticated* (non-anonymous)
call creates the profile exactly as it does today, and linking preserves the
`uid` so there is nothing to migrate. This is pinned with a route test
(`api/test/routes/account_test.dart`) that sends an anonymous token to
`PUT /accounts` and asserts the mocked profile service is never called, rather
than trusting the middleware/handler layering to hold.

`heart_models` is untouched: the provider is consumed and discarded inside the
authenticator and never becomes a field on `User`.
