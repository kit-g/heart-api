# DNS split between the accounts, and certificates in Terraform

heart-api#142. Written from the code as it stands; the move itself is a runbook in
`infrastructure/dns/README.md`, and nothing here is a proposal unless it says so.

## What was wrong

The whole `heart-of.me` zone sat in the dev account, as one root module with its own state. Every
certificate in both accounts was requested in the console, its validation CNAME copied into that
root by hand, and its ARN pasted into the environment that used it — seven ARNs across the two
`main.tf`s. A prod host needed a dev-account apply, standing up the API's domain took three passes
across two roots, and nothing in Terraform tied a certificate to the record that validated it.

## The shape

**Each account owns the DNS for its environment**, as part of that environment's stack
(`app/environments/<env>/dns.tf`), applied with everything else.

Prod holds the apex zone: `heart-of.me`, `www`, `api`, `media`, `mcp` as alias records, the
domain's mail (improvmx MX and SPF, DMARC, Firebase's SPF and DKIM), the site verifications that
share the apex TXT, and one NS record delegating `dev.heart-of.me`.

Dev holds that one zone, and every dev name is under it: `dev.heart-of.me` and `www.dev` for the
web distribution, `api.dev.heart-of.me` for the API, `media.dev.heart-of.me` for the media
distribution, `mcp.dev.heart-of.me` for the MCP host, and Firebase's mail records for `dev.heart-of.me`. The API and media hosts used to be
`dev.api` and `dev.media` — siblings of `dev`, which no `dev` delegation could carry — and were
renamed for this. That is a breaking change for dev builds, accepted: dev is not under the
compatibility floor, and the hosts are named only in the app's local, gitignored env files, the
site's dev config and OAuth metadata, and one test fixture.

**Alias records point at stack outputs.** `module.cdn.web_distribution`, `module.api.custom_domain`
and `module.api.mcp_distribution` each carry `domain_name` and `hosted_zone_id`, which is exactly
what an alias takes. The old root took the distribution and endpoint names as variables copied by
hand after each apply; that whole relay is gone, along with the `count`-gated aliases that made the
intermediate states valid.

**Certificates are `app/modules/certificate`**: an `aws_acm_certificate`, one `aws_route53_record`
per name on it keyed by the configured names (so the set of records is known at plan time), and
the `aws_acm_certificate_validation` whose `certificate_arn` is the module's output. A stack that
takes an ARN therefore waits for issuance. CloudFront's certificates are issued with the
environment's `aws.us_east_1` provider alias, the API's regional one with the default provider;
the api stack's region guard on the ARN still stands.

The five certificates whose names survive were **imported, not reissued**: the distributions and
the API domain name keep what they hold, and ACM asks for the same validation record for a given
name in a given account whichever certificate it is for, so the records the modules write are the
ones the old root had by hand. Dev's api and media certificates are new, with the new names.

Hostnames are locals at the top of each `dns.tf` (`local.api_host`, `local.media_host`, …) and
`main.tf` reads them from there, so a name is spelled once per environment. Adding a host is a
certificate module call, an entry in the aliases map, and the stack argument that uses it.

## What was considered and not done

- **Keeping dev's old names**, each as its own small delegated zone, which would have changed
  nothing a client sees. Three zones for three names, a fourth for every dev host after, and the
  odd `dev.api` shape kept for good. The rename costs one round of dev env files instead.
- **A cross-account role into the dev zone** for prod's validation records. It would have removed
  the console work but kept the apex in dev, and the registrar switch would still be owed later.
- **Keeping the apex in dev**, as the old README planned. Mail, verification and every prod host
  hang off the apex; prod is where they belong.

## The move

The dev subtree moved first and live: the old zone delegated `dev.heart-of.me` to the new one,
which let ACM validate the new names, and the rename happened there. The apex moved second: prod
built its zone, not yet authoritative, the two were compared name by name, and the registration
(Route 53 Domains in the dev account; Gandi is the registrar AWS uses for `.me`) was pointed at
prod's four servers. All of that ran on 2026-10-08, with the registry switching at about 20:10
UTC. What remains is the old root's destruction once the caches have turned over. Steps and
commands: `infrastructure/dns/README.md`.

## Gaps

- **Two SPF records at the apex.** `v=spf1 include:spf.improvmx.com ~all` and
  `v=spf1 include:_spf.firebasemail.com ~all` are separate strings; RFC 7208 says a receiver
  treating that as a permanent error is correct. Carried over unchanged, because the move needs the
  zones identical; merging them into one record is a change for after it.
- **No AAAA records.** The distributions have IPv6 on, but the aliases are A only, as before.
- **The old root still exists** until the last phase of the runbook, and its state object with it.
