# Content localization — locale overlays for the exercise library (heart-go backend)

Shipped. This is a record of what exists and why, not a task brief. The client-facing side of
this — what the Flutter app must send and may assume — is the separate
[locale API contract](2026-08-29.locale-api-contract.md); changes to resolution or fallback
semantics here must be reflected there.

The exercise library is localized through **per-locale overlay files** merged into the master
document at load time, and the first non-English locales (`ru`, `es`, and `fr` — all 271
exercises each, plus the `es_ES`/`fr_CA` regional overlays) ship with it.
Serving was already wired end to end — `Accept-Language` resolution in the API, the
`exercise_translations` table, per-field `COALESCE` fallback in the library query, the
`validated` flag for machine-authored copy — but the content itself was English-only: `ru` was
declared in `locales` and deployed in `SUPPORTED_LOCALES` with zero entries behind it.

```
content/exercise_library.yml       master: structure + fallback locale (en) copy
content/i18n/<locale>.yml          one overlay per non-fallback locale
content/exercise_i18n_schema.json  overlay schema
        │
        ▼  merge_overlays() in scripts/library_locales.py (load time, no build artifact)
merged document ──▶ validate_library.py ──▶ sync ──▶ exercises + exercise_translations
```

## The workflow

Adding or refreshing a locale:

1. `uv run python scripts/validate_library.py --coverage` — lists, per locale, every exercise
   that is missing, stale, or untracked.
2. Translate (human or machine) into `content/i18n/<locale>.yml`: `name`, `instructions`,
   `validated: false` for machine copy, and `source_digest` — the fingerprint of the `en`
   name+instructions the translation was made from (`source_digest()` in
   `scripts/library_locales.py`).
3. A new locale also needs: the master `locales:` list, and `SUPPORTED_LOCALES` in
   `infrastructure/app/stacks/api/lambdas.tf` (the API only *matches* locales it's told about).
4. Merge to `main` — the exercise-library workflow validates and syncs.

A human validating an entry flips `validated: true`; the client drops the machine-copy label.

## Design decisions (settled — do not re-litigate)

1. **Overlay files, not locales inline in the master.** The master is ~750KB of mostly `en`
   instruction markdown; every inline locale would double it, and translation diffs would
   interleave with structural ones. One file per locale keeps diffs single-language and keeps
   the master the sole owner of structure. The fallback locale itself stays in the master — it
   is required to be concrete for every exercise, so splitting it out would just add a failure
   mode.

2. **Merge at load time, no generated artifact.** `get_source()` folds overlays in before
   parsing; validation and sync both see the same merged document. There is no "compiled"
   library file to forget to rebuild or to commit stale. Merge problems (unknown exercise name,
   locale declared in neither `locales` nor the filename, entry defined in both master and
   overlay) are collected and reported all at once, matching the validator's style.

3. **Staleness is tracked by digest, not by process.** Each overlay entry records
   `source_digest` — 12 hex chars of sha256 over the `en` name+instructions it was translated
   from. When the English copy changes, the digest stops matching and the coverage report flags
   the entry stale. This is bookkeeping for the translation workflow only: it is stripped during
   merge and never reaches the database or the app. Coverage is informational, not a CI gate —
   adding an exercise must not break the build until every locale catches up; the fallback chain
   serves `en` in the meantime.

4. **Machine copy ships unvalidated.** All `ru` entries are machine-authored
   (`validated: false`); the client already labels unvalidated copy (the spark icon), so
   shipping the full library beats holding translations hostage to review throughput. Names were
   translated as one canonical pass (equipment vocabulary: штанга/гантели/блок/тренажёр/машина
   Смита/лента/гравитрон; nominal-plural exercise names per Russian gym convention), so families
   like every `(Barbell)` variant stay consistent; instructions keep the master's exact markdown
   section structure with fixed header translations.

5. **The sync prunes translations the source dropped.** Previously a translation removed from
   the YAML lived in `exercise_translations` forever, serving stale copy. The sync now deletes
   rows for (exercise, locale) pairs the source no longer defines — scoped to exercises present
   in this run, so archived exercises (absent from the source by definition) keep the
   translations they shipped with.

6. **Alias locales stay alias-only.** `en_CA` has no copy of its own: entries exist only where
   Canadian spelling would differ, everything else falls through per-field `COALESCE` to `en`.
   An overlay of all-`fallback_to` entries reports as an alias in coverage, not as 0%.

7. **Base languages, not flagship regions.** Spanish ships as bare `es` (neutral international
   Spanish: tú-imperative, no region-marked vocabulary), not `es_ES` — ~90% of Spanish speakers
   are in the Americas, and the CLDR/industry convention is base language + regional deltas.
   `es_ES` exists as exactly the `en`/`en_CA` shape: an alias overlay whose entries appear only
   where Castilian copy should differ. Same rule for any future language: author the base,
   overlay regions.

   Serving a regional locale needs one thing `en_CA` never did: a fallback *chain*. `en_CA`
   works as an alias by a lucky accident — its base (`en`) lives in the master row the query
   already coalesces to. `es_ES`'s base lives in `exercise_translations`, so the library query
   joins the requested locale **and** its base language and coalesces per field
   (`es_ES -> es -> en`). Without the second join, any resolvable `es_ES` request — including
   the moment a first genuinely-Castilian entry ships — would have served English.

8. **Locale resolution truncates regional tags.** `request.locale()` tries each
   `Accept-Language` candidate three ways — exact tag, bare language, any supported regional
   variant — because devices commonly send only a regional tag (`es-MX`) while content is
   authored under base languages. Before this, `es-MX` against `[…, es]` fell through to
   English. The same change fixed a latent bug: relic lowercases parsed tags (`en-CA` →
   `en-ca`), so the exact match against `en_CA` had never actually succeeded; tags are now
   canonicalized to the config spelling before comparison.

## Beyond the exercise library

Other localizable backend data rides other mechanisms, deliberately:

- **Push-notification copy** — `api/lib/notifications/templates.dart`, in-process map keyed
  `[locale][event][variant]`, already `en`/`en_CA`/`ru`.
- **Sample templates** (`content/sample_templates_en.json`, served via CDN as
  `/static/templates`) — reference exercises by slug `key` only; the client resolves each key
  through its local library, so exercise names arrive localized for free. Template titles carry
  their own inline `i18n` locale→string map next to the en `name` (five short proper names —
  the per-locale overlay machinery would be overweight here), resolved client-side with the
  same chain as everything else.
- Anything user-generated is never localized server-side.
