# Anomaly review

Suspicious entries in a training log, found by the server, decided by the
user (heart-api#42). Written from the code as it stands.

## Why

Heart keeps what was entered. Imports and the app write faithfully, and
nothing is corrected on the user's behalf. Real logs are dirty: a 630 kg leg
press (pounds entered in kg mode), `12 kg × 150` (weight and reps swapped), a
workout left running for 283 hours. One such entry creates a false record,
skews a chart, and dominates a weekly total. It is also read by assistants we
don't control, through `/me` and MCP. The answer is a review loop, not
smarter writes.

## Detection

`_sweep_anomalies()` runs every 15 minutes under pg_cron (`anomaly-sweep` in
`api/lib/db/cron.dart`). It picks every user with a workout updated since the
last sweep (`workouts.updated_at`, which the triggers keep for any set
change). The first run covers everyone. For each user, `_detect_anomalies`
judges the whole log, because a new session moves the baseline the old ones
are read against. A sweep that judges a user twice changes nothing, and
writes nothing either: a row is rewritten only when something in it changed.
Each user is judged in a subtransaction, so a log that fails to judge (a
workout deleted under the sweep) is logged as a warning and skipped, and
everyone else's still lands.

The rules are conservative, so a flag is worth a look:

| Reason                  | Entry   | Rule                                                                                         |
|-------------------------|---------|----------------------------------------------------------------------------------------------|
| `duration_left_running` | workout | finished, over 6 hours less its pauses, timed from the start the counts of time use          |
| `outlier_weight`        | set     | over 2.5× or under 0.4× the exercise's median working weight, once it has 8 such sets; not for weighted or assisted bodyweight |
| `implausible_reps`      | set     | over 100 reps on a loaded set                                                                 |
| `swap_suspected`        | set     | one of the two above, where the reps would be an in-line weight and the weight a whole rep count |

A whole history arriving at once is the normal case for an import. So each
exercise is judged against its own full distribution, not against "earlier"
history. The median leaves out the sets the user called invalid. Weighted
and assisted bodyweight work isn't judged by weight: there the weight is extra
load or help, and a change in it is the progress. Each anomaly keeps
`observed`, the values as entered (`weight` and `reps`, or `seconds`), and
`typical`, the median it was judged against.

An entry has one anomaly at most. As the median moves, an unchanged set may
fall under another rule (`implausible_reps` with no baseline yet, then
`swap_suspected`): its row takes the new reason and keeps the decision.

The imports no longer drop an end time more than 24 hours after the start.
They keep it as the file has it, and the sweep flags it.

## Deciding

`pending` until the user decides:

- **valid**: the entry stands and counts. It isn't flagged again while it reads as `observed`.
- **invalid**: the entry stays in the log and drops out of every count. For a
  workout's duration, only its time drops out; the workout still counts.

A decision can be changed: resolving again with the other status replaces it
(the same one again keeps `resolvedAt`). Editing the entry is the other way
out: the next sweep forgets an entry that no longer reads as `observed`, or
asks again if the new value is still odd. A question asked again is found
anew, so it comes back to the top of the list.

`invalid` is applied in the reads the counts fold from, one SQL fragment
(`_setCounts` in `queries.dart`) for every count of sets:
- `getRecordSets`: records, volume, balance, goal progress
- the exercise history query
- `getWorkoutSpans`: a workout with an invalid duration counts with no time

The log itself (`/workouts`, `/me/workouts`, exports) is unchanged.

## Routes and tools

| Route                         | Tool              | Does                                                     |
|-------------------------------|-------------------|----------------------------------------------------------|
| `GET /anomalies`              |                   | the app's list, newest found first, paged, `?status=`    |
| `PUT /anomalies/:anomalyId`   |                   | `{status: valid \| invalid}`                             |
| `GET /me/anomalies`           | `list_anomalies`  | the same list, read-only                                 |

Volume, balance, records, exercise history and goal progress also carry
`warnings`: the pending anomalies among what they counted. Volume and balance
list those in their window; records, those on the exercises shown; exercise
history, those on the sessions shown; a goal, those on what it measured in its
period. An assistant can then flag an entry without
rediscovering it, and the MCP instructions ask it to.

## Gaps

- **The app doesn't read anomalies yet.** Until it marks entries, offers the
  decision and applies `invalid` to its own stats, nothing is resolved and
  the app's numbers and the server's can differ. That's requested in
  heart-of-yours.
- **No duplicate-session or unit-mix rule yet.** `reason` is a word, not an
  enum, so a rule added later reads on older builds.
