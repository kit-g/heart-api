# Exercise movement — substitution groups and load attributes (heart-go backend)

Shipped. This is a record of what exists and why, not a task brief.

Every exercise in the library carries an optional `movement` record: the **movement pattern** it
trains, plus a handful of **objective load attributes**. Two exercises are mutually replaceable
when they share a pattern, which is what lets a client answer *"I'm protective of my back, what do
I do instead of barbell squats?"*

```
Squat (Barbell)          groups: [squat_bilateral]   axialLoad: high
  → drop axialLoad = high, 11 of the group's other 17 members remain, nearest first:
    Hack Squat                 moderate  machine
    Squat (Smith Machine)      moderate  machine
    Goblet Squat (Kettlebell)  moderate  free
    Leg Press                  low       machine
    ...
```

Front Squat and Zercher Squat fall out with the barbell back squat; the machine and front-loaded
variants stay. 264 exercises, 38 groups, 0 unannotated.

## Design decisions (settled — do not re-litigate)

1. **A shared group key, not pairwise links.**
   `substitutions: ["Hack Squat", "Leg Press"]` on each exercise is O(n²) authoring, drifts
   asymmetric (A lists B, B forgets A), and rots on every addition. Instead each exercise names
   the pattern(s) it trains and substitutes are derived as "everyone else in my group". Symmetry
   and transitivity are free; adding an exercise is one line.

2. **The group alone is not the answer — attributes are.**
   `squat_bilateral` contains Barbell Squat *and* Hack Squat *and* Leg Press; that is the point.
   What makes a lifter pick the hack squat is **spinal load**, not the pattern. So the group is
   paired with `axialLoad`, `stability`, `unilateral`, `impact` and `skill`, and substitution is
   "same group, filtered and ranked by attribute distance".

3. **The data is objective; the policy lives in the client.**
   There is no `backFriendly` flag and there must never be one. `axialLoad: high` is a fact about a
   barbell back squat; "good for my back" is a query over that fact. The moment a preference
   becomes a field, every new one (shoulder, knee, wrist, pregnancy) costs a re-annotation of all
   264 exercises.

4. **`groups` is a list, and untyped on the client.**
   Four exercises genuinely train two patterns (`Thruster (Barbell)`, `Thruster (Kettlebell)`,
   `Sumo Deadlift High Pull (Barbell)`, `Squat Row (Band)`); the rest have exactly one. First
   entry is the most representative. The 38-value vocabulary is enumerated in
   `content/exercise_library_schema.json` and validated at merge time, but `Movement.groups` is
   `Iterable<String>` in Dart — deliberately, so content can add a pattern without waiting on an
   app release. This mirrors how `muscles` already handles its enumerated vocabulary.

5. **`movement` is optional, and empty means "no substitutes".**
   `Leg Extension (Machine)`, `Hip Abductor (Machine)` and `Hip Adductor (Machine)` are legitimate
   singletons — the library has nothing to swap them for. User-created exercises have no annotation at all. Both surface as
   `Movement.empty()`, and `sharesPatternWith` returns false in either direction, so an
   unannotated exercise neither offers nor accepts substitutions.

6. **The blob is stored camelCase.**
   The snake_case convention governs **column names**, not the contents of a jsonb blob —
   `profiles.settings` and `goals.stages` already work this way. `scripts/library_locales.py`
   converts the snake_cased YAML to camelCase once, at sync time, so `exercises.movement` is
   already in its wire form and every read path ships the column verbatim.

   This replaced an earlier read-time conversion. A generic recursive `_camel(jsonb)` SQL function
   cost **~20 ms on a full-library read, ~85% of the query** (~24 ms vs ~4 ms), which is
   recomputing a constant: this is static content that changes only when the sync runs. A
   hand-enumerated `jsonb_build_object` was fast but silently **dropped** any key added to the
   schema later, which a client cannot distinguish from an absent attribute. Converting at write
   time avoids both.

## Shape

```yaml
# content/exercise_library.yml — snake_case, the content schema's own vocabulary
"Squat (Barbell)":
  category: Barbell
  target: Legs
  movement:
    groups: [squat_bilateral]
    axial_load: high        # none | low | moderate | high
    stability: free         # free | supported | machine
    unilateral: false
    impact: none            # none | low | high
    skill: moderate         # low | moderate | high
```

| field | meaning |
|---|---|
| `groups` | movement patterns, most representative first. Coarser than `category`, finer than `target` (`target: Legs` lumps calf raises with deadlifts, so it is useless for substitution). |
| `axial_load` | compressive load carried by the spine. `high` = loaded bar on the back or a loaded hinge; `none` = lying, seated unloaded, or hanging (traction, not compression). |
| `stability` | `free` = unsupported free weight or bodyweight; `supported` = torso braced, or cable-guided; `machine` = fixed path. |
| `unilateral` | one limb at a time, including alternating movements. |
| `impact` | joint loading from ground contact or ballistic deceleration. |
| `skill` | technical demand before the movement can be loaded safely. |

Current `axial_load` spread: 135 `none`, 56 `low`, 34 `moderate`, 39 `high`.

## Content workflow

The master YAML is 15k lines, so annotation happens on a small sidecar and is merged mechanically —
never regenerate the master from a model.

```bash
uv run python scripts/movement_seed.py            # rules → content/exercise_movement.yml
                                                  # (never overwrites hand edits; --force to reset)
# hand/LLM review the sidecar, per .prompts/movement_groups.md
uv run python scripts/movement_merge.py --check   # validate against the schema enums
uv run python scripts/movement_merge.py           # ruamel round-trip merge into the master
```

`movement_merge.py` fails on unknown exercise names, illegal enum values, and any group with a
single member (typo guard; the three real singletons are allowlisted). The merge is verified
lossless — a semantic diff of every non-`movement` field before and after is empty.

Rules get ~95% of grouping right from name + category + target; the residue is judgment. Two
things the rules got wrong that are worth remembering:

- **`category` is unreliable for anything but display.** Kettlebell and slam-ball work was filed
  under `Machine`; those five rows were recategorised to `Dumbbell` (there is no `Kettlebell`
  category in the enum). Trust the instructions over the category.
- **`Upright Row (Barbell)` is filed under `target: Back`** but is a shoulder movement, so the
  generic back `row` rule captured it. Rule order matters.

## Data contract the Flutter app relies on

`GET /exercises` returns `movement` on each exercise, already camelCased, or `null`:

```json
{
  "id": "...", "name": "Squat (Barbell)", "category": "Barbell", "target": "Legs",
  "movement": {
    "groups": ["squat_bilateral"],
    "axialLoad": "high",
    "stability": "free",
    "unilateral": false,
    "impact": "none",
    "skill": "moderate"
  }
}
```

- `Movement.fromJson` reads **camelCase only**. A snake_cased key reaching the client does not
  throw — it reads as the field's default, so `axialLoad` would silently become `none` and a
  lifter filtering out high spinal load would be handed exactly what they excluded. Tests on both
  sides pin the contract; a regressed sync script fails loudly.
- Unrecognised *values* do throw (`AxialLoad.fromString('crushing')`), so bad content is caught.
- `AxialLoad`, `Impact` and `SkillLevel` are declared in ascending order and expose
  `atMost(limit)`. The back filter is `m.axialLoad.atMost(AxialLoad.moderate)`. A test pins the
  declaration order so a future reorder cannot silently invert it.
- `Movement.sharesPatternWith(other)` is the substitution predicate.
- `createExercise` / `updateExercise` return `movement` too — update matters, because a patch that
  omitted it would make the client overwrite its cached copy with an empty `Movement`.

Server-side, the lookup is the jsonb `?|` existence operator against the groups array:

```sql
SELECT name FROM exercises
WHERE movement -> 'groups' ?| array['squat_bilateral']
  AND movement ->> 'axialLoad' IN ('none', 'low', 'moderate');
```

`exercises_movement_groups_idx` is `GIN ((movement -> 'groups'))` with **default `jsonb_ops`** —
`jsonb_path_ops` does not support the existence operators (`?` / `?|` / `?&`).

## Template sharing

The share-template CTE copies `movement` along with `asset`, `muscles` and the rest, so a coach's
exercise copied into a student's library keeps its substitution data. Note this branch only fires
for **coach-owned** exercises: a global resolves by name for the student and is never copied.

Workout and template payloads embed a deliberately minimal exercise stub (id, category, target,
name — not even `muscles` or `instructions`) and were left alone. The client resolves the full
exercise from the library.

## Deployment ordering

The migration rides the API pipeline (`deploy-api.yml` runs `apply_migrations.sh`), but the content
sync is a separate workflow. **The migration must land before the sync runs**, or
`library_locales.py` inserts into a column that does not exist.

The triggers do not enforce this. `exercise-library-prod` fires on push to `main`; `deploy-api-prod`
fires only on a `v*` tag. So a single push to main runs the prod sync against a prod DB with no
`movement` column. Per environment, the order is: **deploy the API (migration), then sync the
library.** Both workflows have `workflow_dispatch` with inputs hardcoded per environment.

Also: `[skip ci]` suppresses the tag trigger too, since GitHub checks the head commit message of
the push and a tag push resolves to the same commit.

## Out of scope (deliberately)

- **`createExercise` does not accept `movement`.** A user-made exercise has no library annotation,
  so `null` → `Movement.empty()` → no swaps offered is correct behavior, not a gap.
  `updateExercise` is consistent with it.
- **The real question is vocabulary ownership**, not the field. `groups` is unconstrained in
  Postgres and untyped in Dart, so accepting user input means accepting free-form strings into the
  substitution graph. It is largely self-limiting — a user's exercise is only visible in their own
  library, and a user tagging their custom variant with a *real* group is arguably the feature
  ("offer my machine hack squat when I skip barbell squats").
- **This likely belongs to a future `submitExercise`** — a coach promoting a personal exercise to
  the public library, with metadata and video. Annotation belongs in that review flow, where a
  human is already looking, rather than bolted onto ad-hoc creation.
- **No ranking endpoint.** The server returns the data; the client ranks and filters, consistent
  with the goals decision that the API is a CRUD slice with no aggregation SQL.

- **No `ExerciseFilter` support yet** — parked until the app knows what UI it wants. The analysis,
  so it does not have to be redone:

  `ExerciseFilter` is a **marker interface only**; `Exercise.fits` hardcodes `whereType<Category>()`
  and `whereType<Target>()`. A new enum implementing it is silently ignored, and fails *open*
  (matches everything). Implementing the interface is never the whole change.

  The dimensions split exactly along whether the enum has `atMost`:

  - `stability` is the only **categorical** one — unordered, so chip semantics (OR within, AND
    across) are correct. It is also a better equipment filter than `category`, which conflates
    equipment with tracking type and is unreliable.
  - `unilateral` is categorical too but is a `bool`; it would need an `enum Laterality` to fit.
  - `axialLoad`, `impact`, `skill` are **ordinal**. Every real use is a ceiling, not set
    membership: a chip for `moderate` means *exactly* moderate and excludes `low`, when the lifter
    means *at most* moderate. `skill` is the most defensible of the three (browsing for advanced
    movements is a real use); `axialLoad` is the least — nobody wants "only high spinal load".
  - `groups` cannot implement the interface at all: it is multi-valued and untyped, so it needs
    set-intersection semantics rather than `contains`. It is probably the most useful filter of
    the lot.

  Likely shape when it is picked up: keep `ExerciseFilter` for the categorical dimensions, add a
  small ceiling type over the existing `atMost` helpers, and a group filter with intersection
  semantics — categorical maps to a chip row, ordinal to a slider. The alternative (one interface,
  with the UI expanding an ordinal pick into the cumulative set below it) needs no model change but
  duplicates the ordinal logic into every client and inverts silently if the enum is ever
  reordered.
