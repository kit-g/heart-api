# PostgREST + RPC for reads (and dumb writes)

Status: **exploration / parked.** API today is in great shape; this is for a later phase.

## Why consider it

The API Lambda is invoked for every read, including trivial "user gets their own rows" queries. Those reads dominate volume on read-heavy screens (gallery, workouts list, charts). Each invocation costs cold-start latency the user feels and Lambda dollars we pay.

PostgREST exposes Postgres as an HTTP API. Mobile can read directly from Postgres with a Firebase JWT, gated by RLS, and skip Lambda entirely on the hot path.

## Hard rule: portable Postgres surface only

This is the lock-in firewall. **Use only:**

- Postgres itself (tables, RLS, functions, extensions we already use).
- PostgREST — open source, self-hostable against any Postgres. Drop Supabase tomorrow by running `postgrest` against an RDS Aurora URL; the app doesn't notice.
- Firebase JWT validation via the JWKS knob (`https://securetoken.google.com/<project>/.well-known/jwks.json`). Plain JWT verification — portable.

**Do not use** (anything that ties us to Supabase the platform):

- Supabase Auth (GoTrue) — we're on Firebase already; don't switch.
- Supabase Storage — we use S3.
- Supabase Edge Functions — we have Lambda.
- Supabase Realtime — operationally heavy to leave; revisit only if a feature genuinely needs it.
- `@supabase/supabase-js` client. Mobile talks plain HTTP/PostgREST.

If a feature requires anything in the "do not use" list, it stays in the API Lambda.

## Architecture sketch

```
                  ┌──────────────┐
   Mobile  ─────► │ API Gateway  │ ──► Lambda (Dart)     ◄── writes with side effects,
                  └──────────────┘                            scheduler, FCM enqueue,
                                                              account deletion, etc.
                  ┌──────────────┐
   Mobile  ─────► │  PostgREST   │ ──► Postgres (RPC fns) ◄── reads, dumb upserts,
                  └──────────────┘                            anything pure-data
```

Functions become the read-side contract. They shape responses with `jsonb_build_object` so the wire format stays camelCase. They embed derived fields (e.g. CDN URLs composed from a config table). They handle cursor pagination with the existing `limit + 1` trick.

## Function shape

```sql
CREATE FUNCTION get_workouts(_cursor uuid DEFAULT NULL, _limit int DEFAULT 20)
RETURNS jsonb LANGUAGE sql STABLE AS $$
  WITH page AS (
    SELECT w.id, w.name, w.started_at, w.completed_at,
           _config('cdn_url') || '/' || wi.key AS first_image
    FROM workouts w
    LEFT JOIN LATERAL (
      SELECT key FROM workout_images WHERE workout_id = w.id ORDER BY id DESC LIMIT 1
    ) wi ON true
    WHERE w.user_id = auth.jwt()->>'sub'
      AND (_cursor IS NULL OR w.id < _cursor)
    ORDER BY w.id DESC
    LIMIT _limit + 1
  ), numbered AS (
    SELECT *, ROW_NUMBER() OVER (ORDER BY id DESC) AS rn FROM page
  )
  SELECT jsonb_build_object(
    'workouts', jsonb_agg(jsonb_build_object(
      'id',          id,
      'name',        name,
      'startedAt',   started_at,
      'completedAt', completed_at,
      'firstImage',  first_image
    ) ORDER BY id DESC) FILTER (WHERE rn <= _limit),
    'cursor', CASE WHEN COUNT(*) > _limit THEN MIN(id) FILTER (WHERE rn = _limit) ELSE NULL END
  )
  FROM numbered;
$$;
```

Mobile calls:

```
POST /rpc/get_workouts
Authorization: Bearer <firebase JWT>
Content-Type: application/json

{ "_cursor": "0192…", "_limit": 20 }
```

PostgREST verifies the JWT against the Firebase JWKS, exposes the claims as `auth.jwt()` inside the function, and returns the jsonb result as the response body. No Lambda hop.

## Config table

Runtime constants (CDN base, default locale, anything the API currently reads from env vars) move into a small config table populated per-env via the same migration runner:

```sql
CREATE TABLE _app_config (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
INSERT INTO _app_config VALUES
  ('cdn_url',        'https://dev.media.heart-of.me'),
  ('default_locale', 'en')
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;

CREATE FUNCTION _config(_key text) RETURNS text LANGUAGE sql STABLE AS $$
  SELECT value FROM _app_config WHERE key = _key;
$$;
```

Functions reference `_config('cdn_url')` instead of taking it as a parameter.

## Good migration candidates

Functions, in rough order of "easiest to migrate":

- `GET /charts` — pure ownership filter, no derived fields.
- `GET /connections` — same.
- `GET /devices` — same (not exposed today but trivial).
- `GET /comments?targetType=…&targetId=…` — needs the connection-aware visibility check; doable in a function with an EXISTS subquery against `connections`.
- `GET /exercises` — locale-aware join with `exercise_translations`; asset URLs from config. Tractable.
- `GET /workouts` — first-image URL composition, exercise count. Manageable once `_config()` is in place.

## Stay on Lambda

- Anything that fires a side effect (events queue, scheduler, FCM, S3 mutation).
- Endpoints producing signed URLs / time-bound tokens (need credentials inside the response — can't live in a function).
- Cross-user reads that need complex business logic (e.g., "coaches can read students' workouts only during the active engagement window") — possible in RLS but the cost-benefit gets worse.

## Tradeoffs

**Wins:**
- Lambda cold-start gone from read paths; UX feels snappier on app launch.
- Drastically less Dart code to maintain — the API becomes "workflows only."
- Postgres becomes the authoritative server. Schema + functions are the contract.

**Costs:**
- SQL functions become the API surface. Schema migrations carry wire-shape changes.
- Debugging is `psql` instead of `dart analyze`. Slower feedback loop for read endpoints.
- Error mapping: PostgREST surfaces Postgres exceptions verbatim. Need a small convention (custom ERRCODEs → mobile-friendly status codes).
- Two API layers — the Dart side is for writes-with-side-effects and event handlers; PostgREST is for reads + dumb upserts. The boundary needs to be obvious in the codebase (`database/functions/*.sql` for the read surface, `api/lib/routes/` for the Lambda one).
- RLS adds a layer of access control that's harder to test than Dart unit tests. pgtap can cover it but the muscle memory is different.

## What we'd need before committing

1. Decide whether mobile is willing to speak two APIs (Lambda for writes, PostgREST for reads). It's not a big deal — same JWT, two base URLs — but it's a contract change.
2. JWKS configuration in Supabase pointed at the Firebase issuer. One-time knob in the Supabase dashboard.
3. The `_app_config` table + seed migration.
4. A pgtap discipline for RLS policies and RPC functions. (`runtests()` already supported.)
5. An error-code convention: e.g., reserve `P0001 = forbidden`, `P0002 = not_found`, mobile maps these to HTTP-ish status codes client-side.

## When to revisit

Once one of these triggers:

- A specific read screen is visibly cold-start-laggy on mobile and the user reports it.
- Lambda invocation costs become non-trivial in monthly billing.
- We hit a feature where Postgres-side logic is just clearly the right place (e.g., notification preferences with complex visibility rules).

Until then, the Dart API is genuinely good and there's no urgency. This document exists so future-us doesn't re-derive the analysis from scratch.
