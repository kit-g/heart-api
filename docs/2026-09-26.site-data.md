# App-published data on heart-of.me

A record of what exists, written from the code as it stands; the app-side consumer is
heart-of-yours#153. Nothing here is a proposal unless it says so.

Some pages on heart-of.me describe the app rather than the service: what it does, what each
release brought. That copy is owned by heart-of-yours, next to the code it describes, and
reviewed with it. So the site does not carry it. The app uploads the data as JSON on release,
and a static page here fetches it in the browser and renders it. No build step, no cross-repo
trigger, no token: the two sides share only an S3 prefix and a file shape.

## The prefix

```
s3://<account>-ca-central-1-static/site/data/   served at   https://heart-of.me/data/
```

| Environment | Bucket                            | Served at                     |
|-------------|-----------------------------------|-------------------------------|
| dev         | `583168578067-ca-central-1-static` | `https://dev.heart-of.me/data/` |
| prod        | `922419543441-ca-central-1-static` | `https://heart-of.me/data/`     |

- **heart-of-yours writes it, heart-api never does.** `scripts/site.sh` syncs `site/` with
  `--delete` and excludes `data/*`, so a site deploy neither uploads nor removes anything there.
  `/site/data/` is gitignored so a local preview copy cannot be committed.
- **Credentials already exist.** The app's release workflows assume
  `heart-github-actions-deploy-role` in each account (its trust lists both repos, see
  `infrastructure/global/stack/main.tf`), and that role may `s3:PutObject` / `s3:DeleteObject` on
  `<static bucket>/site/*`. No IAM change was needed.
- **No invalidation.** The web distribution's default behavior uses the managed
  CachingOptimized policy, which honours the origin's `Cache-Control`. Uploads carry
  `max-age=3600`, so a new file is served everywhere within the hour. An app release lands when
  it lands. (The deploy role could invalidate, but the app does not.)

An upload that meets all of the above:

```bash
aws s3 cp docs/features.json s3://<static bucket>/site/data/features.json \
  --content-type application/json --cache-control 'max-age=3600'
```

The content type matters: the page reads the body as JSON regardless, but browsers and crawlers
see what S3 says.

### A missing file is a 200

The web distribution maps S3's 403/404 to `/index.html` with a **200** (see `custom_error_response`
in `infrastructure/app/stacks/cdn/main.tf`, there for app deep links). So before the first upload,
`/data/features.json` answers with the home page's HTML. A page reading from `data/` must treat
"not valid JSON of the expected shape" as "nothing yet", never as an error.

## The feature list: `data/features.json`

Source: [`docs/features.json`](https://github.com/kit-g/heart-of-yours/blob/main/docs/features.json)
in heart-of-yours. Its contract is the app's: the release-notes skill's "Feature list" section,
enforced by `test/features_content_test.dart` there. One entry, from the file as the app wrote it:

```jsonc
{
  "categories": [
    { "id": "train", "title": "Log a session" }           // array order is page order
  ],
  "features": [
    {
      "id": "rest-timers",                                // stable forever: the page anchor
      "category": "train",
      "title": "Rest timers",                             // plain text
      "pitch": "Set a rest timer per exercise and it runs between sets, with a notification when it is time for the next one. Settings lists every timer you have set, in one place.",
      "since": "1.0.5",                                   // null = merged, unreleased
      "tier": "free",                                     // free | premium | coach
      "platforms": ["ios", "android"],
      "highlight": false
    }
  ]
}
```

### How the page reads it

`site/features.html` is a static shell (header, heading, store buttons, footer);
`site/assets/features.js` fills it:

- Entries with `"since": null` are left out, and a category left empty is dropped.
- Entries with `"highlight": true` are shown first under "The short version", then again in
  their category.
- Categories render in array order, features in file order within each.
- `title` and `pitch` are set with `textContent`. Markup in them would show literally, never
  render. That is the app-side "plain text" rule, made safe rather than trusted.
- A card says **Premium** / **Coach** for a paid tier, and **iOS only** / **Android only** when
  `platforms` has one entry and the platform selector is on All. Free, both-platform features
  carry no badge.
- A segmented control (All · iOS · Android, buttons with `aria-pressed`) filters by `platforms`:
  a feature shows when its `platforms` includes the selection, or always under All. The
  highlights follow the filter and a category left empty is dropped. After a change, a
  visually hidden status line announces the count ("23 features"), each feature counted once.
- The selection defaults to the visitor's device (user agent: iPhone or iPad, including iPadOS
  presenting as a touch Mac, is iOS; Android is Android; anything else is All). Pressing a
  button writes `?platform=all|ios|android` with `replaceState`, so a link can preselect it and
  the param beats the guess. An unrecognized value is ignored.
- Each feature's card has `id="<feature id>"` and each category section `id="<category id>"`,
  so `https://heart-of.me/features.html#strong-import` links to one feature. The page scrolls to
  the hash after rendering, since the target does not exist at load. When the hash names a
  feature the selected platform hides (`?platform=android#apple-watch`), the page falls back
  to All rather than land nowhere.
- Anything but an object with `categories` and `features` arrays (a 404-turned-HTML, a network
  error) shows a one-line "on its way" note linking home.

Fields the page does not use today: none. `since` is only a filter; the page does not show
versions.

The page is linked from the header nav (desktop and mobile) of `index.html` and `support.html`.
The legal pages keep their short nav.

## The changelog: reserved

Not built. The same prefix is meant to carry the app's release history, likely from
`assets/whats_new/<locale>.json`, for a page beside `features.html`. `data/*` is already excluded
from the site sync, so adding it needs no change to `site.sh`. Two differences from the feature
list to settle when it lands:

- `body` fields there carry markdown (`**pin**`), where feature copy is plain text. The page will
  need a small, safe subset renderer rather than `textContent`.
- There is one file per locale (`en`, `es`, `fr`, `ru`); the site is English-only today.

## Gaps

- **Unreleased copy can go public.** The page hides `"since": null` entries, but an edited pitch
  for a shipped feature is live as soon as the file is uploaded. Uploading from a release tag
  (when the release-notes skill has just stamped the file) keeps the page equal to what users
  have. Uploading from a branch does not.
- **Release timing.** A tag uploads before Apple and Google approve the build, so the page can
  describe a version that is not yet in the stores for a day or two.
- **No server-side HTML.** Crawlers that do not run JavaScript see the shell and the store links,
  not the list. Fine for link previews (they use the `og:` tags), weaker for search indexing.
  Prerendering at deploy time was built and dropped in favour of this simpler contract. It is the
  fix if indexing matters.
- **Cache vs. correction.** A mistaken upload is corrected by uploading again, visible within
  `max-age`. A faster fix is a manual invalidation of `/data/*` on the web distribution.
