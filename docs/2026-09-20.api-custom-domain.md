# The API's public domain

A record of what exists, written from the code as it stands. Nothing here is a proposal unless it
says so.

The API answers on its own hostname — `api.heart-of.me` in prod, `dev.api.heart-of.me` in dev —
through a **regional** API Gateway custom domain. The `execute-api` hostnames still serve the same
API and are not going away; the custom domain is an addition, which is what let builds pinned to
the old name keep working across the cutover.

## The shape

```
https://api.heart-of.me/v1/templates
                        │  └── path the route table sees as /templates
                        └───── base path mapping, onto stage `v1`
```

Three separate things spell `v1`, and the arrangement is deliberate:

| Thing | Where |
|---|---|
| The segment clients send | `Router` in the app's `heart_api` package prefixes every path |
| The base path | `local.api_base_path` in `app/stacks/api/main.tf` |
| The stage | `aws_api_gateway_stage.v1` |

The base path mapping is what joins the first to the third. Before it existed the client's `v1/`
*was* the stage name — one string doing two jobs, so the stage could not be renamed without a
client release. Now the mapping absorbs that: point the same base path at a different stage and
every shipped build follows.

Route table paths stay unprefixed (`/templates`, not `/v1/templates`). `/v1` is gone before Relic
sees it: the proxy event drops the stage, and the Lambda Web Adapter is set to remove the base path
on top of that (`AWS_LWA_REMOVE_BASE_PATH` in `app/stacks/api/lambdas.tf`), so the same route table
answers on either hostname.

## Regional, not edge-optimized

The REST API was `EDGE` in both accounts until this change. An edge-optimized endpoint is an
AWS-managed CloudFront distribution in front of the regional one: TLS terminates at a PoP near the
caller, and the edge→origin leg runs on AWS's backbone. It caches nothing here — every route is
authenticated — so connection setup was the entire benefit.

It was given up for a reason that is worth stating plainly, because it is a real trade and not a
free win: a regional custom domain will only accept a certificate from **its own region**, and an
edge-optimized one forces the certificate into us-east-1 along with a CloudFront in the path. The
choice was a simpler front door over faster handshakes for distant callers.

Who pays: anyone far from `ca-central-1`. TCP is one round trip and TLS 1.3 another, so roughly two
RTTs precede every request's first byte — and they are **paid per request**, not per session,
because the app does not reuse connections (see Gaps). Near the region the difference is invisible;
measured from a client close to the region, the custom domain and the `execute-api` hostname are
indistinguishable, ~38 ms to `appconnect` and ~75 ms total. That measurement proves only that the
cutover works. It cannot price the trade, because by then both hostnames terminated in-region — the
edge path was gone from under both.

Accepted, rather than merely unmeasured. The client keeps a local SQLite mirror and serves reads
from it, so a `GET` crossing the continent is neither frequent nor on a path a user waits behind;
writes are few and tolerant of a slower round trip. That is what makes the handshake cost cheap
enough to trade away for a simpler front door. It is a judgement about today's traffic, not a
permanent one — the revisit trigger is traction, and the shape of the answer is already known:
front the regional endpoint with a CloudFront distribution, which restores edge termination without
giving the certificate back to us-east-1.

## Why not the web distribution

The serious alternative was serving the API off the existing web CloudFront distribution at
`heart-of.me/v1/*`, same origin as the Flutter web build that will eventually live at the apex.
That is genuinely attractive: same origin deletes CORS rather than solving it, reuses the
certificate that already covers the apex, adds no DNS, and keeps one front door for a future WAF.

It was not taken, and one hazard is worth recording because it is easy to walk into later.
CloudFront's `CustomErrorResponses` are **distribution-wide, not per-behavior**. The standard SPA
fallback — 403/404 → `/index.html` with status 200 — would therefore rewrite the API's own errors:
`route_not_found`, and the `anonymous_account` 403 the client branches on. Anyone putting an API
behind the same distribution as a single-page app needs SPA routing done by a CloudFront Function
on the default behavior instead, leaving `CustomErrorResponses` empty.

The `/api/*` behavior that used to sit on the web distribution is gone in this change. It had never
worked: its origin carried `origin_path = "/v1"`, so a viewer request for `/api/templates` reached
the gateway as `/v1/api/templates`, the stage stripped `v1`, and the route table — which has no
`/api` prefix — returned `route_not_found`. Nothing called it. Removing it also took the api stack's
`api` output, whose only consumer it was.

## Certificates

Both are ACM certs in `ca-central-1`, one per account, DNS-validated, issued outside Terraform the
way every other cert in this repo is. Their validation CNAMEs live in `dns/acm.tf` alongside the
us-east-1 ones.

`app/stacks/api/variables.tf` validates the ARN twice: once for shape, once for **region**, against
`var.region`. The second guard exists because every other certificate here is us-east-1 — CloudFront
demands it — so reaching for a us-east-1 ARN is the trained reflex, and a regional domain name
rejects it. The guard turns an apply-time failure into a plan-time message.

## Standing one up takes two passes

The zone and the app environment each hold something the other needs: the environment cannot create
a domain name until ACM has issued, and ACM cannot validate until the zone carries the CNAME; the
zone cannot alias the domain until the environment has created it. So:

1. `dns` — validation CNAME. Apply. ACM issues.
2. `app/environments/<env>` — `custom_domain`. Apply. Domain name and base path mapping appear.
3. `dns` again — `<env>_api_domain_name` from the environment's `api_custom_domain` output. Apply.
   The alias resolves.

Both halves are gated so the intermediate states are valid rather than half-built: `custom_domain`
is nullable and skips the domain entirely, and each alias record is `count`-gated on a non-empty
target. The same `""`-means-off switch the monitoring stack gives `alarm_topic_arn`.

## CORS, and where it had to sit

`heart-of.me` calling `api.heart-of.me` is cross-origin, so the browser client needs CORS. It is
Dart, not Terraform: the integration is `AWS_PROXY`, so API Gateway forwards a preflight rather than
answering it, and the allowlist wants to live with the code that reads it.

`middleware/cors.dart` is wired outermost in `buildApp`, below only the log line. That position is
the whole design. A preflight is an `OPTIONS` carrying neither a bearer token nor an `x-app-version`,
so `authentication()` would 401 it and the version gate 426 it before anything could answer. Equally,
a 401 that reaches a browser without `Access-Control-Allow-Origin` is not read as a 401 — it is an
opaque network failure, and the client branches that exist for `anonymous_account` never see it.

The allowlist is exact string matching against serialized origins, from `ALLOWED_ORIGINS`. Empty
means off, which is the honest default for an environment with no browser client. There is no
`Access-Control-Allow-Credentials`: the session is a bearer token in a header, never a cookie.
`Access-Control-Allow-Headers` is not guessed — it is the set the client actually sends
(`authorization`, `content-type`, `accept`, `accept-language`, `x-app-version`, `x-timezone`), since
anything absent from it is refused by the browser before the request leaves the machine.

A request with no `Origin` — which is every call the mobile app makes — passes through untouched.

### Middleware does not see what the router could not match

Worth knowing before adding any middleware here. Relic's `use(path, middleware)` *maps stored route
values*: it wraps handlers that exist. A request the router cannot match never reaches one, so
neither a path miss (404) nor a method miss (405) runs the chain — not `cors`, not `authentication`,
not even `requestLogging`.

That bites CORS hardest, because a preflight is an `OPTIONS` and the route table carries none: every
preflight was a 405 composed before `cors` could speak. It is not a thing that can be overridden —
relic settles a method miss from the router's own lookup, so there is no handler to wrap. What there
is instead is making sure neither miss ever happens:

- **Method miss.** `buildApp` registers, for every path, each verb a browser can issue that the path
  does not serve, behind a handler returning `JsonResponse.methodNotAllowed`. The lookup now always
  finds something, so the chain always runs. Three things follow: a preflight reaches `cors`, a 405
  carries CORS headers and a log line, and its body is the same JSON shape as every other refusal
  rather than relic's. `connect` and `trace` are left alone — a browser cannot send them.
- **Path miss.** The router's `fallback` is wrapped by hand in `cors` and `requestLogging`, since a
  fallback is not a stored route and nothing registered with `use` reaches it.

One consequence worth knowing: a wrong verb on an authenticated path is now a 401 before it is a
405, because the chain it newly runs through includes authentication. Arguably the better answer —
it stops an unauthenticated caller mapping which verbs a path serves — but it is a change.

## Gaps

- **`Access-Control-Allow-Methods` is the union across the whole table, not the verbs of the path
  being asked about.** `cors` answers a preflight before routing, so it does not know which path it
  is for. Harmless — the real request still gets a 405, and that 405 now carries CORS headers — but
  a per-path answer would let the browser refuse the call itself, one round trip earlier.
- **No browser has exercised any of this.** CORS is covered by tests through the real chain, not by
  a real Flutter web build, which has not shipped.
- **The cost of dropping edge termination has never been measured, and has been accepted anyway.**
  Measuring it needs a client far from `ca-central-1`; the comparison stopped being available the
  moment the endpoint went regional. Deferred deliberately — see *Regional, not edge-optimized* for
  why the trade is cheap at this traffic level and what would reopen it.
- **`execute-api` is still open.** The custom domain is an addition, not a restriction; the raw
  hostnames answer the same API to anyone who knows them. Closing them needs every shipped build
  moved over first, and the minimum-version gate is what would make that safe.
- **No WAF, no rate limiting, no usage plan.** Authentication is the only thing in front of the
  API.
