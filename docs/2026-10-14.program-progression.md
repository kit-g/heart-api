# Programs: progression, misses, lighter weeks, and the rest

The second round of the program model (heart-api#228–#234). It comes from the
research in the Notion page "Programs — research" (2026-10-14), and extends
`docs/2026-10-13.programs.md` without changing anything that shipped. Written
before code; each part is rewritten from the code as it lands.

## What the first round left out

The five growth rules only ever add. The research and every established
program need more. In order of how many programs need it:

1. **A missed target** holds the weight, and after a few misses in a row cuts
   it (#228).
2. **An AMRAP set** decides how much to add (#228).
3. **A lighter week**, scheduled or taken on demand (#229).
4. **Targets**: reps in reserve, a capped AMRAP, a max hold, and rest per
   exercise (#230).
5. **Variation ladders**: progressing to a harder exercise, not more load (#231).
6. **Slots**: supplemental sets at a share of a base, the same lift with two
   bases, one lift's base driving another, and an open slot for "50–100 reps of
   a pull" (#232).
7. **Phases and test sessions** (#233).
8. **Supersets and circuits** (#234).

## One engine, in heart_models

Today the app decides when a base moves and writes the change. That makes the
rules' meaning live in one client. The rules become data with one reading, the
way position already is:

```dart
ProgressionStep Progression.next({
  required GrowthRule rule,
  required ProgramBase? base,      // the current value, null before the first
  required LoggedExercise session, // this session's working sets with their targets
  required int misses,             // misses in a row before this session
  required bool lighter,           // a lighter week: nothing moves, nothing counts
});
```

`ProgressionStep` is one of: `grow(value)`, `hold`, `miss(streak)`,
`cut(value)`, `advance(toExercise)`. The app turns a `grow`, `cut` or
`advance` into the stored record it already writes (a base, or a swap action),
caused by the workout. `misses` comes from `Progression.streak`, which folds the
exercise's program sessions since its last base change. The server never runs
the engine: it stores what the device wrote, as today. `/me` and MCP describe
the rule; they don't predict.

## Rules, extended

Every rule keeps its kind and gains optional fields. A rule carries fields it
doesn't know and writes them back, so a newer field survives an older build.

```json
{
  "kind": "rangeThenWeight",
  "step": 2.5,
  "miss": {"when": "anySet", "after": 3, "cut": 0.1},
  "amrap": [{"reps": 10, "step": 5}],
  "deload": {"every": 6, "load": 0.9, "volume": 0.5}
}
```

- **`miss`**: what counts as a miss and what follows. `when` is `anySet`
  (a working set short of its target), `amrap` (the AMRAP set short) or
  `totalReps` (with `floor`, the r/Fitness rule: fewer than 15). After `after`
  misses in a row the base drops by `cut`, a share, rounded to the rule's step.
  A miss alone holds the base. Default when absent: `anySet`, after 3, cut 0.1.
  `shareOfMax`'s existing `misses` and `missCut` read as `miss.after` and
  `miss.cut`.
- **`amrap`**: the step chosen by the AMRAP set's reps, the highest `reps` met
  winning; below every entry the rule's own `step`. A `step` of 0 holds; a
  negative one cuts. Covers "double the step past 10", a reps-to-increase
  table, and a training-max cut when the AMRAP falls short.
- **`deload`** lives on the program, not the rule (below).

New kind **`ladder`** (#231): `{"kind": "ladder", "rungs": [exerciseId, ...],
"top": 12, "bottom": 8}`. When every working set reaches `top`, the session's
exercise advances to the next rung and its targets restart at `bottom`. The
last rung grows by reps only. The device records the swap as a program action
`advance` (from, to, the workout), edits the session template, and moves the
rule's key; undoing is deleting the action and the device reverting the
template. Ladders in the library are content: ordered exercise keys in
`content/exercise_ladders.yml`, resolved to ids when a program is copied.

## Lighter weeks (#229)

- **Scheduled:** the program carries `deload: {"every": N, "load": 0.9,
  "volume": 0.5}`: every Nth cycle is lighter. Load and volume are shares the
  sheet applies to the cycle's targets.
- **On demand:** a program action `lighter` makes the open cycle lighter.
- **In a lighter cycle** nothing moves and nothing counts as a miss.
  `ProgramPosition` gains `lighter` for the open cycle.
- A `shareOfMax` wave that has its own deload week keeps it; `every` is for the
  rules without one.

## Targets and rest (#230)

All additive to the target vocabulary from #195:

- **`rir`**: reps in reserve beside the measures, `{"rir": 2, "reps": {...}}`.
  "Stop with 2 left."
- **A capped AMRAP**: a range with `amrap`, `{"reps": {"min": 5, "max": 10,
  "amrap": true}}`: as many as you can, up to 10. An open top stays the uncapped
  AMRAP.
- **A max hold** is already an open top on `duration` (`{"min": 20}`).
- **Rest** per template exercise, in seconds: `rest` on the exercise. A
  workout started from the template carries it.

## Slots (#232)

- **A rule per slot.** A rule may be keyed by a template exercise id (one
  occurrence in one session) as well as by an exercise id. The occurrence's
  rule wins. Bases gain an optional `slot`, the template exercise id, so the
  same lift heavy on Monday and light on Thursday keeps two bases.
- **A share of another base.** `share` gains `of`: `{"share": 0.6, "of":
  exerciseId}`, the front squat at 60% of the squat's training max. Without
  `of`, the exercise's own base.
- **Supplemental sets.** A `shareOfMax` wave set may be `supplemental`: it
  takes its share like the others but never counts for the AMRAP, a miss or a
  bump. A first-set-last 5×5 is five of them at the week's first share.
- **Open slots.** A template exercise may carry a `pattern` (a movement-pattern
  key from the library) meaning "any exercise of this pattern"; its exercise is
  the default the app offers. A target may say `total`: reps across all sets,
  `{"total": {"min": 50, "max": 100}}`.

## Phases and tests (#233)

- **Phases.** A program may list `phases`: `[{"name", "sessions": [templateId],
  "cycles": N}]`, run in order; the last may leave `cycles` out and repeat.
  Without `phases` the program is one repeating phase, as today. Position gains
  `phase` (its index) and `week` counts within the phase; `weeks` stays the
  whole program's length.
- **Test sessions.** A program may name sessions as tests: `tests: {templateId:
  {"share": 0.9}}`. A test workout sets the bases of the exercises it tested:
  share × an estimated one-rep max from the best set (Epley, reps capped at 10).
  The engine's `Progression.test` returns them as `grow` steps caused by the
  workout.

## Supersets and circuits (#234)

A template exercise and a logged exercise may carry a `group`: exercises with
the same group in one session are done back to back. Absent keeps what is
stored, so a build that predates it never splits a superset.

## Storage

| Change                                        | Where                              |
|-----------------------------------------------|------------------------------------|
| rule fields `miss`, `amrap`; kind `ladder`    | `programs.rules` (JSONB, validated) |
| `deload`, `phases`, `tests`                   | new JSONB columns on `programs`     |
| action kinds `lighter`, `advance`             | `program_actions` (+ from, to, workout) |
| `slot` on a base                              | `program_bases.slot`                |
| `rest`, `group`, `pattern`                    | `template_exercises`; `group` also `workout_exercises` |
| `rir`, `amrap` on a range, `of`, `total`      | the set target JSONB, already stored as given |
| ladders                                       | `content/exercise_ladders.yml`      |

## Compatibility

No released build has programs yet, so the program shapes are free to grow.
Templates and workouts are read by 1.13, so their new fields follow the
template rule: an absent key keeps the stored value. Targets are carried
untouched by builds since 2.16.0.
