# Coaching: the backend design

The backend side of coaching (heart-of-yours#168). A draft, written before any code; once the code
lands it gets rewritten from the code, like every other doc here. The app's request is
`docs/2026-10-31.coaching-api.md` in heart-of-yours and its product design is
`docs/2026-10-31.coaching.md` there. Section numbers below (§n) point at the request.

## Scope of the first version

| In | Out, for later |
|---|---|
| Connection groundwork, coach read scope, hiding a workout (§2, §3, §10) | `/me` and MCP surfaces for coaching |
| One-person invitations, in the app and on the web (§1) | A review web app for reports |
| Push rail and flexible settings (§5, plus the note below) | Public links; the schema leaves room |
| Device keys, key delivery, messages and notes, encrypted (§12) | Payment |
| A coach's library, sending, versions (§6) | |
| Shared editing, history, target beside done (§7, §8) | |
| Roster and feed (§4, §5) | |
| Logging for someone, block, report intake (§9, §10, §11) | |

Encryption is a go: messages are encrypted from the first one, and no in-clear version is built or
released.

**`/me` and MCP are out, with one exception that isn't a surface.** Existing tools read data coaching
now writes. Coach-written text reaches the assistant through `list_programs`, `get_program`, `get_program_history`
and, for a workout a coach logged, `list_workouts` and `get_workout`. `quotedIfAssigned` covered templates
only, so programs and every place a session's name appears gained the same marking, and logged workouts do
when logging ships. One path is still open: the name of a custom exercise copied from a coach reads as the
student's own wherever exercises are named, since a copied exercise doesn't record where it came from.
MCP's `update_template` already refuses a program session, so nothing there writes to a coach's copy.

## What exists, and what the request assumes

- **Nothing installed calls any of this.** v1.13.0 and the current app have no client for
  `/connections`, `/comments`, `/devices` or a coach's reads of `/accounts/:id/…`, and no
  `firebase_messaging`. The contract changes below reach no installed build, so they are additive in
  effect. Each still goes in the release's compatibility note.
- **Pushes have never reached a phone.** The rail stops at the server: token table, renderer, firebase
  Lambda. Coaching ships the first push client.
- **`exercise_sets.target` already holds what a set aimed for,** so half of §8 is done.
- **A skip's reason isn't refused today.** `skips.reason` stores `sick` and `sore` in clear, and
  `/me/programs/:id/history` and MCP serve them. Neither the health doc nor `site/privacy.html`
  mentions skips, so the promise §2 cites doesn't cover them. Keeping the reason from a coach is a read
  filter here, not a storage rule. What the server refuses outright is the go-easy list and health
  readings.

## Connections

The table is the base of everything, and it changes in these ways.

**One row per pair and domain, in either direction.** Domains are what let two people hold several
relationships: peers in `general`, or one coaching the other in `running` and the reverse in `swimming`.
That stays. What goes is a hole: `ON CONFLICT` only sees one direction, so a pair can hold two rows in
one domain, which `docs/2026-08-02.connections.md` says can't happen. A unique index on the unordered
pair and the domain closes it. Nothing calls these routes, so the migration expects no duplicates, and
keeps the newest row if it finds any.

**A real id.** It gains a `uuid`, sent as a new `connectionId`. `Connection.id` stays as it is.

**A history.** An append-only `connection_events` (connection, status, by whom, when) records every
move. It closes gap 2 in `docs/2026-08-02.connections.md`, and pause windows are read from it.

**Ending keeps the row, and only an invitation reopens a coach's.** `DELETE` becomes `severed`, because
"this person was a client" has to outlive it.
- `severed` and `declined` no longer move to `pending` on a coach row. Today either person can make that
  move on any row, and then the one who isn't the initiator can accept their own request. This hole is
  open now, whichever way a row got severed.
- For peers the move stays, and the rule changes: whoever moved a row to `pending` can't answer it.
  The check reads `status_by`, not `initiator_id`.
- An invitation names a domain. Accepting one rewrites that domain's row if there is one: who invited, roles, status, a new `accepted_at`, and
  `shares` back to empty. A former client reads from the new date, and the earlier stint stays in the
  events.

**A block belongs to the pair, and to every path.** A `blocks` table (blocker, blocked, created, lifted)
survives being lifted. Setting status `blocked` writes it. A block ends everything live between the two
people, in every domain, so lifting it restores nothing: a coach's row needs a new invitation, and a peer
asks again.
- One SQL function, `_relation(reader, owner)`, folds the pair's rows into one answer (see *Who can read
  what*), and answers nothing under a live block. Every cross-user path goes through it: reads, comments, program and workout writes, key
  fetches, messages, key delivery, and `notify`. A test walks the cross-user routes with a blocked pair.
- Someone with only a link has no row, so `POST /invitation-links/:token/block` blocks the inviter, and a
  report can name a person without a connection. Accepting checks blocks both ways, so a blocked coach's
  next link answers like any link that's no longer good.

**Also:**
- `accepted_at` and `shares` go on the row. `shares` is a list of what the student chose to open,
  empty by default: `history` (workouts before acceptance) and `goals`, in a vocabulary that can grow.
  The student sets it when accepting and can change it at any time, and only the student can.
- **Coach connections come only from an invitation.** `POST /connections` keeps working for `PEER` and
  refuses `COACH` and `STUDENT`, so the scope can't be bypassed.
- **A paused connection resumes only by the student,** for coach connections. Today either side can.

## Peers stay

There's no peer UX, and the groundwork keeps the role alive rather than building around coaches:
- Roles stay as they are, and a peer reads what a peer reads today, photos included.
- Threads, blocks, reports, invitations and push settings belong to the connection or the person. No
  general table has a `coach_id`. An invitation carries a `role`, and only `COACH` is offered at first.
- Coach-only things are the ones that make no sense otherwise: the library, the roster, the feed,
  shared editing, logging for someone.
- Hiding a workout hides it from every connection, peers too.
- A pair can be peers and coach and student at once, in different domains. A student who also coaches
  their coach is two coach rows, one each way.

## Who can read what

Four copies of the `_auth` CTE become one function over `_relation`, and role decides the scope in one
place. Workouts carry no domain, so a read can't be sorted by row, and it takes one answer per direction:

- **A coach's view wins over a peer's.** While the reader holds a live or paused coach row towards the
  owner, a peer row between them adds nothing. A coach can't reach photos or earlier workouts by also
  being accepted as a peer. The other direction is untouched: the student's peer view of their coach
  stays as it is.
- **A pause stops all of it.** If any of the reader's coach rows towards the owner is paused, coach reads
  stop for workouts logged in that time, so a student's pause can't be walked around through another
  domain.
- **Otherwise the rows add up:** the earliest `accepted_at` among active coach rows, and everything those
  rows share. A peer row alone gives what a peer reads today.

Writes do go by row. A copy records its `connection_id`, so ending the `running` relationship ends the
coach's write access to the program sent over it, and leaves `swimming` alone.

| Coach reads | How |
|---|---|
| Workouts | From `accepted_at` (or all, with `history` shared), not hidden, not started in a pause window, without images |
| Skips | `at`, `templateId` and `programId` only. No `reason`, no `weather` |
| Program copy and position | Through a coach's read of that program, by the rule below |
| Goals | Only with `goals` shared, and only workout metrics: if a health-backed metric ever exists, a coach doesn't read it |
| Comments | Only on what the coach can read: a hidden or out-of-scope workout, or any photo, is a 404. Today any connection is enough |
| Name, photo | What the roster and the ask show; never an email |

`workouts.hidden_at` is the hiding. A full replace without the key keeps it, so an old build can't
unhide anything, and only the owner ever sees it.

**Whatever a coach sees that's derived is computed only from what they can read.** That covers position,
bases, the roster and the feed. Otherwise a hidden workout shows up as the week moving on. So a hidden
program workout leaves its session undone in the coach's view, a base it moved stays out of it, and the
coach's week can trail the student's real one. The student's own position is unaffected. That's what
hiding promises, and a coach's edits don't depend on position.

## Invitations

`invitations` holds the inviter, role, domain, a hash of the token, the name the coach wrote, an
optional library program, `expires_at`, `canceled_at`, and `max_uses` (1 for now). What happened goes
in `invitation_responses` (user, accepted or declined, when), so a link that many people can ask
through later needs no new shape.

- `GET /invitation-links/:token` is signed out and returns the coach's name and photo and whether the link
  is good. Nothing else.
- Opening uses nothing up, and accepting is one transaction: connection, event, `shares`, program copy,
  and "Your coach" left on in `extra.features`, so the app agrees when it next opens. It locks the invitation, so of two people racing
  the second gets "no longer good", and the same person accepting twice is a no-op.
- A student at their program limit still connects. The answer says `programDelivered: false`, the coach
  sees that, and can send it later.
- Resending renews the token and the expiry. Cancelling is a timestamp.
- Limits: pending invitations per coach, and a rolling count of declines. `400 invitation_limit`. A
  busy coach has many accepted, and an abusive one has many declined.
- **The web does what the app does.** `site/invite.html` opens to anyone, then signs in or makes an
  account as the consent page does, and accepts, declines or blocks, or makes a link for a coach. Accepting
  there can leave someone with no device holding keys. The coach can tell from their device list, the
  thread waits, and the fingerprint reaches the device if it opens Heart through the same link.
- The coach's key fingerprint rides in the part of the link that never reaches a server, so nothing
  here touches it.

## Pushes and their settings

Push types will multiply, so a new one must cost a catalog entry, with no migration and no app release.

**The catalog** lives in code, one entry per topic: key (`coaching.message`,
`coaching.workout_digest`), group, default delivery, visible or silent, Android channel, collapse key
and localized copy, including the name and description a settings screen shows.

**The preferences** are sparse. `push_preferences (user_id, topic, connection_id NULL, delivery)` has
a row only for what someone changed. The most specific answer wins: this person and topic, then the
topic, then the catalog's default. `delivery` is an open vocabulary, `instant`, `daily`, `off` for
now, read tolerantly.

**`GET /push/settings`** returns the whole catalog, localized, with each topic's resolved delivery.
The app draws its screen from the answer, so a build that has never heard of a topic can still show
and change it. `PUT` writes one answer. They don't live in `extra.features`, because the sender has
to query them.

**One send path.** `notify(userId, topic, args, connectionId)` resolves delivery, groups tokens by
locale, renders and publishes, and sends nothing across a block. Comments move onto it. No topic has a
body or content arguments, comments included: title and ids only, so "Alex messaged you" is what's
possible and a test holds it there. `comment.created` stops carrying its text, because coaching ships
the first client that would receive it, and it would go through Apple and Google.

**Daily delivery** queues rows per person and an hourly job sends them. It reaches Firebase, so it's an
AWS schedule, not pg_cron. The server knows no zones, so `POST /devices` takes an optional UTC offset.
The person's most recently seen device decides their evening, and one push goes to all their tokens,
once a day.

**The firebase Lambda** gains silent pushes, channel and collapse fields. It has no way back to the
database, so stale tokens go by a pg_cron job, after 270 days unseen, when Firebase treats them as
expired. Silent pushes are what heart-api#40 needs, so that ticket sits
on this rail rather than building its own.

## Messages

`threads`: `id`, `connection_id`, and the two people, each nullable. `thread_items`: `id` (v7, from the
device, idempotent), `thread_id`, `sender_id`, `kind`, optional
`subject_type` and `subject_id`, `content`, `commitment`, `tag`, `tag_key`, `at` (the device's),
`xid`, `created_at`. Access is by person, not device: every device of both people reads the same stored
copy.

**Order is the server's, by transaction.** A message written offline carries an old `at` and a v7 id
from then, so sorting by either puts it behind a reader who's already past that point, and it's never
fetched or counted. `xid` and `ChangeCursor` already solve this for the workout feed: reads go by
`(xid, id)`, in both directions, and stop below the oldest running transaction. A read position is such a cursor, and unread
is what's after it from the other person. The app shows `at`.

- `content` is a string of at most 16 KB, never an object. The server doesn't parse it, index it or log
  it. `Request.json()` checks keys and ciphertext has none, so it passes without an exception.
- Paged reads in both directions and "since a point". A connection that has ended stays readable and
  takes no new items.
- A blocked party can't fetch it, the blocker can, and each device keeps its own copy.

**Either person can delete the conversation, for both sides.** One call, whatever the connection's
status, and no agreement from the other side.

- The server removes the thread's items at once and records who and when on the thread. It can take new
  messages if the connection is live.
- `threads.cleared_at` is how every device learns: a device that sees it newer than its own copy drops
  what it holds. A modified client could keep its copy, and the server can't prevent that.
- **The other person gets a short window.** Otherwise deleting a conversation would destroy the
  evidence before a report. The app shows who deleted it and keeps its copy for 7 days, for reporting
  only, and then drops it. Nothing is back on the server in that time. A report carries its own words
  and tag, so the check still works.
- A filed report isn't touched by a deletion.
- It's the whole conversation, not one message.

**Deleting an account leaves the conversation with the other person,** who can still read the ciphertext
they hold keys for. Anyone who wants their words gone deletes the conversation first, and the account
deletion screen and `site/privacy.html` have to say that. The full list is under *Deleting an account*.

**A message can be about any detail of a workout.** `subject_type` and `subject_id` take what comments
already target (`workout`, `workout_exercise`, `exercise_set`, `workout_image`) plus `skip`, `program`
and `session`, in a vocabulary that can grow. So "that third set" is a message in the one inbox, and
`?subject=` finds what was said about it without a device fetching the whole thread.

- The request puts the reference inside the content. It sits beside it here, because a new tablet
  couldn't otherwise show a set's conversation. The server learns which set is being talked about,
  which it already holds in clear, and never what's said.
- It's a link without a foreign key, unlike `comments`, which cascade. A deleted set leaves the message
  standing, and a subject opens nothing: a message about a workout later hidden stays, and the workout
  stays hidden.
- The `comments` table and routes stay as they are. They have no client, and the thread is the inbox.
- Reactions, later (#369), fit the same shape: a `reaction` kind whose subject is a message or a detail,
  sealed like the rest and left out of unread counts.

**`kind` is how things the server refuses today can arrive later.** With encryption working, a
student's device can seal something for their coach with the thread's key: a skip's reason
(`kind: skip_reason`, `subject: skip`), a go-easy area, in time a reading they chose to share. The
server stores a string it can't read, so neither the table nor the route changes. `kind` is an
allowlist in code: the first version accepts `message`, and each new kind is a deliberate one-line
change.

Two limits on that, stated plainly:
- **Sealing doesn't lift the health rule.** `CLAUDE.md`, the health doc and `site/privacy.html` have to
  change first, and that's an explicit policy decision. Until then the allowlist stays at `message`.
- **The server can't check that a string is ciphertext.** The client is the only guard on that, which
  is why the allowlist stays narrow and the app's tests hold the sealing.

## Media, later

Text only is the first version's limit, not the design's. Images and video on sets, exercises,
workouts and messages are coming, and nothing here gets in their way. None of it is built now.

- **In a thread:** the device encrypts the file with its own key and uploads it. That key and the
  file's hash travel inside the message, so the commitment covers them. The server holds a blob and its
  size. `content` has room at 16 KB, and a child table keyed by `thread_items.id` is additive. There
  are no server thumbnails or transcoding, because the server can't open the file.
- **On your own log:** `workout_images` generalizes to a media row with the same subject vocabulary, in
  clear like photos today. A coach doesn't read those (§2) unless `shares` grows a value for it. A form
  check is the thread's kind: a video in a message about that set.
- **Reports** will have to carry a file as well as words.
- **Storage and video limits** need sizing before they ship (#367).

## Encryption

The server hands out public keys and carries sealed items. It never holds anything that opens them.

**Devices.** `crypto_devices`: owner, two public keys, a fallback key, an optional signature from
another device of the owner's, `created_at`, `removed_at`. They're apart from `device_tokens`, since
a push token rotates and a key identity mustn't.

**Single-use keys.** `one_time_keys` holds up to 50 per device. Claiming one deletes it in the same
statement, with `FOR UPDATE SKIP LOCKED`, so none is handed out twice, and the fallback answers once
they run out. A device can read its own count.

**Who can fetch.** Your own devices, and anyone you have a relationship with or had one, under no
block, which includes an ended one: a new phone must still be able to ask for the keys to history it may
read. Without the gate, fetching would probe who has an account and drain someone's single-use keys, so
it's also limited to 60 claims an hour per pair.

**A new or removed device** is listed with whether it was vouched for, and a silent push tells the
other side's app to look.

**Key delivery.** `device_queue`: `seq`, `id` (from the device, so a retry can't deliver twice), recipient
device, sender device, `kind`, `content` under 1 KB.
- A device reads what's unconfirmed, by `seq`, and confirms. It doesn't page by a cursor, so a row
  committed late can't be skipped.
- A sender's device sends one at a time, waiting for each answer, which is what makes `seq` the order
  sent for that pair. The server can't make order out of parallel sends, and the app has to know that.
- At most 2,000 unconfirmed items per sender device and recipient device (`400 queue_full`), about where
  the spike found a pair needs a new session anyway.
- Confirmed rows go, and a pg_cron job removes unconfirmed ones after 90 days.
- Asking again for a missing key is the same route with its own `kind`. A block stops items between
  the two people.

**Commitments and tags.** The sender gives a 32-byte `commitment` with each message, required from the
start, so every message can be reported. The server signs commitment, sender, recipient and time with
a key from Secrets Manager, and stores the tag and the key's id, so the key can rotate. A reporter's key ties the words to the commitment: it's HMAC-SHA256 of the words under
that key. The scheme is
our own work on a published idea and needs a qualified review before release, as the app's design
says.

**Notes.** `coach_notes`: coach, connection, `content` under the same contract, `updated_at`. Only that
coach reads or writes them, on any of their devices, and the client never learns they exist. They stay
when a client leaves or deletes their account, until the coach deletes them or the coach's account goes.

## A coach's library

Library programs are **documents, not rows in `programs` and `templates`.** `library_programs` (coach,
name, current version) and `library_program_versions` (version, body as JSONB, in the shape of a
`POST /programs` body).

Filtering library rows out of `templates` would mean touching every list, export, `/me` query, MCP
tool, summary and limit, and one miss shows a coach's work among their training, including on an old
build. A separate table can't leak that way.

**Sending** makes the copy on the server, because the student may be offline. The copy's `programs` row
gains `coach_id`, `connection_id`, `library_program_id` and `library_version`, which also answers "who holds which
version". Sessions carry `assigned_by` as today, so `quotedFrom` keeps working.

**A copy gets its own ids, all of them.** Two students can't share an id (`403 id_taken` on the second),
and a body is full of references.
- A walk over the whole document replaces every id, as a key or a value, so a later id-bearing key is
  covered without anyone remembering it. Exercises go through the student's own by name, then the
  library's, then a copy made for them, so a coach's custom exercise reaches the student.
  Only what the coach can see goes through: the library's and their own, never someone else's private
  exercise.
- New ids are v7, because anything else reads as no link on a workout or skip. The map from library ids
  to the copy's is stored on the copy, so an update can find its rows.
- Saving a library program gives every session, exercise and set an id, so versions can name the same
  rows.

**A student at their limit** still connects: accepting sends the program as its own step, and the answer
says `programDelivered: false`. Sending the same program twice answers the copy they hold. A send covers several clients
and reports each: one that can't get it comes back as not delivered, with a reason, and stops nothing else.

**Bases** stay the device's job, as when starting from the library: the copy arrives without them and
the student's app proposes them from their history. A new program that would replace another waits
for a start date from the student (§6).

**Bringing a copy up to date** writes through the map, so a session or slot the student has already
trained keeps its id, and with it their week and their bases. A new session joins the next cycle by
`joined`, as any session does. It overwrites the student's own edits to that copy, as a recorded change
that can be put back; the app should say so.

## Two people, one copy

Only a managed copy (`coach_id` set) pays for any of this. Personal programs are untouched.

**History.** `program_changes`: a device-made `id`, actor, when, what it touched (the program's own
fields or one session), `revision`, and `before` and `after` as JSON snapshots. Snapshots outlive what
they describe, so it survives edits and deletes. A write and its record share a transaction. `xid` orders
it, and `GET /programs/:id/changes?since=` answers "what changed", with a silent push saying that
something did. `Program` carries `revision` and `sessionRevisions`, so a device knows what its edit starts
from.

**Conflicts are per session, and only with the other person.** The program's own fields and each session
keep a separate `revision`, and a write carries the `baseRevision` it started from.
- `409 program_changed` means the other person changed this same thing since then. A coach's edit to
  Monday doesn't stop a student's edit to Thursday.
- Your own changes since your base don't conflict, so two queued edits to one session both land.
- A retried save repeats its `id` and gets the stored answer.
- **An old build sends no `baseRevision` and can't handle a 409.** Its write is accepted and recorded
  with `stale: true`. The coach's version sits in `before`, and putting it back is one action. So the
  old build can overwrite, and nothing is lost, which is what the request asks.

**Putting a change back is a new change, and it restores links.** Deleting a session sets
`workouts.template_id` and `skips.template_id` to null, so the snapshot of a deleted session also lists
the workouts and skips that named it. Putting it back recreates the session under its own ids and links
them again, so the position returns. Either person can put a change back.

Coach writes go under `/accounts/:targetUserId/programs/…`, checked against the copy's `connection_id`
and blocks, so access ends with that connection and under a block. A session has to be in the program the path
names, and an id already in use can't be taken over as a new session.

**Target beside done.** What was asked can't be read from the stored session: lighter cycles and wave
rules change it. Doing the planned 2 of 4 sets in a lighter week would read as 2 not done. So the device
says what it planned, as it already works out with `PlannedSession`:
- `PUT /workouts/:id/plan` stores it in `workout_plans`, with which set each planned set became. The first
  one stays, since it's what was asked at the time, and it survives later edits to the session.
- It's beside the workout rather than in it, so nothing about a workout's body changes for old builds.
- Planned sets with no tie are what wasn't done, and tied or untied sets that were added show as added.
  `exercise_sets.target` stays as it is.
- A workout with no plan, from an old build or not from a program, has no comparison and raises no
  reason.

## Roster and feed

Position is a Dart fold over a program's history, so a read-time roster of a thousand clients would
run a thousand folds. **`client_summaries`** holds one row per coach connection, so someone coached in
two domains appears twice: program name and position,
recent training times, last trained, and reasons. It's computed by the read policy, from what the coach
can read. The queue recomputes a row on anything that changes the answer: a workout saved, edited,
deleted, hidden or unhidden, a skip, a program action or change, a pause or resume, and a change to
`shares`. A daily pg_cron job adds gaps and endings. The roster is a keyset page over it, sorted by need
or filtered by reason. It may lag a little, and the app is offline-first anyway.

- Recent training is sent as times, not a seven-day mask. The app has the coach's zone and the server
  doesn't.
- **"Lighter than planned" compares with `workouts.plan`,** so following a lighter week raises nothing.
- **Reasons need an end, and the request doesn't give one.** A "new note" that never clears isn't a
  signal. Each connection keeps a `reviewed_at` for its coach, moved by a new call, and reasons count
  only what came after it. Gaps and endings clear when they stop being true.
- The feed reads workouts and skips of the coach's clients through the read policy, plus endings from
  the summaries, newest first. The daily push draws on the same rows.

## Logging for someone, and reports

**Logging:** `POST /accounts/:targetUserId/workouts` writes the student's workout with `logged_by`,
through `_relation`. It's never public and the student can delete it.
- A coach's custom exercise goes through the same matching as sending, so nothing is dropped.
- The base move is the device's job, as with any workout, so the coach's device works it out with the
  same `heart_models` code and posts it under the same route, idempotent per workout. Without that, the
  student's later weights would be wrong.
- It carries a `plan` like any other workout, and MCP marks its text as quoted.

**Block** is under *Connections*.

**Reports** are in as intake only. `POST /reports` takes the reporter, the person, the connection if
there is one, a reason, and the words the device sends with what's needed to check them. It alerts the
owner with no words in the alert. Apple 1.2 and Google's equivalent ask for a way to report, a timely
response, a way to block and a contact route, and `site/support.html` is the contact route. None of
that requires a review app, which is what moves out.

**Report words are never stored in clear.** They can hold anything a person said about their body, and
the health rule leaves no room for a readable copy. The server checks them against the tag in memory,
records the answer, and stores them sealed to a review key whose private half isn't on the server. The
owner opens them with a script. A closed report is deleted after 90 days, and an unclosed one after a
year, by a pg_cron job. Reports hold plain ids rather than foreign keys, so neither person deleting their
account removes the evidence, and `site/privacy.html` says so.

**Before any tester reaches this:** `site/privacy.html` changes, since it says "don't share", and it and
the health doc say that notes and threads are the first health-shaped things with a remote copy, even
if unreadable. `CLAUDE.md` gets the same line: ciphertext only the two people can open.

## Deleting an account

What each table does when a profile goes. Today nearly everything cascades.

| Table | When that person's account goes |
|---|---|
| `threads`, `thread_items`, read positions | Stay for the other person. The person's side and `sender_id` go null. The thread goes when both sides are gone |
| `connections`, `connection_events`, `client_summaries` | Go: there's no relationship left |
| `blocks` | Go, with that person |
| `coach_notes` | The coach's go with the coach. Notes about a deleted client stay, and their `connection_id` goes null |
| `crypto_devices`, `one_time_keys`, the person's queued items | Go. A queued item from them to someone else stays, its sender null |
| `invitations`, `invitation_responses` | The inviter's go. A responder's id goes null |
| `library_programs` and versions | Go with the coach. Students' copies stay |
| `programs.coach_id`, `programs.connection_id`, `workouts.logged_by`, `program_changes` actor, `assigned_by` | Go null. A copy becomes the student's own, unmanaged |
| `reports` | Stay until their deadline, by plain id |
| `push_preferences` | Go |

## Beta, then release

The rollout has two stages. The beta goes out free to people who test it with the owner, and release
comes after. Payment isn't part of the beta, and nothing here builds for it.

**Who can coach in the beta.** The request has anyone able to coach, with no approval. In the beta,
only an account holding the `coach` entitlement can create an invitation (`403 coaching_beta`
otherwise), and the owner grants it by hand. It's the first row of the entitlement model
`docs/2026-09-23.developer-api.md` calls for: a small `entitlements (user_id, entitlement, granted_at)`,
and the profile says whether the account holds it so the app can show "Coach people". Students aren't
gated: anyone with a link can accept.

**Limits in the beta are guards, not promises.** They protect the database from abuse and nobody is
expected to reach them: 1000 clients per coach, 50 pending invitations, 100 library programs, 60
messages a minute per sender. Real limits are set for release.

**Keep what release will need.** Connection rows and their events survive ending, so how many students
a coach had, and when, can always be counted.

## Compatibility

Additive: every new table, route and optional field, and new `heart_models` members in a minor
version. Old builds keep what they don't know, under the rules templates and workouts already follow.

These tighten or re-mean a contract, and have no installed caller at v1.13.0 or since:
- a coach's reads narrow, and comments follow them
- `POST /connections` refuses `COACH` and `STUDENT`, and a pair holds one row per domain across both
  directions
- `DELETE /connections/:id` keeps the row, and a severed or declined coach row doesn't go back to pending
- only the student resumes a paused coach connection
- `comment.created` pushes lose their body

They still need classifying in the release note, and `heart_models` signatures stay as they are.

Health rule: no route takes a health-shaped field, and `Request.json()` and `health_rule.sql` keep
applying everywhere. `thread_items.content` and `coach_notes.content` are ciphertext strings.

## A coach isn't a second holder of the data

The design treats a coach as someone a student shows things to, not as a separate keeper of them.
Everything a coach reads ends with the connection, and either person can delete the conversation for
both. The app drops what it cached of a former client's workouts and program. Notes are the coach's
own writing, and the server can't read them.

## Decided against

**Age checks.** Heart doesn't ask for an age, estimate one or infer one, so nothing in the schema or the
API branches on it. Coaching changes nothing here. `site/privacy.html` keeps its existing line about
children and its contact route.
