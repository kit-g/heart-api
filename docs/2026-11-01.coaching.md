# Coaching: the backend design

The backend side of coaching (heart-of-yours#168). A draft, written before any code; once the code
lands it gets rewritten from the code, like every other doc here. The app's request is
`docs/2026-10-31.coaching-api.md` in heart-of-yours and its product design is
`docs/2026-10-31.coaching.md` there. Section numbers below (§n) point at the request.

## Scope of the first version

| In | Out, for later |
|---|---|
| Connection groundwork, coach read scope, hiding a workout (§2, §3, §10) | `/me` and MCP surfaces for coaching |
| One-person invitations (§1) | A review web app for reports |
| Push rail and flexible settings (§5, plus the note below) | Public links; the schema leaves room |
| Device keys, key delivery, messages and notes, encrypted (§12) | Signing in and accepting on the web |
| A coach's library, sending, versions (§6) | Payment |
| Shared editing, history, target beside done (§7, §8) | |
| Roster and feed (§4, §5) | |
| Logging for someone, block, report intake (§9, §10, §11) | |

Encryption is a go: messages are encrypted from the first one, and no in-clear version is built or
released.

The request has inviting and accepting work equally on the web. That moves out: the page reads the
invitation and leads to the app or store. It also means nobody accepts without a device that can hold
keys, so a thread never has to say it's waiting for one.

**`/me` and MCP are out, with two exceptions that aren't surfaces.** Existing tools read data coaching
now writes, so these ship in the first version anyway:
- Coach-written text reaches the assistant through `get_program`, `get_program_history` and
  `list_workouts`. `quotedIfAssigned` covers templates today. Program notes and coach-logged workouts
  need the same marking, or a coach's words become instructions to a student's assistant.
- `update_template` on a coach-managed session goes through the same write path as the app, so it's
  recorded in the history.

## What exists, and what the request assumes

- **Nothing installed calls any of this.** v1.13.0 and the current app have no client for
  `/connections`, `/comments`, `/devices` or a coach's reads of `/accounts/:id/…`, and no
  `firebase_messaging`. The contract changes below reach no installed build, so they are additive in
  effect. Each still goes in the release's compatibility note.
- **Pushes have never reached a phone.** The rail stops at the server: token table, renderer, firebase
  Lambda. Coaching ships the first push client.
- **`exercise_sets.target` already holds what a set aimed for,** so half of §8 is done.
- **A skip's reason isn't refused today.** `skips.reason` stores `sick` and `sore` in clear, and
  `/me/programs/:id/history` and MCP serve them. Neither the health doc nor `site/privacy.html`
  mentions skips, so the promise §2 cites doesn't cover them. Keeping the reason from a coach is a read
  filter here, not a storage rule. What the server refuses outright is the go-easy list and health
  readings.

## Connections

The table is the base of everything, and it needs four changes.

1. **A real id.** `connections` has a composite key and a viewer-relative wire id, so nothing can
   point at it. It gains a `uuid`, sent as a new `connectionId`. `Connection.id` stays as it is.
2. **A history.** An append-only `connection_events` (connection, status, by whom, when) records every
   move. It closes gap 2 in `docs/2026-08-02.connections.md`, and pause windows and block history are
   both read from it.
3. **A block is per pair.** Status is per domain, so today a block in `fitness` leaves `running` open.
   A `blocks` table (blocker, blocked, created, lifted) applies across domains and survives being
   lifted. Setting status `blocked` writes it, and the invite, message, comment and read paths check it.
4. **Ending keeps the row.** `DELETE` becomes `severed` for any connection, because threads and "this
   person was a client" have to outlive it. A hard delete only happens with the account.

Also:
- `accepted_at` and `shares` go on the row. `shares` is a list of what the student chose to open,
  empty by default: `history` (workouts before acceptance) and `goals`, in a vocabulary that can grow.
  The student sets it when accepting and can change it at any time, and only the student can.
- **Coach connections come only from an invitation.** `POST /connections` keeps working for `PEER` and
  refuses `COACH` and `STUDENT`, so the scope can't be bypassed.
- **A paused connection resumes only by the student,** for coach connections. Today either side can.

## Peers stay

There's no peer UX, and the groundwork keeps the role alive rather than building around coaches:
- Roles stay as they are, and a peer reads what a peer reads today, photos included.
- Threads, blocks, reports, invitations and push settings belong to the connection or the person. No
  general table has a `coach_id`. An invitation carries a `role`, and only `COACH` is offered at first.
- Coach-only things are the ones that make no sense otherwise: the library, the roster, the feed,
  shared editing, logging for someone.
- Hiding a workout hides it from every connection, peers too.
- `(initiator, target, domain)` is the key, so a pair can't be both coach/student and peers in one
  domain. They can across domains (`fitness` and `general`), with a thread each. That's enough for now.

## Who can read what

Four copies of the `_auth` CTE become one SQL function, and the role decides the scope in one place.
The only per-connection input is the student's `shares`.

| Coach reads | How |
|---|---|
| Workouts | From `accepted_at` (or all, with `history` shared), not hidden, not started in a pause window, without images |
| Skips | `at`, `templateId` and `programId` only. No `reason`, no `weather` |
| Program copy and position | Through a coach's read of that program |
| Goals | Only with `goals` shared, and only workout metrics: if a health-backed metric ever exists, a coach doesn't read it |
| Name, photo | What the roster and the ask show; never an email |

`workouts.hidden_at` is the hiding. A full replace without the key keeps it, so an old build can't
unhide anything, and only the owner ever sees it.

## Invitations

`invitations` holds the inviter, role, domain, a hash of the token, the name the coach wrote, an
optional library program, `expires_at`, `canceled_at`, and `max_uses` (1 for now). What happened goes
in `invitation_responses` (user, accepted or declined, when), so a link that many people can ask
through later needs no new shape.

- `GET /invitations/:token` is signed out and returns the coach's name and photo and whether the link
  is good. Nothing else.
- Opening uses nothing up, and accepting is one transaction: connection, event, `shares`,
  program copy, `extra.features` for "Your coach".
- Resending renews the token and the expiry. Cancelling is a timestamp.
- Limits: pending invitations per coach, and a rolling count of declines. `400 invitation_limit`. A
  busy coach has many accepted, and an abusive one has many declined.
- The page at heart-of.me is a signed-out read and a way into the app or store. The API doesn't care
  who calls it, so accepting on the web can follow without changing it.
- The coach's key fingerprint rides in the part of the link that never reaches a server, so nothing
  here touches it.

## Pushes and their settings

Push types will multiply, so a new one must cost a catalog entry, with no migration and no app release.

**The catalog** lives in code, one entry per topic: key (`coaching.message`,
`coaching.workout_digest`), group, default delivery, visible or silent, Android channel, collapse key
and localized copy, including the name and description a settings screen shows.

**The preferences** are sparse. `push_preferences (user_id, topic, connection_id NULL, delivery)` has
a row only for what someone changed. The most specific answer wins: this person and topic, then the
topic, then the catalog's default. `delivery` is an open vocabulary, `instant`, `daily`, `off` for
now, read tolerantly.

**`GET /push/settings`** returns the whole catalog, localized, with each topic's resolved delivery.
The app draws its screen from the answer, so a build that has never heard of a topic can still show
and change it. `PUT` writes one answer. They don't live in `extra.features`, because the sender has
to query them.

**One send path.** `notify(userId, topic, args, connectionId)` resolves delivery, groups tokens by
locale, renders and publishes. Comments move onto it. New topics have no body and no content
arguments: title and ids only, so "Alex messaged you" is what's possible and a test holds it there.
Comment pushes keep their body, since no build receives them yet, and that's worth fixing when they
get a client.

**Daily delivery** queues rows and an hourly job sends them. It reaches Firebase, so it's an AWS
schedule, not pg_cron. The server knows no zones, so `POST /devices` takes an optional UTC offset,
and a digest goes out at an evening hour local to the device.

**The firebase Lambda** gains silent pushes, channel, thread and collapse fields, and the stale token
cleanup its TODO has been waiting for. Silent pushes are what heart-api#40 needs, so that ticket sits
on this rail rather than building its own.

## Messages

`threads`: `id`, `connection_id`, and the two people, each nullable. `thread_items`: `id` (v7, from the
device, idempotent), `thread_id`, `sender_id`, `kind`, optional
`subject_type` and `subject_id`, `content`, `commitment`, `tag`, `tag_key`, `at` (the device's),
`created_at`. A read position per person gives unread counts. Access is by person, not device: every
device of both people reads the same stored copy.

- `content` is a string of at most 16 KB, never an object. The server doesn't parse it, index it or log
  it. `Request.json()` checks keys and ciphertext has none, so it passes without an exception.
- Paged reads in both directions and "since a point". A connection that has ended stays readable and
  takes no new items.
- A blocked party can't fetch it, the blocker can, and each device keeps its own copy.

**Either person can delete the conversation, for both sides.** One call, whatever the connection's
status, and no agreement from the other side.

- The server removes the thread's items at once and records who and when in `connection_events`. The
  thread itself stays and can take new messages if the connection is live.
- `threads.cleared_at` is how every device learns: a device that sees it newer than its own copy drops
  what it holds. A modified client could keep its copy, and the server can't prevent that.
- **The other person gets a short window.** Otherwise deleting a conversation would destroy the
  evidence before a report. The app shows who deleted it and keeps its copy for 7 days, for reporting
  only, and then drops it. Nothing is back on the server in that time. A report carries its own words
  and tag, so the check still works.
- A filed report isn't touched by a deletion.
- It's the whole conversation, not one message.

**Deleting an account leaves the conversation with the other person.** `threads` and `thread_items`
don't hang off `connections` or `profiles` by cascade: the deleted person's side and `sender_id` go
null, and their keys and devices go, while the other person can still read the ciphertext they hold
keys for. The thread goes when both sides are gone. Anyone who wants their words gone deletes the
conversation first, and the account deletion screen and `site/privacy.html` have to say that.

**A message can be about any detail of a workout.** `subject_type` and `subject_id` take what comments
already target (`workout`, `workout_exercise`, `exercise_set`, `workout_image`) plus `skip`, `program`
and `session`, in a vocabulary that can grow. So "that third set" is a message in the one inbox, and
`?subject=` finds what was said about it without a device fetching the whole thread.

- The request puts the reference inside the content. It sits beside it here, because a new tablet
  couldn't otherwise show a set's conversation. The server learns which set is being talked about,
  which it already holds in clear, and never what's said.
- It's a link without a foreign key, unlike `comments`, which cascade. A deleted set leaves the message
  standing, and a subject opens nothing: a message about a workout later hidden stays, and the workout
  stays hidden.
- The `comments` table and routes stay as they are. They have no client, and the thread is the inbox.
- Reactions, later (#369), fit the same shape: a `reaction` kind whose subject is a message or a detail,
  sealed like the rest and left out of unread counts.

**`kind` is how things the server refuses today can arrive later.** With encryption working, a
student's device can seal something for their coach with the thread's key: a skip's reason
(`kind: skip_reason`, `subject: skip`), a go-easy area, in time a reading they chose to share. The
server stores a string it can't read, so neither the table nor the route changes. `kind` is an
allowlist in code: the first version accepts `message`, and each new kind is a deliberate one-line
change.

Two limits on that, stated plainly:
- **Sealing doesn't lift the health rule.** `CLAUDE.md`, the health doc and `site/privacy.html` have to
  change first, and that's an explicit policy decision. Until then the allowlist stays at `message`.
- **The server can't check that a string is ciphertext.** The client is the only guard on that, which
  is why the allowlist stays narrow and the app's tests hold the sealing.

## Media, later

Text only is the first version's limit, not the design's. Images and video on sets, exercises,
workouts and messages are coming, and nothing here gets in their way. None of it is built now.

- **In a thread:** the device encrypts the file with its own key and uploads it. That key and the
  file's hash travel inside the message, so the commitment covers them. The server holds a blob and its
  size. `content` has room at 16 KB, and a child table keyed by `thread_items.id` is additive. There
  are no server thumbnails or transcoding, because the server can't open the file.
- **On your own log:** `workout_images` generalizes to a media row with the same subject vocabulary, in
  clear like photos today. A coach doesn't read those (§2) unless `shares` grows a value for it. A form
  check is the thread's kind: a video in a message about that set.
- **Reports** will have to carry a file as well as words.
- **Storage and video limits** need sizing before they ship (#367).

## Encryption

The server hands out public keys and carries sealed items. It never holds anything that opens them.

**Devices.** `crypto_devices`: owner, two public keys, a fallback key, an optional signature from
another device of the owner's, `created_at`, `removed_at`. They're apart from `device_tokens`, since
a push token rotates and a key identity mustn't.

**Single-use keys.** `one_time_keys` holds up to 50 per device. Claiming one deletes it in the same
statement, with `FOR UPDATE SKIP LOCKED`, so none is handed out twice, and the fallback answers once
they run out. A device can read its own count.

**Who can fetch.** Your own devices, and the other side of an active connection. Without that gate
key fetching would be a way to probe who has an account, and to drain someone's single-use keys, so
it's also rate-limited.

**A new or removed device** is listed with whether it was vouched for, and a silent push tells the
other side's app to look.

**Key delivery.** `device_queue`: `seq` (bigserial, because order is firm and v7 ids from two Lambdas
can tie), recipient device, sender device, `kind`, `content` under 1 KB, `confirmed_at`. A device
reads what's unconfirmed, oldest first, and confirms. It doesn't page by a cursor, so a row committed
late can't be skipped. Confirmed rows go, and a pg_cron job removes unconfirmed ones after 90 days.
Asking again for a missing key is the same route with its own `kind`. A block stops items between the
two people.

**Commitments and tags.** The sender gives a 32-byte `commitment` with each message, required from the
start, so every message can be reported. The server signs commitment, sender, recipient and time with
a key from Secrets Manager, and stores the tag and the key's id, so the key can rotate. The scheme is
our own work on a published idea and needs a qualified review before release, as the app's design
says.

**Notes.** `coach_notes`: coach, connection (nullable, so a client's account going doesn't remove them),
`content` under the same contract, `updated_at`. Only that
coach reads or writes them, on any of their devices, and the client never learns they exist. They stay
when a client leaves, until the coach deletes them or the coach's account goes.

## A coach's library

Library programs are **documents, not rows in `programs` and `templates`.** `library_programs` (coach,
name, current version) and `library_program_versions` (version, body as JSONB, in the shape of a
`POST /programs` body).

Filtering library rows out of `templates` would mean touching every list, export, `/me` query, MCP
tool, summary and limit, and one miss shows a coach's work among their training, including on an old
build. A separate table can't leak that way.

**Sending** makes the copy on the server, because the student may be offline, using the existing
`_shareTemplates` matching of custom exercises to the student's own. `rules` is keyed by exercise id,
so its keys have to be remapped too. The copy's `programs` row gains `coach_id`, `library_program_id`
and `library_version`, which also answers "who holds which version". Sessions carry `assigned_by` as
today, so `quotedFrom` keeps working.

**Bases** stay the device's job, as when starting from the library: the copy arrives without them and
the student's app proposes them from their history. A new program that would replace another waits
for a start date from the student (§6).

**Bringing a copy up to date** replaces its sessions, as a change in the history, so it can be put
back. It overwrites the student's own edits to that copy; the app should say so.

## Two people, one copy

Only a managed copy (`coach_id` set) pays for any of this. Personal programs are untouched.

- `programs.revision` goes up with every change to the program or its sessions.
- `program_changes`: revision, actor, when, kind, `before` and `after` as JSONB snapshots of the
  session or program. Snapshots outlive what they describe, so it survives edits and deletes. Written
  in the same statement as the change, on every write path (app, coach, upsync, MCP).
- Writes take an optional `baseRevision`. If it's out of date: `409 program_changed` with the current
  revision. This includes queued offline writes, which replay with the revision they were based on.
- **An old build sends no `baseRevision` and can't handle a 409.** Its write is accepted and recorded
  with `stale: true`. The coach's version sits in `before`, and putting it back is one action. So the
  old build can overwrite, and nothing is lost, which is what the request asks.
- `GET /programs/:id/changes?since=` answers "what changed", and a silent push says that something did.
- Coach writes go under `/accounts/:targetUserId/programs/…`, gated on an active coach connection, so
  access ends with the connection.
- Putting a change back is a new change.

**Target beside done.** Sets gain an optional `source_set_id` and the workout a `plan_revision`, both
links rather than requirements. What was asked is the snapshot at that revision, so it survives later
edits. Asked-for sets with no tied set are what wasn't done. Sets without a tie were added, and old
workouts simply have none. `exercise_sets.target` stays as it is.

## Roster and feed

Position is a Dart fold over a program's history, so a read-time roster of a thousand clients would
run a thousand folds. **`client_summaries`** holds one row per connection: program name and position,
recent training times, last trained, and reasons. Workout, skip, action and program events update it
through the queue, and a daily pg_cron job adds gaps and endings. The roster is a keyset page over it,
sorted by need or filtered by reason. It may lag a little, and the app is offline-first anyway.

- Recent training is sent as times, not a seven-day mask. The app has the coach's zone and the server
  doesn't.
- **Reasons need an end, and the request doesn't give one.** A "new note" that never clears isn't a
  signal. Each connection keeps a `reviewed_at` for its coach, moved by a new call, and reasons count
  only what came after it. Gaps and endings clear when they stop being true.
- The feed reads workouts and skips of the coach's clients through the read policy, plus endings from
  the summaries, newest first. The daily push draws on the same rows.

## Logging for someone, and reports

**Logging:** `POST /accounts/:targetUserId/workouts` writes the student's workout with `logged_by`, on
an active coach connection. It's never public and the student can delete it.

**Block** is in the first version, since most of it is the groundwork above.

**Reports** are in as intake only. `POST /reports` stores the reporter, the person, the connection, a
reason, the words the device sends and what's needed to check them, and alerts the owner, who reads
them with a query. The server checks the words against the stored tag and records the answer. Those
words are the one place a message exists in clear, so reports are deleted once closed. Apple 1.2 and
Google's equivalent ask for a way to report, a timely response, a way to block and a contact
route, and `site/support.html` is the contact route. None of that requires a review app, which is what
moves out.

**Before any of this ships:** `site/privacy.html` changes, since it says "don't share", and it and
the health doc say that notes and threads are the first health-shaped things with a remote copy, even
if unreadable. `CLAUDE.md` gets the same line: ciphertext only the two people can open.

## Beta, then release

The rollout has two stages. The beta goes out free to people who test it with the owner, and release
comes after. Payment isn't part of the beta, and nothing here builds for it.

**Who can coach in the beta.** The request has anyone able to coach, with no approval. In the beta,
only an account holding the `coach` entitlement can create an invitation (`403 coaching_beta`
otherwise), and the owner grants it by hand. It's the first row of the entitlement model
`docs/2026-09-23.developer-api.md` calls for: a small `entitlements (user_id, entitlement, granted_at)`,
and the profile says whether the account holds it so the app can show "Coach people". Students aren't
gated: anyone with a link can accept.

**Limits in the beta are guards, not promises.** They protect the database from abuse and nobody is
expected to reach them: 1000 clients per coach, 50 pending invitations, 100 library programs, 60
messages a minute per sender. Real limits are set for release.

**Keep what release will need.** Connection rows and their events survive ending, so how many students
a coach had, and when, can always be counted.

## Compatibility

Additive: every new table, route and optional field, and new `heart_models` members in a minor
version. Old builds keep what they don't know, under the rules templates and workouts already follow.

These tighten or re-mean a contract, and have no installed caller at v1.13.0 or since:
- a coach's reads narrow
- `POST /connections` refuses `COACH` and `STUDENT`
- `DELETE /connections/:id` keeps the row
- only the student resumes a paused coach connection

They still need classifying in the release note, and `heart_models` signatures stay as they are.

Health rule: no route takes a health-shaped field, and `Request.json()` and `health_rule.sql` keep
applying everywhere. `thread_items.content` and `coach_notes.content` are ciphertext strings.

## Open

- Limits and pricing for release.

## A coach isn't a second holder of the data

The design treats a coach as someone a student shows things to, not as a separate keeper of them.
Everything a coach reads ends with the connection, and either person can delete the conversation for
both. The app drops what it cached of a former client's workouts and program. Notes are the coach's
own writing, and the server can't read them.

## Decided against

**Age checks.** Heart doesn't ask for an age, estimate one or infer one, so nothing in the schema or the
API branches on it. Coaching changes nothing here. `site/privacy.html` keeps its existing line about
children and its contact route.
