# A developer API: personal access tokens and a read surface

Status: **mostly built.** On `main`: personal access tokens with both rate-limit windows and usage
logging (heart-api#111), the `/me` reads and the Strong-format export, the change feed and personal
records, exercise history and library search, and the MCP server, also on its own host. OAuth has
its own doc (`2026-10-04.oauth.md`), as does MCP (`2026-10-04.mcp.md`). In review: the stage-wide
throttle (heart-api#132) and the public docs page (#137). Still proposals: writes, and what premium
bundles. The app side of tokens is heart-of-yours#271.

This is the base layer of Heart's AI story, which is deliberately not an AI product: people work
with AI however they like, and Heart's job is to make their log reachable by machines and easy to
take elsewhere. No coach, no in-app model, no inference bill. A personal script, a spreadsheet, an
MCP host and a ChatGPT app all stand on this surface.

## Why now

r/strongapp is asking for a user-facing API, and the mood there is that Strong has been abandoned.
People who are annoyed with an app, own years of training history and want to script against it
are the easiest users to win over, and there is a window while they are still looking.

Where things stand:

|                    | Strong | Hevy                                      | Heart                                                                 |
|--------------------|--------|-------------------------------------------|-----------------------------------------------------------------------|
| Public API         | none   | yes, Pro only                             | — (this doc)                                                          |
| Price of access    | —      | Pro: $2.99/mo, $23.99/yr, $74.99 lifetime | free for everyone; higher volume with the `api` entitlement           |
| Getting history in | —      | —                                         | `POST /workouts/imports?source=strong` + the app's import screen      |
| AI assistants      | none   | official ChatGPT app; community MCP       | `2026-10-04.mcp.md`                                                   |

Hevy's API (`api.hevyapp.com/docs`) is the real competitor. It is Pro-only, keyed from
`hevy.com/settings?developer`, and covers workouts, routines, routine folders and exercise
templates, both read and write. The community built on it — MCP servers for AI assistants, a
Home Assistant integration, Python clients — shows what people actually want: **their log,
readable by their own tools, especially AI tools.**

Heart already has the part that brings people over, the Strong CSV import, which lands a user's
whole history on day one. The API is what makes staying worthwhile.

### Pricing

**Access is free; volume can be paid.** Reading your own log, exporting it and connecting an
assistant to it are part of "your data is yours", so none of it sits behind a paywall. Hevy's API
is Pro-only; Heart's is not. What premium can sell is *volume*: a higher rate limit, and later
conveniences that scale with server cost (webhooks, write volume). It's one entitlement among the
things that make premium worth buying, priced under Hevy. Heart's costs are infrastructure only
(no salaries), so a price that covers the bill is a small one.

**Free stays free, limits included.** Once a free limit ships it never shrinks. That makes the
free limit a permanent number, sized against the worst case before launch, not tuned afterwards.
See *Sizing the free limit*.

Later, the bundle should come apart into **flexible tiers: pick what you need.** That shapes
the design even now. Access should be modelled as a set of **entitlements** on the account
(`api`, `watch`, `social`, …), not a single `free < pro` ladder. Then a bundle is just a named
set of entitlements, and splitting it up later needs no migration. The entitlement model, and
what grants one (store subscriptions and their webhooks), belong to the premium tier's own
design, not this one. This API only reads it: does the account hold `api`?

Any premium feature built on health data (watch apps especially) is still bound by the
device-only rule. The server can know an account is *entitled* to a feature. It never holds the
feature's health data.

## Goals and non-goals

**Goals**

- A user can mint a token in the app and read their own workouts, templates, folders, goals and
  custom exercises from a script, a spreadsheet or an AI assistant.
- A user can take their whole history out in a format another app imports, from day one.
- One surface under every machine consumer: tokens here, OAuth clients and the MCP server on top.
- A surface that stays stable on its own terms, not one that moves whenever the app does.
- Revocable, auditable, rate-limited access that can't hurt the app's own traffic.

**Non-goals (for now)**

- Writes. See *Phase 4*.
- Third-party apps acting for a user (OAuth, client registration, consent screens). A token is
  the user acting as themselves; delegated access is `2026-10-04.oauth.md`, which reuses this
  surface, its middleware and its rate limit.
- Anything health-shaped, ever. See *The health rule*.

## The surface

A namespace in the existing route table, under the existing base path:

```
https://api.heart-of.me/v1/me/workouts
                        │  │
                        │  └── route prefix; middleware is wired per prefix, like every DI binding
                        └───── the existing base path mapping onto stage v1
```

**Why a prefix and not the app's own routes.** The app's routes are shaped for the Flutter
client: they carry the app-version gate, they take writes with replay semantics
(`2026-09-05.upsync-replay.md`), and style says "client and server ship together, no shims".
Published routes can't change freely. A separate prefix gets its own auth, its own rate limit and
its own compatibility rule, and the app's routes stay free to change.

**Why a prefix and not a second base path or hostname.** `AWS_LWA_REMOVE_BASE_PATH` is a single
string (`/v1`, `app/stacks/api/lambdas.tf`), and the route table is the one place paths live. A
second base path mapping means a second removal rule, or routes that know their hostname. A
prefix costs nothing and keeps one Lambda and one route table. A `developer.` hostname can be
added later as a CNAME on the same mapping if marketing wants one.

**Why `/me` and not `/public`.** "Public route" already means *unauthenticated* in this codebase
(`_publicRoutes`, `isPublicRoute` in `api/lib/routes/index.dart`). Using it for "the
token-authenticated surface" would make every middleware conversation ambiguous.

### Compatibility rule

The same rule as `shared/heart_models`: **additive only.** New fields and new routes are fine.
Removing or renaming anything needs a new prefix (`/me2`, or a real `v2` base path at that point)
and a deprecation window announced in the docs. Response shapes reuse `heart_models`
serialization wherever the app's wire shape is already right (`Workout.toMap` embeds the
exercise, which is what a script wants). They inherit that package's additive-only discipline,
which is the rule this surface needs anyway. Anything that should *not* leak (image storage keys,
replay-only fields) gets a `Me*` view model in `heart_models`, per "shapes live in exactly one
place".

### Endpoints, phase 1

All `GET`, all caller-scoped. There is no `:targetUserId`: coaches and connections are the
app's business, not a token's.

| Route | Returns |
|---|---|
| `/me` | id, username, unit system: what a script needs to label its output |
| `/me/workouts?limit&cursor` | `Paginated<Workout>`, newest first, keyset on `id` per style |
| `/me/workouts/:workoutId` | one workout with exercises and sets |
| `/me/exercises` | the account's custom exercises; catalog exercises are embedded in workouts by key, name and id, so no second lookup is needed |
| `/me/templates`, `/me/template-folders` | as the app lists them |
| `/me/goals` | definitions (see *The health rule*) |
| `/me/export?format=strong` | the whole account as a Strong-format CSV, the same shape `?source=strong` imports |

Pagination is `Paginated<T>` exactly as style describes (`limit + 1`, cursor = last `id`). No
bare `cursor` field, no offset.

**Export is phase 1, not an afterthought.** Machine access and easy export are the two halves of
the same promise, and export is the half that needs no client at all. The Strong-format export
is a deliberately generous move: "we export in Strong's format, so you can leave us too." It costs
little (the import parser's inverse) and makes the no-lock-in claim something people can check.
The app already exports JSON and CSV on device (heart-of-yours#95); this route serves scripts and
any signed-in user away from the phone. Two things to settle in the implementation:

- **Size.** Years of history can pass the 6 MB Lambda response limit. Past a threshold the route
  answers `303` to a short-lived presigned S3 URL of the generated file instead of the body.
- **Formats.** `strong` first. `format` is an enum so `json` (the `/me/workouts` shape, unpaged)
  and other apps' formats can follow without a new route.

### Endpoints, phase 2

| Route                                 | Why                                                                                                               |
|---------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| `/me/workouts/changes?since=<opaque>` | Incremental sync for Sheets, Home Assistant and anything that polls. Returns upserts and deletions since a point. |
| `/me/records`                         | Personal records per exercise, computed from sets. The first question every AI assistant asks.                    |

`changes` needs schema work. `workouts` has no `updated_at` today, and edits come through
`PUT`/`PATCH` on the workout *and* its child rows. A migration adds `workouts.updated_at` with
triggers on `workouts`, `workout_exercises` and `exercise_sets` that bump the parent.
Deletions already have tombstones: `archive.deleted_workouts` has `(user_id, deleted_at)`
indexed. The cursor is `(updated_at, id)`, opaque to callers. This is the one justified exception
to "cursor is the last item's id", and the doc that ships it should say so.

As built (heart-api#114): the position is the **transaction** that made each change
(`workouts.changed_xid`, `archive.deleted_workouts.deleted_xid`, both `xid8`), not `updated_at`. A
time stamp is a transaction's start, so a long save could commit behind a cursor already handed out.
The feed reads only changes from transactions older than the oldest one still running (the
snapshot's `xmin`), all of them finished, so nothing can. The cursor is `(transaction id, id)`,
still opaque. `updated_at` stays, as the time.

**Moving the database** (Supabase to RDS, or any dump and restore onto a new cluster): transaction
ids belong to one cluster, and a new one starts its counter lower. The feed refuses a cursor at or
past the counter (`400 stale_cursor`, and clients start over), which catches every poller that comes
back before the new counter climbs past its cursor. To close the rest, re-stamp everything once,
right after the restore and before the API takes traffic, so every workout and deletion reappears
for everyone:

```sql
BEGIN;
-- the row trigger would also reset every updated_at to today; this is a move, not an edit
ALTER TABLE workouts DISABLE TRIGGER workouts_stamp;
UPDATE workouts SET changed_xid = pg_current_xact_id();
ALTER TABLE workouts ENABLE TRIGGER workouts_stamp;
UPDATE archive.deleted_workouts SET deleted_xid = pg_current_xact_id();
COMMIT;
```

An in-place major upgrade (`pg_upgrade`) keeps the counter and needs nothing.


## Personal access tokens

### Shape

```
hrt_2Qx9…43 more base64url chars…
└┬┘
 └── fixed prefix: greppable, and eligible for GitHub secret scanning later
```

32 random bytes, base64url. The server stores **only `sha256(token)`**. The input has 256 bits
of entropy, so a slow hash buys nothing, and a plain digest keeps lookup a single indexed
equality. The plaintext is shown once, at creation.

### Table

```sql
CREATE TABLE IF NOT EXISTS api_tokens
(
    id           UUID        DEFAULT uuidv7() PRIMARY KEY,
    user_id      TEXT        NOT NULL REFERENCES profiles (id) ON DELETE CASCADE,
    name         TEXT        NOT NULL,          -- "Home Assistant", "my sheet"
    purpose      TEXT,                          -- optional, picked at creation; see *Knowing who calls*
    token_hash   BYTEA       NOT NULL UNIQUE,
    hint         TEXT        NOT NULL,          -- last 4 chars, for the list UI
    scopes       TEXT[]      NOT NULL DEFAULT '{read}',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_used_at TIMESTAMPTZ,
    expires_at   TIMESTAMPTZ,                   -- null = until revoked
    revoked_at   TIMESTAMPTZ
);
```

`ON DELETE CASCADE` from `profiles` means account deletion revokes everything with no extra step.
`scopes` exists from day one so that adding `write` later needs no migration and no reissue.
Revoked rows are kept, not deleted, so the list UI can show "revoked on …" and support can
answer "what touched my account".

### Management routes (Firebase-authenticated, app-facing)

| Route | |
|---|---|
| `POST /accounts/tokens` | `{name, expiry, purpose?}` → the token *with* its plaintext, once. `400 token_limit` past 5 active tokens, like `goal_limit`. |
| `GET /accounts/tokens` | list, never the plaintext |
| `DELETE /accounts/tokens/:tokenId` | revoke; takes effect on the next request |

`expiry` is `"year"` or `"never"`. The server turns it into `expires_at`. An enum rather than a
timestamp, so the choices can grow (90 days, custom) without the app computing dates. The
column already takes any timestamp.

These sit under `/accounts` and use the ordinary Firebase middleware, so anonymous accounts
already can't reach them (`anonymous_account` 403, `2026-09-05.anonymous-accounts.md`). The app
needs a settings screen (name, create, copy once, list, revoke), which means a frontend ticket via
the `handoff` skill and new `ApiToken` models in `heart_models` (minor bump).

### Middleware

`/me` swaps the auth chain, it doesn't extend it:

- **Authentication.** A `tokenAuthentication` middleware wired with `..use('/me', …)`: one
  statement looks up by hash, checks `revoked_at`/`expires_at`, applies the rate limit, bumps
  `last_used_at`, and returns `user_id` (see *Rate limiting*). The Firebase `authentication`
  middleware must *skip* `/me`, so its `shouldAuthenticate` predicate learns the prefix. The
  current name, `isPublicRoute`, returns true for routes that *need* auth, which is already
  inverted from what it reads as. Rename it while touching it.
- **Firebase tokens on `/me`.** Not accepted. One credential type per surface keeps the 401s
  unambiguous and stops the app from quietly coming to depend on `/me`.
- **Version gate.** `version()` would reject every script, since nothing but the app sends an app
  version. `shouldCheckVersion` excludes `/me`.
- **CORS.** None for `/me` in phase 1. The consumers are scripts, servers and MCP hosts, and a
  token pasted into a web page is a leak waiting to happen. Revisit if a browser use case turns up.
- **Errors.** `401` with `code: invalid_token` for unknown, revoked and expired alike: the caller
  can't act on the difference, and telling them apart leaks which tokens once existed. `403`
  `insufficient_scope` when phase 4 arrives.

## Rate limiting

Scripts poll, and a `* * * * *` cron in someone's Home Assistant shouldn't set the Lambda and
Postgres bill.

**Per account, by entitlement, in the auth statement.** The limit is per account, not per
credential. Otherwise five free tokens, or a token plus three connected assistants, get five
times the free quota. OAuth access tokens (`2026-10-04.oauth.md`) count against the same row.
The counter lives in its own row, and the table holds counting only, never entitlements.

Two windows: a **minute** window that shapes bursts, and a **day** window that bounds cost. The
minute window alone can't bound cost: a free account held at its per-minute ceiling around the
clock is a monthly bill, multiplied by every account that does it.

```sql
CREATE TABLE IF NOT EXISTS api_usage
(
    user_id      TEXT PRIMARY KEY REFERENCES profiles (id) ON DELETE CASCADE,
    minute_start TIMESTAMPTZ,
    minute_count INTEGER NOT NULL DEFAULT 0,
    day_start    TIMESTAMPTZ,
    day_count    INTEGER NOT NULL DEFAULT 0
);
```

The token lookup already has to hit Postgres, so the counters ride on the same round trip. Fixed
windows, each restarting when it has run out:

```sql
WITH _token AS (
    UPDATE api_tokens
    SET last_used_at = now()
    WHERE token_hash = @token_hash
      AND revoked_at IS NULL
      AND (expires_at IS NULL OR expires_at > now())
    RETURNING user_id, scopes
), _usage AS (
    INSERT INTO api_usage (user_id, minute_start, minute_count, day_start, day_count)
    SELECT user_id, now(), 1, now(), 1 FROM _token
    ON CONFLICT (user_id) DO UPDATE
    SET minute_start = CASE WHEN api_usage.minute_start > now() - interval '1 minute'
                            THEN api_usage.minute_start ELSE now() END,
        minute_count = CASE WHEN api_usage.minute_start > now() - interval '1 minute'
                            THEN api_usage.minute_count + 1 ELSE 1 END,
        day_start    = CASE WHEN api_usage.day_start > now() - interval '1 day'
                            THEN api_usage.day_start ELSE now() END,
        day_count    = CASE WHEN api_usage.day_start > now() - interval '1 day'
                            THEN api_usage.day_count + 1 ELSE 1 END
    RETURNING user_id, minute_start, minute_count, day_start, day_count
)
SELECT user_id, scopes, minute_start, minute_count, day_start, day_count
FROM _token JOIN _usage USING (user_id);
```

Once entitlements exist, the statement joins them in as one more CTE (still one round trip)
and returns whether the account holds `api`. Until then every account gets the free limit.
Limits live in config, not in a table, so changing them is a deploy, not a migration; *raising*
the free one is always allowed, lowering it never is. Over either limit returns `429`,
`code: rate_limited`, with `Retry-After` set to the end of whichever window ran out.

One write per request is fine at this scale. If it stops being fine, the counter moves to a
cache, not the design.

### Sizing the free limit

The free limit is permanent the day it ships (see *Pricing*), so it is sized against the worst
case, not the average.

**What real use needs.**

| Consumer                                | Shape                                                    | Requests             |
|-----------------------------------------|----------------------------------------------------------|----------------------|
| An assistant answering one question     | `me`, a page or two of workouts, `records`               | 3–8 in a few seconds |
| An assistant on a busy day              | a dozen questions                                        | ~100/day             |
| Home Assistant polling `changes`        | every 5 minutes                                          | 288/day              |
| A nightly sheet sync                    | one `changes` page, sometimes two                        | 1–2/day              |
| Pulling the whole history once          | 1,000 workouts at 100 a page, or one `export`            | 1–10, once           |

**What the worst case costs.** On the stack as it stands (REST API Gateway at about $3.50 per
million requests, a 512 MB arm64 Lambda at roughly $1 per million 150 ms invocations, the
database a fixed cost that cares about concurrency, not volume), a request costs about
**$5 per million**.

| Free limit                  | One account maxing it for a month | 1,000 accounts doing it |
|-----------------------------|-----------------------------------|-------------------------|
| 20/minute, no daily cap     | ~864k requests, ~$4.30            | ~$4,300                 |
| 20/minute and 2,000/day     | 60k requests, ~$0.30              | ~$300                   |
| 20/minute **and 200/day**   | 6k requests, ~$0.03               | ~$30                    |

**Proposal: free is 20/minute and 200/day; the `api` entitlement is 120/minute and
20,000/day.** 20/minute absorbs a multi-call assistant answer. 200/day covers a busy day of
questions, a nightly sync and a one-off history pull, which is personal use. It doesn't cover
polling around the clock, and that's deliberate: tight polling is automation, and automation is
what the entitlement is for. A poller on the free tier can check every 15 minutes (96/day) and
still have room for an assistant. The worst case stays at pennies per account. Free limits can
only ever go up, so starting low is the safe direction: raising it later is a gift, and lowering
it is never an option. `export` generates a file, so it gets its own allowance instead of the
general counter: one a day on free.

### Why not API Gateway API keys

Usage plans look like a fit: a plan per tier, throttle and quota per key, and over-limit requests
are turned away *before* Lambda runs. That last point is a real advantage. It loses on the rest:

- **Keys aren't authentication.** AWS says not to use them for auth, so the hashed token lookup
  stays either way. That makes two stores to keep in step on every create, revoke and entitlement
  change, with a failure window between the database write and the API Gateway call.
- **The secret moves into AWS.** An API key's value can be read back in plaintext by anything
  with `apigateway:GET`. The hash-only property goes. Keeping the `hrt_` token and mapping it to
  a key needs a Lambda authorizer (`apiKeySource = AUTHORIZER`), which adds a second invocation
  per request, cacheable but still a moving part.
- **It changes the gateway's shape.** `api_key_required` is per method, and today there is one
  `{proxy+}` resource serving the app too. `/me` would need its own resource.
- **Enforcement is best effort.** AWS documents usage plan throttles and quotas as not hard
  limits, and usage plans and keys both have per-region quotas.

So: **internal.** The way back is open. If abuse ever shows up on the bill, an authorizer plus
usage plans can sit in front of the same tokens without reissuing any.

**Stage-wide backstop.** Checked live on 2026-09-23: in both accounts, `heart-api`'s `v1` stage
has no method settings. The only ceiling is the account default (10,000 rps, 5,000 burst), and
no usage plans or API keys exist. The throttled stage in the dev account belongs to `vault-api`
(200 rps, 100 burst), a different project. Add an `aws_api_gateway_method_settings` with
`method_path = "*/*"` and throttling limits, so a flood of *invalid* tokens, which never reaches
the per-account counter, still hits a ceiling before Lambda concurrency does. With a single
`{proxy+}` resource this can't be scoped to `/me` alone, so set it well above the app's real peak.
This is worth doing now, independent of `/me`.

Built in heart-api#110 (`var.throttle` and `var.api_concurrency` on the API stack), sized from
prod on 2026-10-06. The busiest minute in 14 days was 107 requests, and the API averages 149 ms an
invocation. Traffic doesn't set the limit; two other constraints do. Lambda concurrency started at
the new-account quota of 10, shared by all three functions (raised to 1,000 the same day). And
every API instance holds one database connection through Supabase's session pooler, whose pool is
15. Prod therefore reserves 12 executions for the API and 3 for the MCP function, which share the
pool, and leaves the other functions their share. The stage throttle sits under that, at 60 rps and
burst 12, so a
spike meets the gateway's 429 before Lambda's: a throttled function surfaces through API Gateway
as a 500. The gateway's 429 is in the API's own error shape (`code: throttled`) and carries
`Retry-After: 1`, like every error the gateway answers itself (`stacks/api/main.tf`,
`gateway_errors`). Dev
stays at the quota of 10, can't reserve (AWS keeps 10 unreserved), and keeps the default of 25 rps,
burst 50. Past that, Supabase's transaction pooler is the next step.

The changes feed exists partly for this reason: a poller asking "anything new?" should get an
empty page cheaply, not re-read the whole history.

## Knowing who calls

Who uses the API, and how much of it is AI, decides what gets built next. It's collected from
what callers already send. **Nothing is required**: a mandatory header lengthens the curl example,
turns first tries into `400`s, and is trivially faked by anyone determined, so it would only
inconvenience honest callers.

### Signals

| Surface                 | Signal                                                                                     | Reliability                        |
|-------------------------|--------------------------------------------------------------------------------------------|------------------------------------|
| `/mcp`                  | every call is an assistant, by definition; the handshake's `clientInfo` names the host and version | high                        |
| OAuth tokens            | the grant's `client_id`: a host's metadata URL, fetched and verified (`2026-10-04.oauth.md`) | highest; unforgeable short of owning the host's domain |
| Personal tokens         | the token's `purpose`, if the user picked one                                              | honest, since nothing depends on it |
| Any request             | `User-Agent`: defaults alone say a lot (`curl/`, `python-requests/`, `node`, Home Assistant's `aiohttp`) | medium; rarely faked |

- **`purpose`** is an optional picker on the token screen: *script*, *spreadsheet*,
  *home automation*, *AI assistant*, *other*. It's a closed enum validated at the boundary,
  stored as text so the list can grow.
- **The docs ask for a User-Agent** that names the tool, such as `my-sheet-sync/1.0`, in one line
  under the curl example, as a courtesy and not a rule.
- **The blind spot** is a third-party MCP server built on a personal token, which is how every Hevy
  integration works. It shows up as `python` or `node` unless its author sets a User-Agent or the
  user picked *AI assistant*. The official MCP server exists partly so that most AI traffic arrives
  labelled.

### Collection

**One structured log line per `/me`, `/mcp` and `/oauth` request**, emitted by the token middleware
after the response:

```jsonc
{ "surface": "me", "route": "/me/workouts", "status": 200,
  "credential": "pat",          // pat | oauth
  "client": null,               // OAuth client_id, or MCP clientInfo.name
  "purpose": "spreadsheet",     // personal tokens only
  "ua_family": "python-requests",
  "account": "<sha256 of user_id, truncated>" }
```

- The account is pseudonymised, which is enough to count distinct users without putting raw ids
  in logs.
- The raw User-Agent is reduced to a family by a small fixed table at log time.
- Reporting is CloudWatch Logs Insights over those lines: callers per week, the share of traffic
  that's AI, top clients, top routes. That's no new table and no extra write in the hot path. The
  rate-limit round trip stays exactly as it is.
- If a dashboard is wanted later, a scheduled query rolls the same lines up per day. The log line
  is the contract.

What it never records: request or response bodies, query values, or anything from a workout.

## The health rule

This surface is read-only over data the server already holds, and the server holds no health
data, so the API can't leak any. Specifically:

- `calories` on a workout is the MET **estimate**. The public docs say so in those words, so
  nobody mistakes it for a watch reading.
- `/me/goals` returns health-backed goals as **definitions only**: target, deadline, cadence. It
  has no progress field for those kinds, because the server never has one. The docs say why.
- **Inbound is the real risk, and it's a phase 4 problem.** Hevy users migrating over will expect
  to `POST` heart rate with a workout. Any write scope rejects health-shaped fields exactly as
  every app route does, and the API docs state the device-only promise up front. For the people
  in that subreddit, "we don't have your heart rate, by design" is part of the pitch.

## Privacy policy

`site/privacy.html` says "we … don't share it". A token is the user sharing their own data with a
tool they chose, which is consistent with that promise, but the policy should say so explicitly
before launch: tokens exist, the user creates and revokes them, and what they grant access to. It
also says that API use is logged per account (which tool, which route, how often; never the data
itself) to understand how the API is used. Update "Last updated" with it.

## Docs and the MCP server

- **Reference.** A published API needs a spec, and this runs into the unfinished OpenAPI
  question (`2026-08-02.connections.md`, *On generating an OpenAPI spec*). Routes and inputs are
  machine-readable. Responses aren't: handlers return `Model`, whose shape is whatever `toMap()`
  builds at runtime. That needs deciding for the whole API, not patched for `/me` alone: a way
  for handlers to declare input and output types that a generator can read. `/me` is a good
  first user of it, being small, read-only and additive-only, but it shouldn't get a hand-written
  spec that drifts from the code. The page itself (curl example first, health promise in the
  first paragraph) goes wherever that decision puts generated docs.
- **MCP and ChatGPT, phase 3.** No longer a stdio package that reads a token from an env var: that
  reaches developers only. Claude's connectors and ChatGPT's apps both need a remote MCP server
  behind OAuth, and one server can serve every host. That design is `2026-10-04.mcp.md`, on top
  of `2026-10-04.oauth.md`. Personal tokens still work there as a bearer credential for hosts
  that take one, so nothing built on phase 1 is wasted.

## Phase 4: writes (not now)

`write` scopes for scripts and assistants: "build me a 4-day upper/lower" as a template folder
first, then "log today's session". They're deferred because the app is local-first. A
server-side create has to reach the device's mirror and not collide with an in-flight replay.
The replay contract (client-minted v7 `id`, id-idempotent creates) is most of the answer, but
"the app learns about rows it didn't write" is a sync feature the app doesn't have yet. Don't
ship writes before that exists. Templates come before workouts: they're rarely edited on two
devices at once, so a conflict is unlikely and cheap. Scopes are split per resource
(`write:templates`, `write:workouts`) so a user can grant one without the other.

## Rollout

1. **Phase 1**: migration, token routes, `/me` read routes, Strong-format export, middleware,
   rate limit, stage backstop, docs page, privacy update. Frontend ticket for the token settings
   screen. The free limit is final at this step.
2. **Announce.** Not in r/strongapp: it bans self-promotion (tried). The message: import from
   Strong in one step, export back to Strong's format any time, the API, a curl example, the
   health promise. Lead with the import. The API is the reason to stay.
3. **Phase 2**: `changes`, `records`.
4. **Phase 3**: OAuth (`2026-10-04.oauth.md`), then the remote MCP server and the ChatGPT app
   (`2026-10-04.mcp.md`).
5. **Phase 4**: writes, templates first, once the app can pull rows it didn't create.

## Open questions

- **What premium bundles** at launch, and when it launches. Features still to be built. The
  entitlement model is that design's first decision.
- **`/me` versus a dedicated hostname** (`me.heart-of.me` was floated). Cosmetic; the prefix
  works either way.
- **OpenAPI.** Response-type declarations for the whole API, then where generated docs are
  published. Blocks the reference page, not the routes. MCP tool schemas want the same
  declarations, which raises the priority.
- **Announcement channel**, now that r/strongapp is out.
- **The free limit's final numbers.** *Sizing the free limit* proposes 20/minute and 200/day.
  Once phase 1 ships they can only go up.

## Decided

- **No paid API.** Reading, exporting and connecting are free for everyone, forever. Higher
  volume is one entitlement in a premium tier, priced under Hevy, that bundles other features.
  Flexible tiers later, so access is modelled as entitlements, not a ladder.
- **Free limits never shrink.** Whatever ships free stays free, limits included.
- **5 active tokens per account.** OAuth grants don't count against it; they share the rate
  limit instead.
- **Expiry:** one year or never, chosen at creation. Revisit later; the enum and the column both
  leave room.
- **Tokens and limits stay internal**, not API Gateway keys (see *Why not API Gateway API keys*).
