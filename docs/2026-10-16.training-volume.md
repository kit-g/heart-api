# Training volume and balance on the server

The last of the MCP server's first round (heart-api#116): "which muscles did I
skip?" and "weekly volume per muscle", as `/me` routes and tools together under
the parity rule. They count what the app's pattern lens counts
(`docs/2026-10-11.pattern-lens.md` in heart-of-yours), so an assistant and the
app's weekly card never disagree. Written from the code as it stands.

## No aggregation foundation

#116 had them waiting on heart-api#37 and #38 for a shared aggregation layer.
They don't need one: every request folds the window's working sets
(`getRecordSets`, the same read personal records use) against the caller's
exercise library, in memory. A year of training is a few thousand rows. Nothing
is stored or materialized, so nothing can go stale, and the app being
offline-first means no endpoint needs a precomputed answer.

## What a set counts toward

The unit is one exercise's completed working sets (warm-ups left out) in one
workout.

- **Muscle groups.** The ten groups the app's body map draws
  (`MuscleGroupKey` in `heart_models`). A library tag reaches a group by naming
  it (`legs`) or by naming a muscle in it (`pectoralis_major_l` is `chest`).
  Each group gets the role's share of a set (`docs/2026-10-12.muscle-shares.md`):
  all of it as primary, half as secondary unless content says otherwise. A
  group reached by both roles counts once, as primary. An exercise nobody
  tagged, one the user made, counts fully toward its target's group
  (`Target.muscleGroup`); a target with no group (cardio, full body) places
  nothing.
- **Movement patterns.** All of a set for each pattern on the exercise:
  `movement.groups` for library exercises, the pattern the user gave their own
  (heart-api#269).
- **Sessions.** A key counts a workout once, however many of its exercises
  reached it.
- **Unplaced sets.** Sets neither key can place, reported per week so a total
  doesn't quietly undercount.
- **Direct work.** Each muscle group's `primarySets`: the part of its sets from
  exercises that work it first (`MuscleTagging.primaryGroups`), an untagged
  exercise's target group included. The rest is indirect.

Each week also carries its totals: the finished workouts started in it, their
time less pauses, and `totalVolume`, the working sets' weight times reps in kg.
Assisted bodyweight adds nothing, since its weight is help, not load. The
workouts come from a read of their own (`getWorkoutSpans`), so a session with
no working sets still counts.

The muscle-to-group map lives in `heart_models`, so the app can read it too.
`MuscleTagging.shareOf` matches groups the same way: before this,
`shareOf('chest')` was 0 for a barbell bench, which tags only
`pectoralis_major`. A test holds the map to the content schema's muscle list,
so a muscle the library adds can't go uncounted.

## Weeks

UTC weeks starting on the user's `firstWeekday` from the profile's settings
(`Settings.firstWeekday`, ISO 1–7), or Monday while the app hasn't sent it.
Every response says which day it used (`weekStart`). Without `from`, the window
is the 4 weeks ending with the current one, as the app's balance view reads; a
window is at most a year (`LensWindow.longest`).

## Routes and tools

| Route         | Tool                  | Returns                                                                                                                  |
|---------------|-----------------------|--------------------------------------------------------------------------------------------------------------------------|
| `/me/volume`  | `get_training_volume` | per week: `workouts`, `duration`, `totalVolume`, `muscles` and `patterns`, each key's `sets` (two decimals) and `sessions` (`primarySets` for muscles), `unplacedSets`; `untrained` groups |
| `/me/balance` | `get_balance`         | per pair: each side's key, name in the caller's language, patterns and `sets`; `weeksTrained`                            |

Both take `?from=&to=` as the other windowed reads do. The tool returns the
route's body as is. Balance counts a row's sets once toward a side when any of
its patterns is on that side, whole sets as the app does, and draws no
conclusion: the pairs content carries no thresholds
(`docs/2026-10-15.balance-pairs.md`), and the app's own "not enough yet" bar
is the app's.

The pairs are read from the bucket the CDN serves `static/balance` from, held
an hour per instance like the program library. Until the file is uploaded,
`/me/balance` returns no pairs and `get_balance` says they aren't published.

## Goal progress

`/me/goals/progress` and `get_goal_progress` measure each live goal the way
the app's goal card does (`currentGoalValue` in heart-of-yours), so an
assistant and the card agree:

- `workouts` counts finished workouts.
- `sets` and `sessions` count the goal's subject from the rows above: an
  exercise's own sets, a pattern's, a muscle group's at its share. A muscle
  key that is no group reads nothing, as in the app.
- Any other metric is its exercise's per-session value (`toSessionMetrics`).
  A milestone takes the best session ever; a cadence folds the period's
  sessions by `periodAggregate`, and an empty period is 0 (but nothing for
  pace, where 0 would read as met).

A weekly goal's period is the current week from `firstWeekday`, and a monthly
one's the calendar month, both in UTC. `progress` is the card's bar: through
the current stage from 0 to 1, the target over the value for pace, 1 once a
ladder is finished. The server only reads: stamping a stage achieved stays the
app's.

## Freshness

`/me/records` and `get_personal_records` say when each exercise was last done
in the span (`lastTrained`). A record that hasn't moved on a lift not done for
weeks says nothing about getting weaker. No trend or verdict is computed: the
data is the server's job and the conclusions are the assistant's.

## Gaps

- **The app doesn't send `firstWeekday` yet.** It keeps the choice on the
  device; until it reports it in settings, the server counts Monday weeks and
  says so.
- **Weeks are UTC.** The server doesn't know the user's timezone, so a late
  Sunday workout west of Greenwich lands in the next week. Same as
  `/me/programs`, and the app's goal periods are local, so a goal can read a
  workout differently near a week's edge.
- **A program on rotation counts its own cycle in the app** (pattern lens,
  rule 2). The server counts calendar weeks only.
- **`static/balance` isn't uploaded.** It goes out with the other content
  objects once the copy is reviewed.
