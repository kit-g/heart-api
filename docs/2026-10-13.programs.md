# Programs: the backend design

The backend side of Programs (heart-api#86). The product design is
`docs/2026-10-11.programs.md` in heart-of-yours. This document holds what the
server stores, what it computes and what it serves. It was written with the
user before any code; once the code lands, it gets rewritten from the code like
every other doc here.

It builds on three changes already in review:
- targets on template sets (#195, `docs/2026-10-12.template-set-targets.md`)
- muscle shares (#197, `docs/2026-10-12.muscle-shares.md`)
- goals about a pattern or a muscle (#196, `docs/2026-10-12.goal-subjects.md`)

Skips (#202) and the free library (#198) come after it and follow its shapes.

## Decisions

These were made with the user on 2026-10-12 and 2026-10-13.

1. **Many programs can be active at once.** Lifting and stretching run side by
   side, and each keeps its own position. Zero, one or many: never exactly one.
2. **A program owns its sessions as copies.** Starting a library program copies
   its sessions into the user's own templates, in a folder named after the
   program. The program remembers the library id it came from. After that the
   user edits freely: drop bench from a 5/3/1, swap a session, change a rule.
   Nothing ever points at Heart's content, so a library update can never change
   a program under someone's feet.

   This supersedes the product doc's "a free program runs on Heart's templates
   as they are". Copy-on-write would need a second, override layer. Copying up
   front needs none.
3. **The schedule is offered, never enforced.** A program has a weekly target
   ("3 a week") and, optionally, preferred days. Missing Wednesday and training
   Thursday changes nothing. The copy encourages and never accuses: a week shows
   "1 of 3", and the next week starts clean, with nothing carried over as debt.
   There are no streaks.
4. **Two clocks, independent of each other.**

   | Clock          | Counts                                    | Moved by                                   |
   |----------------|-------------------------------------------|--------------------------------------------|
   | Program week   | where you are in the progression          | completing a cycle; repeat; replay         |
   | Calendar week  | "2 of 3 this week" against the target     | the calendar; a paused program is not counted |

   A cycle is one pass through the program's sessions, each done or skipped, in
   any order, on any day.
5. **Position is computed, never stored.** The program week, the next session
   and whether the program is paused are all derived from a history: program
   workouts, skips and program actions. No cursor exists, so nothing can drift,
   and two devices can't disagree. Undoing anything means deleting the record
   that caused it.
6. **The user steers with actions.**

   | Action               | Effect                                                                                     |
   |----------------------|--------------------------------------------------------------------------------------------|
   | Repeat               | Runs the cycle again at the same week. The usual moment is "next week raises the weight and I'm not ready". |
   | Pause / Resume       | Takes the program out of "up next" and the weekly count. Illness never reads as "0 of 3". |
   | Replay from week N   | Goes back to an earlier week, with the option to lower the bases (5/3/1's reset is −10%).  |

   A skip (#202) is the fourth steer: "count this session as done and move on".
   Repeat, replay and pause apply to the whole program. Holding back a single
   exercise is a base change, not an action (see decision 7).
7. **Every change to a base is stored, with its cause.** An exercise's base is
   what its rule grows:
   - the training max, under share of a max
   - the working weight, under add weight and under range, then weight
   - the duration or distance, under longer each week

   A change records what caused it: a workout, an action (a replay's cut), or
   the user's own edit. That history is the "100 → 102.5 → 105" view. "Keep 57.5
   kg" on the Done page is a user entry on top of it, and undoing a deleted
   workout's bump is a delete.
8. **The weekly target lives on the program, not in Goals.** Starting a program
   never writes goal rows behind the user's back. The app can offer "track this
   as a goal" as its own opt-in, which creates a normal `sessions` or `workouts`
   goal.
9. **Position is computed once, in heart_models.** The app, `/me` and MCP all
   call the same function on the same records, so they give the same answer.

## The data model

### `programs`

| Column       | Holds                                                                                          |
|--------------|------------------------------------------------------------------------------------------------|
| `id`, `user_id`, `created_at`, `updated_at` | as for templates                                                 |
| `name`       | 1–100 characters                                                                               |
| `note`       | optional, up to 1000 characters: what it's for, in the user's words or the library's           |
| `source`     | optional library program id (text, no foreign key: CDN content), kept when copied              |
| `per_week`   | optional weekly target in sessions, not days, 1–28: two-a-days and a physio's "twice daily" fit |
| `days`       | optional preferred ISO weekdays (`smallint[]`, 1–7, unique); a hint for reminders and "up next" |
| `weeks`      | optional length in program weeks; null means ongoing                                           |
| `rules`      | JSONB, a growth rule per exercise id, absent meaning "as written"                              |
| `constraint_key` | optional content key such as `avoid_high_axial_load`, spelling-checked like goal subjects; `constraint` on the wire |
| `archived`   | the user stopped following it; history is kept                                                 |

Growth rules sit on the program row as a JSONB map, not in a child table. They're
edited with the program, validated as a whole, and read with it. A `rules` key
is an exercise id. A rule naming an exercise that no session contains is kept,
not rejected: taking bench out of a session must never make the program invalid,
and putting it back brings its rule back.

### Sessions are templates

`templates` gains `program_id`, a foreign key that cascades. A session is a
template carrying it, and the program's session order is `order_index` within
the program.

- Deleting a session means deleting the template.
- Deleting a program deletes its templates. The app warns first and offers
  "keep the templates" (null `program_id`, then delete) as the other way out.
- `joined_program_at` on the template is what makes position stable when
  sessions change (see "Computing position"). It's when the template joined,
  not when it was made: a template filed into a program later ("make a program
  from a folder") joins the next cycle. The device says when, as the template
  body's `joined`, so a session filed offline joins when it was filed, not
  when it synced. When a write moves a template into a program without
  saying, the database stamps its own clock; a time ahead of the server's is
  capped at it. A program carries it as `joined`, keyed by template id.
- A one-line reason per session ("big lifts for the quads, chest and lats") is
  library content. It goes in a new optional `templates.note`, useful outside
  programs too.

### Workouts and skips name their program

`workouts` gains two optional columns:
- `template_id`, set null when the template is deleted: the template the
  workout was started from. It's general, not only for programs, so #172's
  "Previous from the same template" and a per-template progress chart use it
  too.
- `program_id`, set null when the program is deleted. It's kept separately so a
  workout still counts toward its program after its session is deleted.

Both are links, never requirements. A workout saves whatever they say: an id
that isn't the caller's, or isn't an id at all, reads as none, so a session
finished before its template synced, or after it was deleted, still lands. A
replace without the keys keeps them; an explicit `null` lets go. `Template`
`toWorkout()` sets both, and a repeat of a past workout starts without them.

A skip (#202, `docs/2026-10-14.skips.md`) carries the same two references, by
the same rule.

### `program_actions`

Columns: `id`, `program_id` (cascade), `kind` (`repeat`, `pause`, `resume`,
`replay`), `week` (replay only, ≥ 1), `at` (the device's time), `created_at`.

A replay's cut isn't a column. It's written as base changes linked to the
action.

### `program_bases`

Columns:
- `id`, `program_id` (cascade), `exercise_id`
- `value` (real, > 0; kilograms, seconds or kilometres, per the rule's measure)
- the cause: at most one of `workout_id` and `action_id`, or neither (the
  user's edit). Both cascade: deleting a workout or undoing an action deletes
  the move it caused, so nothing is left for the app to clean up.
- `at`, `created_at`

A unique index on `(program_id, exercise_id, workout_id)` makes a bump
idempotent. Each workout's bump is written by the device that saved the
workout, in the same upsync. A second device that writes it again gets the
first one back.

Both tables keep `user_id` and reach their program through a composite key, so
nothing can join another user's program. A program keeps at most 1000 actions
and 5000 bases (`400 program_history_limit`): years of use, and a ceiling on
what a fold reads.

The current base is the latest row. The first one is written when the program
starts: suggested at about 90% of the estimated one-rep max, and always
editable.

## Growth rules

Five kinds, stored as data, and checked when the program is saved
(`400 invalid_rule`):

| Kind              | Parameters                                    | Grows                                                     |
|-------------------|-----------------------------------------------|-----------------------------------------------------------|
| `none`            | (none)                                        | nothing; the sets stay as written                         |
| `addWeight`       | `step` (kg)                                   | the base, after every completed session                   |
| `rangeThenWeight` | `step` (kg)                                   | the base, once every set reaches the top of its range     |
| `shareOfMax`      | `waves`, `step`, `missCut`, `misses`          | the base, when the cycle's AMRAP set is made; −`missCut` after `misses` misses |
| `longer`          | `step` (s or km)                              | the base, after every completed cycle                     |

Rep ranges come from the session's set targets (#195). The rule never repeats
them.

`shareOfMax` needs sets that change by week. 5/3/1 is 5/5/5+, 3/3/3+, 5/3/1+,
then a deload. `waves` is a list per program week, cycled. Each entry is a list
of `{share, reps, amrap?}` that is applied to the session's working sets in
order. A share-of-max set target from #195 (`{"share": 0.85}`) means "share of
the exercise's base". This is the key #195 left room for, and it ships with the
programs heart_models release.

There are no user-defined formulas. A sixth kind arrives the way a goal metric
did: a new value, read tolerantly by older builds.

## Computing position

`ProgramPosition.of(program, marks:, actions:, now:, firstWeekday:)` in
heart_models is a pure fold, in time order. A mark is a program workout, at its
start, or a skip.

1. A cycle's sessions are fixed by its first mark: the sessions that had joined
   the program by then (`joined`, else the id's time). Before any mark, or when
   none had joined (a clock behind), all of them. A session added later joins
   the next cycle, so adding one never undoes past weeks. A deleted session's
   workouts still count by `program_id`, but no longer complete anything.
2. A program workout or a skip marks its session done in the open cycle.
   Doing a session twice doesn't count twice.
3. When every session of the cycle is done, the week advances and a new cycle
   opens.
4. `repeat`: if the open cycle has nothing in it yet, the week goes back one
   and the just-finished cycle runs again. Otherwise the open cycle restarts at
   the same week.
5. `replay N`: a new cycle at week N.
6. `pause`: paused until a `resume`, or until a program workout, which resumes
   implicitly.
7. A program with `weeks` is finished once its week passes `weeks`.

The output:
- `week`
- `done` and `remaining` for the open cycle
- `next`: the first remaining session in order; null once finished
- `paused`
- `finished`
- `thisWeek`: program workouts this calendar week, a count and nothing more
- `target`: what `thisWeek` counts toward, `perWeek`, or null while paused or
  finished. A paused week is no week, so illness never reads as "0 of 3".

Preferred days don't choose `next` yet: they are a hint the app can use.

The server runs the same fold for `/me` and MCP over the same rows: a program's
workouts at their start, its skips, and its actions. Its cost is one program's
history, read when asked, and nothing is cached. The server knows neither the
user's zone nor their first weekday, so its `thisWeek` counts ISO weeks in UTC;
the app counts the user's own.

## The API surface

The app's surface, under `/programs`:
- `GET /programs`, `GET /programs/:id`: the user's programs, archived ones
  included, each with `sessions`, its template ids in order. The templates
  themselves come through `/templates`, which carries `programId` and `note`.
- `POST /programs`: creates the program and its session templates in one
  transaction. Starting a library program is this call: the device has the
  library from the CDN, makes the copy, and posts it with `source` set. The
  server never reads the CDN.
- `PUT /programs/:id`: full replace of the program's own fields and rules.
  Sessions are edited through the template routes, which now take `programId`.
- `DELETE /programs/:id`: with `?keepTemplates=true` for the other way out.
- The answers: `400 invalid_rule` (a rule this server doesn't know, or out of
  range), `400 invalid_key` (a misspelled `source` or `constraint`),
  `400 program_limit`, `404 program_not_found`, and `404 unknown_program` for a
  template naming a program the user doesn't own.
- `GET`, `POST` and `DELETE` on `/programs/:id/actions` and
  `/programs/:id/bases`, each create idempotent on its id. A base naming an
  exercise the caller can't see or a workout they don't own is `404
  unknown_exercise` / `unknown_workout`, and one naming another user's action
  `404 unknown_action`.
- Workout and skip bodies take `templateId` and `programId`.

The shapes the app relies on are contract:
- Lists answer `{"programs": [...]}`, `{"actions": [...]}` and
  `{"bases": [...]}`, every row included, in order (actions and bases oldest
  first).
- A create answers `201` with the row when it made it, and `200` with the
  stored row when the id already existed (an upsync replay). Neither ever
  answers the body it was sent.
- A delete answers `204`, and deleting what isn't there is not an error.
- A program's own fields that a `PUT` leaves out are cleared: it's a full
  replace. `Program.without` is how the app unsets one before sending.

The developer surface is read-only, as #86 says:
- `/me/programs` and `/me/programs/:id`, with the computed position, the
  current bases and the next session spelled out.
- MCP `list_programs` and `get_program`, on the same data. The tool
  description says what a base is and that position is computed.

Coaches, together, and writes through MCP are later. A coach's program is the
same entity arriving over a connection, as `assigned_by` already is on
templates.

## Compatibility

Everything here is additive under the compatibility floor:
- new tables, routes and optional fields
- a new heart_models minor version
- a set-target key that 2.16.0 already carries untouched

One case needs care. **A build that predates programs must never drop a program
reference.**
- Mobile 1.13 edits a program's template with a full-replace `PUT` that has no
  `programId`. An absent key keeps the stored value, the same rule #195 uses for
  `target`. Only an explicit `null` detaches the template.
- The same holds for a workout's `templateId` and `programId`.
- 1.13 shows a program's templates as ordinary templates, in the folder named
  after the program. That is honest, and it still works.
- Deleting one there removes the session. The program shows one fewer, which is
  the user's own choice.

Health rule: nothing here is health-shaped. A weight goal shown beside a program
stays on the phone.

Limits: at most 100 programs per user, archived ones included, enforced in the
insert the way the goal cap is, and at most 50 sessions in one create. They
guard the database against abuse rather than limiting anyone, so they're the
same for free and premium. A program's templates count toward the template
limits, the same way any template does.

## What the app does with it

These are notes for heart-of-yours from the Hevy UX walk-through (the "Hevy —
UX research" page, sections 2.6 and 4). They're requests, not specs.

- **Preview before commit.** A library program is fully readable before it's
  started. Hevy's Trainer asks nine questions and shows only a summary.
- **One meaning of "program".** A library program and a started one are the
  same thing. Hevy has two unrelated "programs" in one tab.
- **The rule in one sentence, where the range is shown**: "once every set hits
  10, the weight goes up 2.5 kg".
- **Repeat as an equal choice, never a failure.** At a cycle's end, show next
  week's weights with "Let's go" and "Repeat this week" side by side.
- **Ease back in.** After a long gap, offer to pick up where you left off, or
  to replay a week, lighter. The app decides when to offer it, and the server
  stores nothing time-based.
- **Round shares when showing them.** Secondary muscles count 0.5 (#197), and
  Hevy shows "36.5 sets".
- **Honest durations.** Hevy shows an estimate of 1h 14min on a program built
  for 60 minutes.

## Open

- **Program templates in the template list.** Whether the template list hides
  them when the app knows programs (it probably should) is the app's call. The
  server returns them either way.
- **Exercise-specific waves.** A `shareOfMax` rule per exercise covers
  5/3/1-style main lifts. Per-session variants (a heavy day and a light day on
  the same lift) would need a rule per session exercise. That's left out until a
  library program needs it.
- **Folder name collisions.** Starting the same program twice hits the unique
  folder name, so the second copy gets "(2)". That's the app's job when it
  makes the copy.
