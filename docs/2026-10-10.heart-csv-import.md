# Importing Heart's own CSV export

`POST /workouts/imports?source=heart` reads the app's CSV export through the same pipeline as
Strong and Hevy (heart-api#39, #72): a new parser, then the canonical batch, the shared SQL in
`api/lib/db/queries.dart`, and the preview and report the app already shows. Written from the
code as it stands; nothing here is a proposal unless it says so. Ticket: heart-api#175. The
app's JSON export is the app's own business (heart-of-yours#329, below); the API's Strong-layout
file (`GET /me/export?format=strong`) stays `source=strong` and is not part of this.

## What the app writes

`ExportSnapshot.toCsv` in heart-of-yours (`shared/heart_state/lib/src/export.dart`) writes the
finished workouts of the local store, oldest first, one row per set:

```
workout_id,start,end,exercise_id,exercise_name,set_index,weight,unit,reps,duration,distance,notes
```

| Column | What it holds |
|---|---|
| `workout_id` | the workout's own id, the UUIDv7 the app minted for it |
| `start`, `end` | ISO-8601 instants in UTC (`2026-03-01T10:00:00.000Z`); blank when unset |
| `exercise_id` | the exercise's id: the library's for a catalog exercise, the user's custom's otherwise |
| `exercise_name` | the name as displayed — for a catalog exercise, in the app's language |
| `set_index` | 1-based, restarting for every exercise entry of the workout |
| `weight`, `distance` | in the unit the user saw them in: the exercise's own override, else the global setting; two decimals at most, no trailing zeros |
| `unit` | the unit of that row: `kg`, `lb`, `km`, `mi`, or both with a slash on a carry (`kg/km`, weight's first); blank when the row has neither |
| `reps`, `duration` | as stored; `duration` in seconds |
| `notes` | the **exercise's** note, repeated on each of its rows |

RFC 4180 quoting (a field with a comma, a quote or a line break is quoted, quotes doubled),
LF row ends, every row terminated. An empty store is the header alone. Nothing in it is health
data: the snapshot drops `calories` and `met` on the way out.

No real file is in a bucket yet. `api/test/fixtures/heart/export.csv` is written by hand to the
writer's rules and its own test (`shared/heart_state/test/export_test.dart`) — a metric store
with two exercises overridden to imperial, a quoted name, a multi-line note, a carry, the same
exercise twice in one workout — and is the fixture the parser tests read.

## What the parser does

`WorkoutImport.fromHeartCsv(csv)` in `api/lib/models/imports.dart`, picked by
`ImportSource.heart.parse` from the `source` query parameter (`api/lib/inputs/workouts.dart`).

**Nothing is asked.** The instants carry their offset and every row names its unit, so the
request's `tzOffset` and `unit` are read for Strong and Hevy and ignored for Heart. A blank
`unit` on a row that has a weight (which the writer never produces) reads as metric.

**Workouts** are grouped by `workout_id`, in file order. A row without a `workout_id`, whose
`start` does not parse, or that measures nothing is skipped and counted in `rowsSkipped`; zero
reads as not recorded, as from the other exporters. The end is kept when it parses and is after
the start and within 24 h, as for the other sources; an unreadable end is no end, not a lost
workout. A workout has no name and no note: the file carries neither.

**Exercises.** A block opens where the name changes or `set_index` is `1`, so the same exercise
logged twice in one workout stays two entries, as the lifter had it. `notes` becomes the
exercise note, once. The `exercise_id` travels with the block.

**Sets** are weight (to kg), reps, duration, distance (to km) from the row's unit. The file has
no set types and no RPE, so every set is a normal, unrated one.

## Identity

The file's `workout_id` is the identity. The import id is `heart:<workout_id>` when the id is a
UUIDv7, which is every id the app has minted since it moved off Firebase: a UUID leaks nothing
(the `strong:`/`hevy:` ids hash their source rows for that reason) and the owner can trace a copy
to the workout it came from. A store old enough to hold Firebase-era ids exports them as they
are; such a workout imports under `heart:<16 hex of sha256 over the id>`, like the other sources'
identities, and carries no `workoutId` into the payload, so none of the id matching below applies
to it. Two things follow for the rest, both in the shared SQL (`_reimportCandidates` in
`queries.dart`, where `_reimported` is now "the stored workout an incoming one already is"):

- **Importing into another account** creates each workout once, under a fresh uuid-v7 minted
  at the workout's start — never the file's id, which belongs to the account that exported it —
  with `import_id = heart:<workout_id>`. A second import of the same file is a no-op reported
  as `workoutsSkipped`, as for the other sources, and a re-import fills gaps (an exercise note
  the stored copy lacks) and nothing else.
- **Importing into the account the file came from** changes nothing: a row whose `workout_id`
  is one of this user's `workouts.id` is that workout, already there. The preview counts it in
  `workoutsAlreadyImported`, the report in `workoutsSkipped`, and the workout keeps its id and
  its `NULL` import identity. Unlike a workout found by import identity, it is **not** enriched:
  the store is newer than its own export, so an exercise note that is `NULL` in the store and
  present in the file was cleared after the export, and writing it back would undo that. (The
  `_reimported` rows carry `by_identity`; only those fill gaps.)
- **A deleted workout is not the user's own any more.** `workouts.id` is checked, not
  `archive.deleted_workouts`: a workout the user deleted after exporting comes back from the
  file under a fresh id and `import_id = heart:<old id>`. That is the behaviour the other sources
  have ("a deleted workout comes back", `docs/2026-09-26.import-fidelity.md`), and it is what a
  backup is for.

The other sources' SQL path is unchanged in behaviour: their payloads carry no `workoutId`, so
the second half of `_reimported` matches nothing, and the "already there" set is the same
`(user_id, import_id)` set the `ON CONFLICT` clause has always handled (the clause stays, for a
concurrent import).

## Exercise resolution

A Heart row names its exercise twice, by id and by name. The id is exact and cheap, and the name
is the catalog's display copy in the app's language, which the library knows only in English and
`import_names` has no `heart` rows for — so the id is tried first, and the resolver's `_keys`
gained an id key that wins outright over any name match. The id resolves when it is the library's
or one of the user's own exercises: a custom from another account (or one an anonymous session
minted and never upsynced) matches nothing by id and falls to the name, through the existing
resolver (library names and aliases, the user's customs, case-insensitively), and then to a
custom under the name as written, gated by `createCustom` as for the other sources. A name the
file gives two different ids is matched by name alone.

For Strong and Hevy nothing changes: their names carry no id, so the id key is never built.

## What the CSV loses

Relative to the app's JSON export, which is lossless, the CSV has no workout name, no workout
note, no set types, no RPE, no pauses, no calories (by design — the health rule), no templates,
no folders, no custom exercise definitions (category, target, instructions), no goals, no unit
preferences, no images. An import of it is workouts, exercises, sets and exercise notes, and the
custom exercises it has to create get a guessed category and `Other` as the target, as for any
import.

The JSON is imported app-side (heart-of-yours#329): the app loads the snapshot into its local
store and the anonymous → account upsync replay (heart-api#66, `docs/2026-09-05.upsync-replay.md`)
carries it to the server by id, templates, folders, customs and goals included. The file never
reaches the server and there is no `source=heart` for it.

## Request and response

Unchanged from Strong and Hevy but for `source`:

```jsonc
// POST /workouts/imports?source=heart&dryRun=true
// body: the export as text/csv, or {"csv": "...", "createCustom": [...]}
{
  "source": "heart",
  "workoutsFound": 3,
  "workoutsAlreadyImported": 3,
  "exercisesMatched": 5,
  "exercisesUnmatched": [],
  "rowsSkipped": 0,
  …
}
```

`source=anything-else` is `400 unsupported source: … (supported: strong, hevy, heart)`. A file
in no known layout is a 400 as before; only the Hevy parser parks a file (`202`), as before. An
import that skipped rows is kept under `imports/partial/…` as for every source.

## Gaps

- **A workout the server has not seen yet is not "the user's own".** The app is offline-first:
  a workout logged, exported and imported into the same account before it has upsynced is not
  in `workouts`, so the import creates a copy under `heart:<id>`, and the upsync then lands the
  original under `<id>` — two workouts. Nothing recognises `heart:<id>` against a workout
  arriving later with that id; the app importing its own file while it has unsynced work is the
  case to avoid (sync first), or `POST /workouts` could one day answer an id whose `heart:<id>`
  copy exists with that copy.
- **Two exercises sharing a display name are one on import.** The batch resolves exercises by
  name (`_names`, `_lookup`), and the id rides along per name; a name the file gives two ids (a
  library exercise and the user's same-named custom, both logged) gets no id and resolves by
  name alone, so both histories land on one exercise. Telling them apart means keying the
  payload's exercises by something other than the name, which is the shared SQL's whole shape.
- `workouts.import_id`'s column comment describes the `strong:`/`hevy:` shape (`<source>:<16
  hex of sha256>`); `heart:<uuid>` is a third shape. A comment-only migration would say so.
- A row the app wrote for a set with nothing in it (if the app ever stores one) is skipped and
  counted, which keeps the file as a partial import in the bucket. Harmless, and a sample worth
  seeing if it happens.
- The category guessed for a custom reads the typed name, so a non-English name's equipment
  modifier is not recognised and the guess falls back to the set shape, as for Hevy.
- The API's Strong-layout export (`/me/export?format=strong`) still imports as `source=strong`
  with `tzOffset=+00:00` and no workout ids; its re-import into the origin account duplicates,
  as heart-api#175 records. Out of scope here.
- The app's source picker is heart-of-yours' side; the contract is the existing one plus
  `source=heart`.
