# Task: per-user preferences — per-exercise unit + global settings (heart-go backend)

You are in the heart-go API project (`/Users/kitg/mine/heart-go`), a Dart (relic) server.
We're reworking per-user preferences so the Flutter app (heart) has a coherent place for
both **per-exercise** prefs and **global** UI/settings prefs.

The app resolves an exercise's display unit as: **exercise preference → global setting**.
Weights/distances stay stored canonically in metric; unit preference is display-only.

## Design decisions (settled — do not re-litigate)

Split preferences by **cardinality**:

- **Per-`(user, exercise)`** prefs (chart type, unit override) → relational, one row per
  `(user, exercise)`, with a real FK so deleting an exercise cascades the pref away.
  These are an unbounded map keyed by exercise, mutated independently, and joined onto the
  exercise list — they do not belong in a blob.
- **Global, scalar** settings (unit-system *default*, theme mode, accent color, future UI
  toggles) → a `settings JSONB` column on `profiles`. One value per user, loads with the
  profile, no join, no migration per new toggle.

Specific calls made with the user:

1. **One merged per-exercise table.** Replace `chart_preferences` with `exercise_preferences`
   carrying both `chart_type` and `unit_system` (both nullable). The app is **not** using the
   chart endpoint yet, so **no data migration** — just drop and recreate.
2. **Kill the dormant overrides.** `workout_exercises.unit_system` and
   `template_exercises.unit_system` (migration `2026-05-23.unit-system.sql`) are orphaned by
   this model. **Remove them** — columns, read-helper output, and all heart_models / query
   plumbing. Do not leave them dangling.
3. **Global settings ride on `PUT /accounts`.** No new endpoint. `User` gains a typed
   `settings` field that round-trips through the existing account upsert (which returns the
   updated `User`). There is no `GET /accounts`; the app gets its profile back from the upsert.
4. **`settings` is a typed `Settings` model**, not an opaque map. Known fields validated at the
   boundary; unknown keys preserved so the app can add toggles without a backend change.

## Data contract the Flutter app relies on

- `GET /exercises`: each exercise object includes `"unit_system": "imperial"|"metric"|null`.
- `POST /exercise-preferences {exerciseId, unitSystem?, restTimer?}` (camelCase request
  body, ≥1 pref field) partial-upserts (only sent fields written);
  `DELETE /exercise-preferences/:exerciseId?pref=unitSystem|restTimer` clears one field
  (400 on missing/unknown `pref`); the other field is left intact.
- `GET /exercises` items also carry `"rest_timer": <int seconds>|null` (per requesting user).
- `unit_system` is per `(user, exercise)`; null/absent ⇒ app falls back to the global setting.
- `PUT /accounts {..., settings: {...}}` upserts the profile and returns the `User` with
  `settings` (unit-system default, theme mode, accent color, + any extra keys preserved).
- `/charts` endpoints are unchanged externally; they now read/write the merged table.
