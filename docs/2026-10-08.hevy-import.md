# Hevy import

`POST /workouts/imports?source=hevy` reads a Hevy CSV export through the same pipeline as
Strong (heart-api#39, #84): the parser is new, everything from the canonical batch down is
shared. Two things landed with it that apply to every source: a translated exercise title is
resolved in the database, and a file no parser can read is kept for a manual import instead
of refused. This doc is written from the code as it stands; nothing here is a proposal unless
it says so. Ticket: heart-api#72. Follow-ups: heart-api#140 (move an exercise's history),
heart-api#141 (absorb Hevy's catalog).

## What Hevy exports

Everything below was observed on real exports of one test account (every set type, RPE value
and exercise type, supersets, all 454 catalog exercises, every month, hostile text, DST and
duplicate keys), in all 17 app languages and from hevy.com. The bundle is in the dev account at
`s3://583168578067-ca-central-1-static/imports/hevy/2026-10-04/` (its `README.md` has the
full findings). The English app and web files are copied to `api/test/fixtures/hevy/`; the
German and Korean ones carry Hevy's translated catalog, so they stay out of the repository and
the tests read them from the gitignored `content/assets/hevy/` where present.

Two exporters write one layout, one row per set:

```
title,start_time,end_time,description,exercise_title,superset_id,exercise_notes,
set_index,set_type,weight_kg|weight_lbs,reps,distance_km|distance_miles,duration_seconds,rpe
```

The unit columns follow the account's units at export time. Every string field is quoted.
Neither file has a BOM. A workout's rows are contiguous; `set_index` restarts at 0 for every
exercise block, so the same exercise twice in one workout is two runs from 0. Zero is exported
as blank, so a blank is "zero or not tracked". Weight and distance are rounded to 2 dp after
unit conversion (lbs with 2.20462). `set_type` is `normal|warmup|failure|dropset` and RPE is
6–10 in half steps, in English whatever the language. Supersets are per-workout integers.
`custom_metric` (stair floors and steps) is not exported.

| | App (`workout_data.csv`, iOS = Android) | Web (`workouts.csv`) |
|---|---|---|
| Dates | `d MMM yyyy, HH:mm`, month token in the app's language | `Intl` medium date + short time in the browser's language and timezone |
| Exercise titles | catalog titles translated into the app's language; customs as typed | always English |
| Line breaks in a field | the two characters `\n`; a CR survives raw | real CRLF |
| Row endings | CRLF, with a few bare LF | LF |
| Order | newest first | fetch order |

Both are naive local time at minute precision with no offset.

## What the parser does

`WorkoutImport.fromHevyCsv(csv, {unit, utcOffset})` in `api/lib/models/imports.dart`, picked by
`ImportSource.hevy.parse` from the `source` query parameter (`api/lib/inputs/workouts.dart`).

**Dates.** Two grammars. The app's is read in every language with one table of 126 month tokens
(`hevyMonths`, generated from `content/imports/hevy/months.json`): no token means two different
months in any pair of languages, so the language is never detected or asked. The web's is read
in English only (`Sep 5, 2026, 6:10 AM`, `Sept` included). A file none of whose rows parse is
refused whole, which the route turns into a parked import (below), rather than reported as every
row skipped. The instant is the wall clock minus `tzOffset`, as for Strong; a workout spanning a
DST switch is off by an hour at one end, accepted.

**Titles** are kept exactly as the file writes them. The parser knows nothing of Hevy's catalog;
resolution is the database's (below).

**Workouts.** A workout is a contiguous run of rows with equal title, start, end and
description. `title` + `start_time` does not identify one: the account has two different
sessions with the same title and start at minute precision. The import id is
`hevy:<opaque(startLocal|endLocal|title|n)>` where the local times are the parsed minutes
(`2026-09-22T06:00`, so the app and the web files give the same id) and `n` is the run's
ordinal among equal keys in the file. Re-running an export is a no-op that reports the skips,
and a web export after an app export of the same history enriches rather than duplicates.

**Exercises.** An exercise logged twice in one workout stays two exercises (a new block opens
when the title changes or `set_index` is 0). Strong's parser merges by name as before; the
shared `_WorkoutBuilder` does both.

**Sets.** Blank is null. `warmup`/`dropset`/`failure` become `warmup`/`drop`/`failure`,
`normal` is null. RPE is kept on any set, cardio included; an off-scale value is dropped and
the set kept. `exercise_notes` becomes the exercise note (once, though Hevy repeats it on every
row), `description` the workout note; the app's `\n` escapes are turned back into line breaks
and CRLF into LF so a note reads the same from both exporters. A row with no measurement at all,
or a negative one (the database rejects it, and one would abort the whole statement), is
skipped and counted in `rowsSkipped`. `superset_id` is dropped and not counted. Weight is
converted to kg and distance to km from the header's unit; `unit` is the fallback for a bare
header.

**The end** is kept only when it is after the start and within 24 h, as for Strong.

## Name resolution: translations and aliases

Hevy's app writes catalog titles in the app's language (`Bankdrücken (Langhantel)`,
`벤치 프레스 (바벨)`), and Hevy's catalog with every title in all 17 languages is Hevy's content,
so it is neither in the repository nor in the binary. It lives in the dev account's bucket and
`scripts/import_names.py` loads it into **`import_names`** (`2026-10-08.import-names.sql`): one
row per `(source, title)` → English `name`, unique case-insensitively. Eleven translated titles
are shared by two catalog exercises (pl `Brzuszki` is Crunch or Sit Up, pt `Abdominal Canivete`
is Jackknife Sit Up or V Up, …); the loader takes the first live one in catalog order and prints
the picks, and heart-api#140 is how a user corrects one. The loader has to run against each
database (dev and prod) with the bucket's catalog; until it has, a translated title is a custom.

The import SQL (`api/lib/db/queries.dart`) resolves each incoming name through that table to
its **canonical** form (itself when no row matches), and matches the canonical form against
`exercises.name` and `exercises.aliases`, case-insensitively; the user's own exercise wins over
the library's, and a name over an alias. A custom is created under the canonical name, so the
same history exported in German and in English makes one custom. Everything keyed by the
incoming spelling stays so: the preview's `exercisesUnmatched`, the `createCustom` allowlist,
the report's `exercisesSkipped`. The report's `exercisesCreated` carries the names as created,
i.e. English where a translation was known.

The alias match is the hook heart-api#141 fills: a Hevy name that is the same movement as a
Heart exercise becomes that exercise's alias in `content/exercise_library.yml`, and from then
on it imports as a match instead of a custom.

## A file no parser reads is kept, not refused

`ImportWorkoutsIn` parses the body and, when the parser throws, keeps the file and the reason
instead of answering 400. The route then stores the file in the content bucket under
`imports/parked/<user hash>/<source>-<content hash>.csv` (`parkedImportKey`; a retry of the
same file is the same object), alerts the owner on the monitoring topic (best-effort, like the
large-import alert), and answers **`202`**:

```jsonc
{
  "source": "hevy",
  "status": "parked",
  "message": "We couldn't read this Hevy export automatically. We've kept the file and will message you once it has been imported.",
  "reason": "unreadable date \"05.09.2026, 06:10\": export from the Hevy app, or from hevy.com in English"
}
```

`status` is the stable word a client branches on; `message` is prose it may show as is. A dry
run parks too, so the user hears it at the preview. Only an empty body is a 400: there is
nothing to keep. The import of a parked file is manual, by the owner, and so is messaging the
user afterwards; neither has a mechanism yet (Gaps).

## Request and response

Unchanged from Strong except `source` and the parked outcome:

```jsonc
// POST /workouts/imports?source=hevy&dryRun=true&tzOffset=-04:00
// body: the export as text/csv, or {"csv": "...", "createCustom": [...]}
{
  "source": "hevy",
  "workoutsFound": 58,
  "workoutsAlreadyImported": 0,
  "exercisesMatched": 170,
  "exercisesUnmatched": [{ "name": "Pistol Squat 🦵", "sets": 1 }, …],
  "rowsSkipped": 3,
  …
}
```

`source=anything-else` is `400 unsupported source: … (supported: strong, hevy)`.

## Gaps

- Messaging the user after a manual import has no mechanism. The app's push channel
  (`api/lib/notifications`) is the obvious one; a parked import is not health data, so the push
  can carry content.
- Web exports in the 12 other languages are parked, not parsed. The formats are known
  (`README.md` in the bundle) but only English was verified on a real file.
- `import_names` is loaded by hand; nothing in CI runs the loader, and a renamed or new Hevy
  exercise needs a fresh catalog in the bucket and a re-run.
- The category guessed for a custom (`WorkoutImport.exercises`) reads the typed title, so a
  German title's `(Langhantel)` is not recognised as a barbell and the guess falls back to the
  set shape.
- The parser does not snap converted weights back (26.46 lbs → 12.0021 kg, not 12). Strong
  doesn't either.
- `Pull Up (Assisted)` with a weight means assistance and `Chin Up (Weighted)` added load; the
  file has no exercise type, and the set stores the number as a weight either way, as today's
  schema does for every category.
- Hevy's per-exercise unit override can put a value in the other unit under the account-unit
  header (from Hevy's code, never reproduced). Nothing detects it.
- `measurement_data.csv` (body mass, body fat, girths) is never imported: the device-only health
  rule (CLAUDE.md). It fails the header check, and is parked like anything unreadable.
- The app's source picker and the parked outcome are heart-of-yours' side (heart-of-yours#72
  shipped Strong-only on purpose); the contract is the existing one plus `source=hevy` and the
  202.
