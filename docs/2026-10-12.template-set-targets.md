# Targets on template sets

What a template set aims for: "6 to 10 reps", "hold 30 s", "8+". Written from
the code as it stands (heart-api#195, for heart-of-yours#173). It is the first
slice of Programs (heart-of-yours#340, heart-api#86), and it stands on its own
without them.

## Why it exists

A template set held one value per measure, plus a set type. It could say "8
reps at 60 kg" but not "6 to 10", which is the whole of double progression,
and not "hold 30 s" as an aim rather than as something already done.

## The data model

`template_exercise_sets.target` is a `jsonb` object keyed by measure, in the
set's own units:

```json
{"reps": {"min": 6, "max": 10}, "weight": {"min": 60}, "duration": {"min": 30, "max": 30}}
```

- Measures are `reps`, `weight` (kg), `duration` (s) and `distance` (km).
- Each one is a range: `min` equal to `max` is an exact number, and no `max`
  is an open top ("8+", as many as possible). A bounded range with `amrap:
  true` is as many as possible up to `max` ("up to 10"; heart-api#230).
- Beside the measures:
  - `rir`: reps in reserve, 0 to 10 in halves ("stop with 2 left";
    heart-api#230).
  - `share`: in a program, the weight as a share of the exercise's base
    (heart-api#217).
- NULL is no target. The schema refuses `{}`, so "no target" is spelled one way.
- The set's own `weight`, `reps`, … stay what they were: what the template
  prefills. A target sits beside them and replaces none of them.

Workout sets have no target column. A target is a plan, never a record of
what was done.

The schema checks only that a target is a non-empty object. The input layer
validates the shape, so the vocabulary can grow (a share of a training max
comes with heart-api#86) without a migration.

## The API surface

Template bodies (`POST /templates`, `PUT /templates/:id`) take `target` on
each set, and every template read returns it, null included:

| Body says           | Stored target             |
|---------------------|---------------------------|
| no `target` key     | left as it is             |
| `null` or `{}`      | cleared                   |
| an object           | replaced by that object   |

A malformed target is `400 invalid_target`, naming the set. That covers:
- an unknown measure
- a range without a numeric `min`
- a key besides `min`, `max` and `amrap`, or an `amrap` that isn't a boolean
- a `rir` outside 0–10 or not in halves, or a `share` outside (0, 2]
- a negative bound, or `max` below `min`
- fractional reps or seconds

A share of a template to a student copies the targets with the sets.

### Older builds

A build that predates targets sends sets without the key. A replace updates a
kept set in place, so the stored target survives that build's save. A set the
older build creates anew (a new id) starts without one, which matches what
that build shows.

## heart_models (2.16.0)

- `SetTarget`: the ranges this build can read (`operator []`, `ranges`) and
  `withRange` to change one. It reads tolerantly. A measure or range shape
  this build doesn't know is carried as it arrived and written back by
  `toMap`, so an app on 2.16.0 won't drop a share-of-max target that a later
  version wrote.
- `ExerciseSet.target`:
  - `toMap` writes the `target` key only on a set that arrived with the key
    or had a target assigned. On those sets it always writes it, null
    included, so a target can be cleared.
  - A logged set's write is unchanged.
  - `copy()` keeps the target, so a session started from a template can show
    it. The server keeps none on a workout: workout bodies ignore the key.
- `TemplateSetRequest.target`: null leaves the stored target alone, and
  `SetTarget.none` clears it.

## Gaps

- The MCP tools and the developer reference don't describe targets yet.
  `list_templates` shows set counts only, and `/me/templates` returns the
  key without documenting it. Both come with Programs' read-only surface
  (heart-api#86).
- The sample templates on the CDN carry no targets. The free program library
  (heart-api#198) is where Heart's own templates get them.
- Nothing checks that a target's measures fit the exercise's category (a
  `distance` target on a barbell set is stored as sent). The app only offers
  the measures the category records.

## Rest between sets

A template exercise carries `rest`, seconds between sets (0–1800), as the plan
has it: 2–3 minutes on a compound lift, 60–90 seconds on isolation work
(heart-api#230). It's three-valued like a target: no key keeps the stored
value, `null` clears it. A share copies it, and heart_models 2.26.0 carries it
on `WorkoutExercise.rest`, so a workout started from the template has it.
