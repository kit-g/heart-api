# An OAuth 2.1 authorization server

Status: **built, in review** (heart-api#115, branch `feat/oauth`, on top of the developer API stack).
On in dev, off in prod until prod has a Firebase web app. Builds on `2026-09-23.developer-api.md`
(the `/me` surface, `api_tokens`, the rate limit) and is the foundation for `2026-10-04.mcp.md`.

### As built

Where the build differs from the design below:

- **The consent page is `/connect.html`.** The site has no extensionless routing.
  CloudFront serves it with `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `no-referrer` and
  `no-store`. The page also refuses to render framed.
- **Connected apps are `/accounts/connected-apps`**, not `/accounts/grants`. The wire model is
  `ConnectedApp` (`heart_models` 2.14.0).
- **A grant can hold several live access tokens.** The design said at most one. One account can
  run the same client on several devices, and revoking the others on each issue would make them
  knock each other out every hour. Expired access tokens are cleared on each issue and refresh.
- **Rotated refresh tokens are kept 7 days** for reuse detection, then cleared.
- **Reuse has a one-minute grace.** A refresh token presented again within a minute of its rotation
  is a host's parallel or retried refresh. It's refused without revoking anything. After that, reuse
  revokes the grant.
- **The grant's `revoked_at` is the authority.** A token whose grant is revoked is refused even if
  its row survived. A token minted concurrently with a revocation can escape the delete, so the
  delete is only cleanup.
- **Resource binding is in the lookup.** A token presented to another surface is refused before
  anything is counted.
- **`resource` is optional at `/authorize`** and means the MCP server. Trailing slashes are
  normalised.
- **Unknown scopes are dropped, not refused** (`offline_access`, `openid`). Asking only for unknown
  ones is `invalid_scope`.
- **A DCR client-secret method becomes `none`**, as RFC 7591 §3.2.1 allows.
- **Registrations are capped at 16 KB**, and only RFC 7591 fields are stored, both from DCR and from
  metadata documents.
- **`private_key_jwt` assertions** may be addressed to the issuer or to the endpoint being called.
  They must carry `iat`, and expire within five minutes.
- **Client metadata documents are cached for a fixed hour**, not by their HTTP caching headers.
- **The authorization server is its own router** (`buildOAuthRouter`, at `/oauth`). Only its
  consent routes are behind Firebase. The version gate skips `/oauth`, because a browser has no
  app version to send.
- **The MCP server's resource is `https://<api>/v1/mcp`** until the dedicated host exists. Its
  protected resource metadata is at `/v1/mcp/.well-known/oauth-protected-resource`, and every 401
  names it.
- **A daily cleanup clears what no flow can use.** An EventBridge schedule puts `oauth.cleanup` on
  the events queue. Live connections already prune their own tokens on every refresh; the job
  takes the rest:
  - requests and codes, a day after they expire;
  - expired access and refresh tokens, and rotated ones after the reuse check's week;
  - revoked grants after 30 days, with whatever is left under them;
  - expired client metadata documents (the next use refetches them);
  - dynamic registrations with no live grant and no use for 30 days.

  A client with a request in flight waits for the next run. Personal tokens are never touched.

Not built yet, deliberately:

- **No per-IP cap on `/oauth/register`.** The stage-wide throttle (heart-api#110) is the only
  limit.
- **A client assertion's `jti` isn't remembered.** One can be replayed within its five minutes of
  life. PKCE and the single-use code still bind every exchange it could be replayed into.
- **A replayed authorization code doesn't revoke what it issued** (RFC 6749 §4.1.2 SHOULD). It
  only fails.

## Why

Personal access tokens cover a user scripting against their own log. They don't cover the user
clicking "Connect" in Claude or ChatGPT: those hosts speak OAuth, and nothing else. The MCP
authorization spec (revision 2026-07-28) and both hosts' connector docs require an authorization
server (AS) that issues tokens bound to the resource they're for.

The same AS is what anything larger needs later: a Home Assistant integration that doesn't ask for
a pasted token, a coach's tool acting for a client who agreed to it, any third-party app. Build it
once, properly, and every later integration is a client registration, not a design.

### Why our own, and not a managed one

Firebase Auth stays the login. It is not an OAuth AS for third-party clients: it signs users into
our own apps and issues Firebase ID tokens, nothing a foreign client can be granted. Something
has to sit on top.

| Option                         | Against                                                                                                                                                                                                                                  |
|--------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Cognito                        | A second user directory to keep in step with Firebase, and no client-metadata-document support as far as checked.                                                                                                                         |
| Auth0, WorkOS, Stytch and kin  | A per-user bill for a free product, a second identity hop, and the hosts' quirks are theirs to fix on their schedule: Auth0 rejects ChatGPT's client metadata document today because it insists on `private_key_jwt` (community thread, 2026). |
| **Our own, in the Dart API**   | Work. In exchange: one Lambda, one database, tokens in the same table and counted by the same rate limit as personal tokens, and no per-user cost.                                                                                         |

The rate limit already needs a database lookup per request (`2026-09-23.developer-api.md`,
*Rate limiting*), so opaque tokens hashed in Postgres cost nothing extra, and revocation is
immediate. A managed AS would bring JWTs we'd still have to look up for counting.

## What the hosts require

From the MCP authorization spec 2026-07-28 and the Claude and ChatGPT connector docs, checked
2026-10-04:

- **OAuth 2.1, authorization code with PKCE S256.** No implicit grant, no client credentials.
- **AS metadata (RFC 8414)** at the issuer's well-known path. `issuer` must equal the URL it was
  fetched from. `code_challenge_methods_supported` must be present, or clients refuse to proceed.
- **Resource indicators (RFC 8707).** Clients send `resource=<canonical resource URI>` to both the
  authorize and token endpoints; the token is bound to it, and the resource server rejects a token
  bound to anything else. No passthrough.
- **Client registration.** In the client's order of preference: pre-registered, then **Client ID
  Metadata Documents** (CIMD: the `client_id` *is* an HTTPS URL to the client's metadata), then
  Dynamic Client Registration (RFC 7591), which the spec now calls deprecated and keeps for
  compatibility. Claude uses CIMD only if the AS advertises both
  `client_id_metadata_document_supported: true` and `none` among token endpoint auth methods;
  otherwise it falls back to DCR. ChatGPT prefers CIMD and its published document declares
  `private_key_jwt`.
- **`iss` in the authorization response (RFC 9207):** SHOULD now, expected to become MUST.
- **Refresh tokens:** rotated on every use for public clients. Claude refreshes on a `401` and up to
  five minutes before expiry; a dead refresh token must answer `invalid_grant`.
- **Timeouts:** Claude gives discovery, registration and token calls 10 seconds. A cold Lambda has
  to fit.

## Shape

```
  host (Claude, ChatGPT…)        heart-of.me (site)                 api.heart-of.me/v1
  ───────────────────────        ──────────────────                 ──────────────────
  GET /.well-known/oauth-authorization-server ──▶ static JSON
  GET /oauth/authorize?client_id&redirect_uri&code_challenge&resource&scope&state ───────────▶ validate client,
                                                                                               store the request
                                 ◀──────────────────────────── 302 /connect?request=<id> ─────
                                 /connect: Firebase sign-in,
                                 "Claude wants to read your
                                  training log"  [Allow]
                                 POST /oauth/requests/:id/approve (Firebase ID token) ────────▶ mint code
                                 ◀──────────────────────── {redirect: redirect_uri?code&state&iss}
  ◀── 302 redirect_uri?code&state&iss
  POST /oauth/token (code, code_verifier, resource) ─────────────────────────────────────────▶ access + refresh
```

### The issuer is the site

`issuer` is the environment's site origin, `https://heart-of.me` in prod. Its metadata is a static
file, served exactly the way `apple-app-site-association` already is: per-environment copies under
`site/.well-known/<env>/`, uploaded by `scripts/site.sh` with an explicit JSON content type. That
sidesteps the one awkward part of the API's hosting: `api.heart-of.me` maps the API at `/v1`, so
it can't answer at a root `/.well-known/` path, and RFC 8414 puts the document there.

Endpoints in the metadata point wherever they live; they don't have to share the issuer's host:

```jsonc
{
  "issuer": "https://heart-of.me",
  "authorization_endpoint": "https://api.heart-of.me/v1/oauth/authorize",
  "token_endpoint": "https://api.heart-of.me/v1/oauth/token",
  "revocation_endpoint": "https://api.heart-of.me/v1/oauth/revoke",
  "registration_endpoint": "https://api.heart-of.me/v1/oauth/register",
  "scopes_supported": ["read"],
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["none", "private_key_jwt"],
  "token_endpoint_auth_signing_alg_values_supported": ["RS256", "ES256"],
  "client_id_metadata_document_supported": true,
  "authorization_response_iss_parameter_supported": true
}
```

No `offline_access`: refresh tokens are always issued, so there's nothing to opt into, and the spec
says a resource server shouldn't list it.

### Consent lives on the site

`/connect` is a page on heart-of.me. It signs the user in with the Firebase JS SDK, with the
same providers as the app, and Firebase's `/__/auth/*` handler is already proxied on that
distribution. A returning user is already signed in there, so connecting a second host is one
tap.

The page shows:

- **who is asking:** the client's name and, as the CIMD rules require, the redirect URI's host,
  prominently, so a look-alike client can't pass as Claude;
- **what for:** each scope in plain words ("Read your workouts, templates, goals and custom
  exercises"), and that nothing can be changed under `read`;
- **the health line:** "Heart doesn't have your heart rate, sleep or other health data, so it
  can't share it." It's true by construction, and it's the pitch;
- **Allow / Cancel.** Cancel returns `error=access_denied` to the client, as the spec expects.

Approval is an ordinary Firebase-authenticated API call, so the page holds no secret and there is
no cookie to forge. CSRF has nothing to ride on. The page sends `frame-ancestors 'none'`, so it
can't be framed for clickjacking.

**Anonymous accounts can't consent.** The approve route sits behind the normal Firebase middleware,
which already answers `anonymous_account` (`2026-09-05.anonymous-accounts.md`). The page says why
and links to signing in from the app: there's nothing on the server to share until there is an
account.

## Clients

### CIMD, the default

The `client_id` is an HTTPS URL. On `/authorize` the API fetches it, checks that the document's
`client_id` equals the URL exactly, and checks `redirect_uri` against its `redirect_uris`.

The fetch is an outbound request to a URL a stranger chose, so it is guarded like one:

- HTTPS only, no redirects followed, a short timeout and a body cap of a few KB;
- refuse private, loopback and link-local addresses, after resolving, so DNS can't rebind into
  the VPC;
- cache by the response's HTTP caching headers within a floor and a ceiling (minutes to a day), so
  a popular host costs one fetch, not one per connection.

### DCR, for compatibility

`POST /oauth/register` takes RFC 7591 JSON and returns a generated `client_id`. It exists because
some hosts still fall back to it. Registrations are open by design, as the spec intends, so they're
cheap rows that are garbage-collected when unused: a registration that never completes an
authorization within a day is deleted.

### Redirect URIs

Exact string match, with one exception: loopback redirects (`http://localhost/…`,
`http://127.0.0.1/…`) match on any port, per RFC 8252. Claude Code registers that way.

Hosts as of 2026-10-04, from their docs:

| Host                     | Redirect                                                                    | Registration      |
|--------------------------|-----------------------------------------------------------------------------|-------------------|
| Claude (web, apps)       | `https://claude.ai/api/mcp/auth_callback`                                   | CIMD or DCR       |
| Claude Code              | loopback, any port                                                          | CIMD              |
| ChatGPT                  | `https://chatgpt.com/connector_platform_oauth_redirect`, `https://chatgpt.com/connector/oauth/{id}` | CIMD (or DCR)     |

Nothing in this table is configuration. CIMD and DCR carry the redirects. The table is here so
whoever tests the flow knows what to expect.

### Client authentication at the token endpoint

- **`none` plus PKCE** for public clients: the default, and what Claude uses.
- **`private_key_jwt`**: the client signs an assertion with a key from its `jwks_uri`. ChatGPT's
  metadata document declares it. Supporting it from day one avoids the Auth0 failure above.

## Tokens

### Access tokens share `api_tokens`

An OAuth access token is the same kind of thing as a personal token, a bearer credential for one
account with scopes, so it lives in the same table and passes through the same middleware and
rate limit. Two columns tell them apart:

```sql
ALTER TABLE api_tokens
    ADD COLUMN grant_id UUID REFERENCES oauth_grants (id) ON DELETE CASCADE,
    ADD COLUMN resource TEXT;
```

- `grant_id` is null for personal tokens and set for OAuth tokens. Revoking a grant cascades to its
  tokens.
- `resource` is the RFC 8707 audience: `https://mcp.heart-of.me` for the MCP server,
  `https://api.heart-of.me/v1/me` for a third-party app on the REST surface. The middleware
  checks it against the surface being called. A personal token has `resource` null and is accepted
  on both, because the user is acting as themselves. Liftosaur does the same with its API keys.
- Prefix `hrt_at_` for access tokens, so a leaked one is recognisable as short-lived.
- **Lifetime one hour.** Short, as the spec recommends; the refresh token carries the session.

Personal tokens' 5-per-account cap doesn't apply to OAuth tokens: a grant holds at most one live
access token, and the rate limit is per account either way.

### Grants and refresh tokens

```sql
CREATE TABLE IF NOT EXISTS oauth_grants
(
    id           UUID        DEFAULT uuidv7() PRIMARY KEY,
    user_id      TEXT        NOT NULL REFERENCES profiles (id) ON DELETE CASCADE,
    client_id    TEXT        NOT NULL,          -- a CIMD URL or a DCR id
    client_name  TEXT        NOT NULL,          -- as shown on consent, frozen at that moment
    scopes       TEXT[]      NOT NULL,
    resource     TEXT        NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_used_at TIMESTAMPTZ,
    revoked_at   TIMESTAMPTZ
);

CREATE TABLE IF NOT EXISTS oauth_refresh_tokens
(
    token_hash  BYTEA       PRIMARY KEY,
    grant_id    UUID        NOT NULL REFERENCES oauth_grants (id) ON DELETE CASCADE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ NOT NULL,
    rotated_at  TIMESTAMPTZ                      -- set when exchanged; a second use means theft
);
```

A grant is one user's consent to one client for one resource, and is what the user sees and
revokes. Approving the same client again for the same resource widens the existing grant's
scopes rather than adding a row.

Refresh tokens rotate on every use. Exchanging one sets `rotated_at` and issues the next. If a
token that has already been rotated is presented again, someone else holds a copy, and **the
whole grant is revoked**. That's RFC 9700's reuse detection, and costly only to the thief.
Refresh tokens expire after 90 days without use. A host the user hasn't touched in three
months asks them to connect again.

Authorization codes and pending requests are short-lived rows of their own (`oauth_requests`:
client, redirect, PKCE challenge, scopes, resource, state; the code hash once approved; single
use, 60 seconds). They're deleted on use or expiry.

### Scopes

| Scope             | Grants                                                         | When                        |
|-------------------|----------------------------------------------------------------|-----------------------------|
| `read`            | everything under `/me` and every read-only MCP tool            | now                         |
| `write:templates` | creating and editing templates and template folders            | phase 4 of the developer API |
| `write:workouts`  | logging workouts                                               | after templates             |

Per resource, not per verb, so a user can let an assistant build programs without letting it touch
their history. A missing scope is `403` with
`WWW-Authenticate: Bearer error="insufficient_scope", scope="…"`, which makes compliant hosts
re-authorize with the union. No scope is health-shaped, and none ever will be: there's nothing
behind one.

## Routes

| Route                                  | Auth          | Does                                                                     |
|----------------------------------------|---------------|--------------------------------------------------------------------------|
| `GET /oauth/authorize`                 | none          | validates client, redirect, PKCE, resource, scope; 302 to `/connect`     |
| `GET /oauth/requests/:requestId`       | Firebase      | what the consent page shows: client name, redirect host, scopes          |
| `POST /oauth/requests/:requestId/approve` | Firebase   | creates or widens the grant, mints the code, returns the redirect        |
| `POST /oauth/requests/:requestId/deny` | Firebase      | returns the `access_denied` redirect                                     |
| `POST /oauth/token`                    | client (none / `private_key_jwt`) | form-encoded; `authorization_code` and `refresh_token`  |
| `POST /oauth/revoke`                   | client        | RFC 7009                                                                 |
| `POST /oauth/register`                 | none          | RFC 7591 DCR                                                             |
| `GET /accounts/connected-apps`         | Firebase      | the app's "Connected apps" list                                          |
| `DELETE /accounts/connected-apps/:grantId` | Firebase  | revoke, effective on the next request                                    |

`/oauth/*` skips the version gate, like `/me`. The token endpoint answers form-encoded requests
and OAuth-shaped errors (`{"error": "invalid_grant"}`), not the API's usual error body: that
format belongs to the protocol.

**In the app:** "Connected apps" sits beside personal tokens in one settings screen: name, when it
was connected, last used, scopes, Disconnect. A frontend request, plus a `Grant` model in
`heart_models` (minor bump).

## Operations

- **Cold starts.** The token endpoint must answer inside Claude's 10-second budget from cold. The
  API is AOT-compiled Dart on arm64, which starts fast. Measure it before launch, not after a host
  times out.
- **Reachability.** Hosts call from their own egress (Anthropic publishes `160.79.104.0/21`).
  Nothing in front of the API filters by IP today. Any WAF added later has to let them through.
- **Rate limits** on the unauthenticated OAuth routes come from the stage-wide backstop
  (`2026-09-23.developer-api.md`), plus a per-IP cap on `register`, which is the one route that
  writes rows for strangers.
- **Audit.** Grants keep `created_at`/`last_used_at`/`revoked_at`, as tokens do, so "what is
  connected to my account" always has an answer.

## Privacy policy

Before launch: the user can connect third-party apps. Each one sees only what the scopes on the
consent screen say. The user can disconnect any of them in the app. What a connected app does with
the data is under that app's own terms. Update "Last updated" with it.

## Gaps and open questions

- **Sign in with Apple on the web is not set up yet, and it blocks launch.** Without it, anyone who
  signed up with Apple can't consent. It doesn't wait for a web app; it's provider configuration:
  - a Services ID in the Apple developer account;
  - the return URL `https://heart-of.me/__/auth/handler`, which the web distribution already
    proxies to Firebase;
  - Apple's domain verification file under `site/.well-known/<env>/`, deployed by `site.sh` like
    the others;
  - the Services ID and key in Firebase's Apple provider, with heart-of.me among its authorized
    domains.

  An earlier attempt left nothing in the repo, so it starts from a check of what the Apple and
  Firebase consoles already hold. Approving in the app instead (a universal link or QR code from
  `/connect`, the app's own session doing the approval) would remove the web login entirely. It's a
  nicer flow for later, not a substitute now.
- **Hosted Claude's CIMD URL** wasn't found in its docs. It doesn't block anything, since the
  document announces itself, but the end-to-end test should record it.
- **`private_key_jwt` verification** means fetching and caching the client's JWKS, with the same
  outbound guards as the CIMD fetch. The API already verifies Firebase JWTs and depends on
  `openid_client` and `pointycastle`, so the primitives are in hand. Whether `openid_client`
  covers JWKS-by-URL for arbitrary clients is to check.
- **Dev issuer.** Dev's site origin, with its own metadata copy. Hosts must be pointed at dev
  explicitly when testing.
- **Consent page copy and design** follow the site's design system. It's the one page every
  connected user sees.
