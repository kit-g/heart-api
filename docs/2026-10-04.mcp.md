# A remote MCP server, and Heart in ChatGPT

Status: **proposal.** Nothing here exists yet. Stands on `2026-09-23.developer-api.md` (the
`/me` surface and its rate limit) and `2026-10-04.oauth.md` (how a host gets a token).

## What and why

One MCP server that any assistant can connect to with the user's consent, so the user can ask
about their training ("how has my squat moved since June?", "which muscles did I skip this
month?") and later have the assistant build templates. Heart provides the access. The user picks
the assistant, the assistant does the thinking, and Heart runs no model and pays no inference.

| Host                                   | How it connects                                                                                     |
|----------------------------------------|-----------------------------------------------------------------------------------------------------|
| Claude (web, desktop, mobile)          | a custom connector by URL, later a directory listing. The free plan allows one custom connector.    |
| Claude Code, Cursor, VS Code, Gemini CLI | the same URL; OAuth over a loopback redirect, or a personal token as a bearer header              |
| ChatGPT                                | an app, packaged as a plugin in OpenAI's directory since July 2026: this server plus UI widgets     |

Where others stand: Hevy has an official ChatGPT app plus community MCP servers built on its
Pro-only API. Liftosaur runs an official remote MCP server for premium users. Strava has an
official Claude connector and now forbids third-party MCP servers. Heart's is free (the
developer API's *Pricing*: access is free, volume can be paid) and carries no health data.

## Where it runs

**A route in the existing Dart API, served on its own host:** canonical URI
`https://mcp.heart-of.me`. Same code, same route table, same database pool. A second Lambda
function from the same build, behind CloudFront (see *Hosting*).

- **Tools call the services `/me` uses, in process.** There is no hop through HTTP and no token
  forwarding, so the spec's no-passthrough rule is met by construction.
- **Stateless fits Lambda.** Revision 2026-07-28 of the spec removed sessions, the GET stream
  and resumability. Every JSON-RPC message is one POST, answered with plain JSON or with an SSE
  stream scoped to that one request. The 2025 revisions already allowed that mode. Nothing has to
  live between requests.
- **Hand-rolled, not a library, for now.** The surface is small. `dart_mcp` (the Dart team's
  package) doesn't support Streamable HTTP or auth in its released version (0.5.2; HTTP is on
  `main`, unreleased). The community `mcp_dart` stops at 2025-11-25. A JSON-RPC handler over
  a handful of methods is less code than adapting either, and the protocol layer can be swapped
  for `dart_mcp` once it ships HTTP. A separate TypeScript or Python service would bring a
  mature SDK but a second deployable and a second copy of every query. Not worth it for this
  surface.

### Hosting

```
mcp.heart-of.me ──▶ CloudFront ──▶ Lambda function URL (RESPONSE_STREAM) ──▶ heart-mcp function
                    adds a secret                                           same artifact as the API;
                    origin header                                           Lambda Web Adapter in
                                                                            response_stream mode
```

**Why its own host and not `api.heart-of.me/v1/mcp`:**

- **The root is ours.** The spec's well-known fallback for protected resource metadata lives at
  the host root, which `api.heart-of.me`'s `/v1` base path mapping can't answer. On
  `mcp.heart-of.me` it's a plain route.
- **Streaming.** A function URL in `RESPONSE_STREAM` mode lets a response be a per-request SSE
  stream, and lifts the 6 MB response cap to a 20 MB soft limit. API Gateway REST APIs gained
  streaming in November 2025 too, but only per integration. The API's single `{proxy+}` resource
  would need a separate `/mcp` resource and a second function anyway, since the adapter's invoke
  mode is per function. Having paid for a second function, the dedicated host costs nothing more.
- **A URL people can type** into a connector dialog, and that the docs can print.

**What streaming is for here.** The default answer stays plain JSON. A tool that takes long
enough to matter streams progress notifications before its result, which is what the spec's
per-request SSE is for. Nothing is pushed outside a request; that channel no longer exists in
the spec.

**The origin is locked with a secret header, not OAC.** CloudFront's origin access control for
function URLs requires signed request bodies (`x-amz-content-sha256`) on `POST`, which no MCP
client sends. So the function URL is `AuthType NONE`, CloudFront adds a secret header, and the
function rejects requests without it. The secret lives in the function's config and rotates like
any other.

**Two functions, one artifact.** `heart-mcp` differs from the API function in environment and
wiring only: the adapter's invoke mode, no `/v1` base path removal, the origin secret, and a
route table of just the MCP route and its `/.well-known/*` documents. Nothing else in the API is
reachable through `mcp.heart-of.me`.

**What replaces API Gateway's backstop.** There's no stage throttle in front of a function URL.
Reserved concurrency on `heart-mcp` caps it, so a flood degrades the MCP server without touching
the app's API. WAF rate rules on the distribution are the next step if that's ever not enough.

**As built** (the MCP host PR):
- **Names:** the function is `heart-api-mcp` (`infrastructure/app/stacks/api/mcp.tf`), the same zip as the API, which the deploy ships to both. `HEART_SURFACE=mcp` makes `main` build `buildMcpApp`: request logging, the origin lock, the config, and the MCP router at the root.
- **The origin lock:** the header is `x-heart-origin`, with a secret Terraform generates (`random_password`), compared in constant time.
- **Concurrency:** prod reserves 3 executions, the API 12, out of the session pool's 15. Dev reserves nothing (its account quota is still 10).
- **The domain is optional** (`mcp_domain`). Until the `us-east-1` certificate exists, the host answers at its `*.cloudfront.net` name, and OAuth keeps naming the API's `/v1/mcp`. With a domain, `MCP_RESOURCE` is `https://mcp.heart-of.me` for both functions.
- **`api.heart-of.me/v1/mcp` keeps serving personal tokens.** It's what the developer docs print.

### Protocol versions

Hosts are mid-migration. Anthropic is rolling out 2026-07-28 across Claude, and there is no
statement yet for ChatGPT. The server speaks both:

| Request                          | 2025-06-18 / 2025-11-25 clients            | 2026-07-28 clients                                    |
|----------------------------------|--------------------------------------------|-------------------------------------------------------|
| handshake                        | `initialize` → capabilities; no session id | `server/discover`                                     |
| `tools/list`, `tools/call`, `resources/read` | as is                          | same, plus `resultType`, `ttlMs`/`cacheScope` on lists |
| headers                          | `MCP-Protocol-Version`                     | plus `Mcp-Method`/`Mcp-Name`, checked against the body (`400`, `-32020` on mismatch) |
| `GET`, `DELETE`                  | `405`                                      | `405`                                                 |

No server-to-client requests (sampling, elicitation, roots) are needed, so the 2026 retry
mechanism for them never comes up. `Origin`, when present, must be an allowed host origin or the
answer is `403`. That's the spec's DNS-rebinding defence. Server-side callers send none.

### Auth

- No token or a bad token: `401` with
  `WWW-Authenticate: Bearer resource_metadata="https://mcp.heart-of.me/.well-known/oauth-protected-resource", scope="read"`.
  Claude only starts sign-in on a `401`. ChatGPT also reads `_meta["mcp/www_authenticate"]` on a
  tool error, which the server sets too.
- **Protected resource metadata (RFC 9728)** at that URL, which is also the spec's root fallback:
  `resource` exactly `https://mcp.heart-of.me` (no trailing slash; Claude compares it to what the
  user typed),
  `authorization_servers: ["https://heart-of.me"]`, `scopes_supported: ["read"]`.
- Accepted credentials: an OAuth access token whose `resource` is the MCP URI, or a **personal
  token**, for config-file clients and anyone who'd rather paste one. Both go through the
  token middleware and the per-account rate limit. Only `tools/call` and `resources/read` count
  against it. The handshake and listings (`initialize`, `server/discover`, `tools/list`) are what
  a host sends at the start of every conversation, and with a 200/day free limit they'd eat a
  real share of it for no data.
- Every call is logged as the developer API's *Knowing who calls* describes, with the host taken
  from `clientInfo`. A 2026-07-28 client sends it in each request's `_meta`; a 2025 client sends
  it only in `initialize`, so for those the OAuth `client_id` names the host, and a personal-token
  caller is known by its User-Agent alone.

## Tools

Every tool's input is a JSON Schema, and its output is `structuredContent` plus a short text
rendering for hosts that only show text. Every tool has a `title` and explicit
`readOnlyHint`/`destructiveHint`/`openWorldHint`, which both directories require. Read-only tools
then run without a confirmation prompt in Claude. Reads and writes are separate tools, and there
is no catch-all.

### Phase 1: reads (`read` scope)

| Tool                     | Answers                                                                                  | Backed by                     |
|--------------------------|------------------------------------------------------------------------------------------|-------------------------------|
| `get_profile`            | username, unit system, how much history there is                                         | `/me`                         |
| `list_workouts`          | workouts in a date range, newest first, paged; summaries (name, date, exercises, set counts, volume) | `/me/workouts`      |
| `get_workout`            | one workout in full: exercises, sets, set types, RPE, notes                              | `/me/workouts/:id`            |
| `get_exercise_history`   | one exercise's sessions, newest first: working sets and the progress chart's values (top set, e1RM, volume, …) | `/me/exercises/:id/history` |
| `get_personal_records`   | records per exercise, or for one                                                          | `/me/records`                 |
| `list_templates`         | templates and their folders                                                               | `/me/templates`, `/me/template-folders` |
| `list_goals`             | goal definitions and, for training goals, progress                                        | `/me/goals`                   |
| `search_exercises`       | the exercise library, with the same aliases and glossary the app searches (heart-api#102), in the user's locale | `/me/library`    |

Shipped first (heart-api#116): `get_profile`, `list_workouts`, `get_workout`, `list_templates`,
`list_template_folders`, `list_goals`, `list_custom_exercises`, one per `/me` route;
`get_personal_records` followed with `/me/records` (heart-api#114), and `get_exercise_history`
with `/me/exercises/:id/history`. A session's values come from `toSessionMetrics` in `heart_models`, the
progress chart's own definitions, so the assistant and the chart agree. `get_workout` names each
exercise's id, which is how a model gets from a workout to its history. `search_exercises` came
last, with `/me/library`: the app's own matcher (`Exercise.match`) over the localized library and
its glossary. A host's `Accept-Language` says nothing about the user, so the tool takes `locale`.

**Parity rule: the MCP server never knows something the REST API can't tell.** A tool that needs
a new read, such as `get_exercise_history`, gets its `/me` route in the same change. Scripts and
assistants then see the same account, and tools stay thin.

**Output is sized for a context window, not a screen.** Weights come in the user's unit with the
unit named, dates in ISO, and only the fields the question needs. A list never returns full sets
unless asked. A whole history is paged, never dumped. Tool descriptions say how to page.

**Server instructions** (the `instructions` text hosts show the model) say what Heart holds and
what it doesn't: training only, and no heart rate, sleep or body weight from the health store
because Heart doesn't have them. Workout calories are an estimate. That stops the assistant from
promising the user what it can't fetch.

### Later: aggregates

"Which muscles did I skip?" and "weekly volume per muscle" want server-side aggregation
(heart-api#37, #38). Each lands as a `/me` route and a tool together, under the parity rule.

### Phase 4: writes

Separate scopes and separate tools, as the developer API's *Phase 4* sets out, templates first:

| Tool                       | Scope             | Hints                                   |
|----------------------------|-------------------|-----------------------------------------|
| `create_template`          | `write:templates` | not read-only, not destructive          |
| `create_template_folder`   | `write:templates` | not read-only, not destructive          |
| `update_template`          | `write:templates` | destructive (it overwrites)             |
| `log_workout`              | `write:workouts`  | not read-only, not destructive          |

A host holding only `read` that calls a write tool gets `insufficient_scope` and asks the user to
widen the grant. The writes wait on the same thing the REST writes wait on: the app learning about
rows it didn't create.

**Prompt injection gets real with writes.** Today every string a tool returns is the user's own,
but templates can come from a coach through connections. Strings from another account come back
marked as quoted content, and write tools are never exposed through a read-only grant.

## The ChatGPT app: widgets

ChatGPT shows an app's results as UI. The standard for that is now **MCP Apps**, the official
extension: a tool's `_meta.ui.resourceUri` points at a `ui://` resource of type
`text/html;profile=mcp-app`, and the host renders it in a sandbox fed with the tool's result.
OpenAI's older `openai/outputTemplate`/`window.openai` keys are compatibility aliases. Claude, VS
Code and others render MCP Apps too, so **the widgets aren't ChatGPT-only**: build once, every
supporting host shows them, and text-only hosts still get the text.

First widgets, each on an existing read tool:

| Widget            | On                      | Shows                                                              |
|-------------------|-------------------------|--------------------------------------------------------------------|
| Workout card      | `get_workout`           | the session as the app's workout-done screen lays it out           |
| Exercise progress | `get_exercise_history`  | the app's progress chart for that exercise                         |
| Records           | `get_personal_records`  | the record list with dates                                         |
| Template preview  | `create_template` (phase 4) | what will be created, before the user confirms                 |

Widgets are static HTML/JS bundles served from `resources/read`, built in the app's design
system (the site's tokens). They render only what the tool returned, fetch nothing themselves,
and need no CSP exceptions beyond the host defaults.

A ChatGPT app that only answers in text is still an app. The widgets are what make it worth
choosing over a plain connector, and they can follow the first submission.

## Directories

**Claude** (connector directory, reviewed):

- titles and hints on every tool;
- tool names of 64 characters or fewer;
- no injection-shaped descriptions;
- actionable errors;
- a populated test account;
- public docs by the publish date.

**ChatGPT** (plugin directory since July 2026, reviewed):

- a verified individual or organisation;
- a privacy policy;
- all three hints set explicitly;
- a demo account with full data and no 2FA or extra sign-up steps;
- no selling digital subscriptions inside the plugin. That's moot here: Heart's is free.

The policy forbids collecting protected health information. A training log isn't that, and the
server holds no health-store data, but the submission should say so plainly rather than leave a
reviewer to guess.

**The demo account** is a real email/password Firebase account with a few months of imported
history. Strong's CSV import makes that one upload. Its credentials go to the reviewers, never
into the repo.

## Health

Nothing to filter, because nothing is there: the server holds no health data, so no tool can
return any. What the doc commits to is keeping it that way:

- no tool parameter or output field is health-shaped. `Request.json()`'s `400 health_data` guard
  applies to MCP bodies like any other, because they go through it;
- `calories` is labelled an estimate in the schema description;
- don't copy Strava's tool surface. Its connector serves per-second heart-rate streams, which is
  exactly what Heart's promise rules out.

## Rollout

1. **Personal-token MCP.** The phase 1 reads behind personal tokens, first attached to the API at
   `https://api.heart-of.me/v1/mcp` (its own router, `buildMcpRouter`), so Claude Code, Cursor and
   desktop config files can use it with no new infrastructure. The dedicated `mcp.heart-of.me`
   function serves the same router and arrives with OAuth, which needs its root.
2. **OAuth** (`2026-10-04.oauth.md`): protected resource metadata, `401` discovery, then connecting
   from Claude and ChatGPT by URL.
3. **Docs page** for connecting each host, with the health promise first.
4. **Directory submissions**: Claude, then ChatGPT.
5. **Widgets** via MCP Apps.
6. **Writes**, with the developer API's phase 4.

## Gaps and open questions

- **Unauthenticated tools.** `search_exercises` needs no account, and Liftosaur exposes its
  reference tools without auth. But Claude only starts sign-in on an HTTP `401`, and how hosts
  treat a server that is half open is unverified. Phase 1 requires auth everywhere. Revisit with
  a real host.
- **ChatGPT's plan availability.** Older reports said published apps work on every logged-in plan
  outside the EU; a newer help snippet suggests full MCP apps are Business/Enterprise on the web.
  Unverified. Check by hand before promising it in copy.
- **ChatGPT and 2026-07-28.** No statement found. The dual-version server covers it either way.
- **Gemini.** The consumer app takes no custom MCP servers as of this writing; Gemini CLI does.
- **Response schemas.** Tool output schemas want the same response-type declarations the OpenAPI
  question needs (`2026-09-23.developer-api.md`, *Open questions*). Solving it once serves both.
