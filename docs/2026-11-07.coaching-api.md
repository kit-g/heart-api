## Conventions

Every route takes the Firebase bearer token, as the rest of the API does, unless it says signed out. Bodies are JSON. Errors are `{"error", "code", "reason" | "message"}`, and `code` is what to branch on. A list that pages answers `{"<items>": [...], "cursor": "…"}`, with `cursor` present only when there is more; pass it back as `?cursor=`. Ids the device makes are UUIDv7. Requests sit behind API Gateway and Lambda, so a body past about 6 MB fails before the API sees it.

## Connections, what a coach reads, hiding a workout

App ticket heart-of-yours#552. Wire models: `Connection` and `ConnectionListResponse` (with `connectionId`, `acceptedAt`, `shares`, `name`, `avatar`), `HiddenWorkout`, and the existing `Workout`, `Goal` and skip models for a coach's reads. `User.entitlements` says whether an account holds `coach`.

- **One id per connection.** `connectionId` (a UUID, the same from both sides) is what every route takes: `/connections/:connectionId`, threads, notes, push settings per person, the roster, sending a program. One the caller isn't on answers 404, as one that doesn't exist does. Words such as `role` and `domain` are lower case everywhere; `heart_models` still reads the upper case an earlier server wrote.
- **A pair holds one connection per domain,** in either direction. Ending it (`DELETE`) keeps it as `severed`, and the coach loses every read and write at once (the examples end with those 403s). Only a new invitation reopens a coaching connection; `POST /connections` refuses one with `400 invitation_required`.
- **What a coach reads is narrower than what a peer read before.** Workouts from `acceptedAt` on, or all of them with `history` shared; never a hidden workout, never one started while the connection was paused, and no images. Skips without a reason or weather. Goals only with `goals` shared. A hidden or out-of-scope workout answers 404, not 403, so it's indistinguishable from one that doesn't exist.
- **`shares`** is the student's alone to set (`403` for the coach), replaces the list each time, and is an open vocabulary: `history`, `goals`, and `assistant` (what the coach reads, to the coach's assistant too: `2026-11-09.coach-assistant.md`) today. An unknown word is refused.
- **Hiding** hides a workout from every connection, peers too. A full `PUT /workouts/:id` from a build that doesn't know about hiding keeps it hidden. `GET /workouts/hidden` lists what is hidden and since when, so another device of the owner can catch up.
- **Pausing** (`PUT /connections/:connectionId` with the existing status move) stops coach reads of anything logged during the pause; only the student resumes a paused coaching connection.
- **Who the other person is:** `name` and `avatar`, as their profile says now, on `GET /connections` and on the answer to a status or shares change, so any device of the caller shows a renamed coach's current name (heart-api#409). Absent when they have none; when the caller only asked them and they never accepted, so a request reveals nobody; and when they blocked the caller, who sees that connection as `severed` rather than `blocked`, without their face. The answer to `POST /connections` leaves them out.
- **Blocks** reach every path between two people: reads, messages, keys, pushes. Lifting one restores nothing.
- **A blocked person can't tell** (heart-api#405). The blocker's connection reads as `severed` to them, without a name or photo. What they do with it answers as for an ended one: ending it answers 204 and changes nothing, `severed` is `400`, starting it again is refused as while any block stands, and `blocked` blocks back, after which each of them reads the row as the other's block shows it. Elsewhere a block already answers as no relationship does: keys `403`, messages and program writes as for an ended connection, an invitation of the blocker's as `invitation_gone`. Their threads with the blocker stop being listed, which an ended connection's don't: a block keeps the blocker's words from them.
- `User.entitlements` holds `coach` for an account that may invite. Students need nothing.

## Invitations, in the app and on the web

App ticket heart-of-yours#553. Wire models: `Invitation`, `InvitationPreview`, `AcceptedInvitation` (the connection plus how the named program arrived), `BlockedPerson`.

- **A link is for one person and expires** (`expiresAt`, a week). The `token` comes back when the invitation is made and when it's resent, never on a list; the server keeps only its hash. Resending gives a new token and expiry and kills the old one. Cancelling is idempotent.
- **The web page does everything the app does:** `https://heart-of.me/invite.html?t=<token>` previews signed out, then signs in (or makes an account) and accepts, declines or blocks; with no `t` it lets a coach make a link. The part of a link after `#` never reaches any server, which is where a key fingerprint can travel. Someone who accepts on the web may have no device holding keys yet; their device list shows it (see the keys ticket).
- **Accepting** is one step: the connection, `shares`, and "Your coach" left on in the account's `extra.features`, so an app opening afterwards agrees. A program named by the invitation is delivered after, as a step of its own: `programDelivered` says whether it arrived and `programId` which copy it is. A student at their program limit still connects, with `programDelivered: false`; the coach can send it again later. The student's app learns of the new program on its next fetch of `/programs`, or from the answer when it is the app that accepted.
- **Accepting again** answers the same connection and tells nobody: only the accept that connected them pushes. Accepting one's own link is `400 own_invitation`; a cancelled, expired, used or blocked link is `400 invitation_gone`, the same answer whichever it is.
- **Declining** doesn't use the link up: the same person can still accept it later. **Blocking from a link** blocks the inviter without any connection between them.
- **The coach is told** by a `coaching.invitation_accepted` push carrying only `topic`; the new connection arrives on the next `GET /connections`.
- **Limits:** only an account with the `coach` entitlement can invite in the beta (`403 coaching_beta`). Pending invitations and recent declines per coach are capped (`400 invitation_limit`); nobody is expected to reach them.
- Names in previews, lists and pushes are the one the account's profile holds (its `username`, the display name the app sets).

#### `POST /invitations`

A coach makes a one-person link. Needs the `coach` entitlement in the beta. `name` is what the coach calls the person; `programId` optionally names a library program the student gets on accepting. The answer carries the `token`, here and on resend only; the server keeps a hash. The web page's link is `https://heart-of.me/invite.html?t=<token>`, and anything after `#` never reaches a server.

## Pushes and push settings

App ticket heart-of-yours#554. Wire models: `PushSettings` and `PushSetting` (`forPeople` for per-person answers).

- **The server sends pushes; nothing reaches a phone without a token registered by `POST /devices`.** This is the first time pushes reach the app. Each push's data carries `topic`; titles are rendered on the server in the device's locale and never hold what was said. A title names someone as their profile does, and by the name on their sign-in only when the profile has none.

| Topic | Kind | Data besides `topic` | When |
|---|---|---|---|
| `coaching.message` | visible, channel `messages` | `threadId` | a message arrived |
| `coaching.invitation_accepted` | visible, channel `coaching` | none | someone accepted the coach's invitation, once |
| `coaching.program_received` | visible, channel `coaching` | `programId` | a coach's send made the student a new copy |
| `coaching.workout_digest` | visible, daily, channel `coaching`, collapses | none | once an evening, if the coach's clients trained |
| `coaching.program_changed` | silent | `programId` | the other person changed a managed copy |
| `coaching.thread_cleared` | silent | `threadId` | the other person deleted the conversation |
| `security.devices_changed` | silent | `userId` | the person, or someone the app shares keys with, added, removed or vouched for a device |
| `security.queue_waiting` | silent, collapses | `deviceId` | something arrived in the key queue of one of the person's devices |
| `comment.created` | visible, channel `comments` | as before, minus the text | unchanged, except it no longer carries the comment's words |
| `reaction.created` | visible, channel `reactions` | `targetType`, `targetId` | someone reacted to the person's workout, exercise, set or photo (`docs/2026-11-08.reactions.md`) |

- **Settings are drawn from the server's answer.** `GET /push/settings` returns every topic a person can change, localized, with `delivery` resolved and the `options` that topic allows, so a topic a build has never heard of can still be shown and changed. Silent topics aren't listed and can't be set. `delivery` is an open vocabulary: `instant`, `daily`, `off` so far.
- **Per person:** the same `PUT` with a `connectionId` sets an answer for one connection, and the most specific answer wins: person, then topic, then default. `forPeople` lists those answers. `DELETE` goes back to the default.
- **Which side a topic is for:** each topic's `perPersonAs` lists the caller's own roles in a connection for which choosing it for one person means anything: `comment.created`, `reaction.created` and `coaching.message` for `coach`, `student` and `peer`, `coaching.program_received` for `student`. Empty for a topic chosen only as a whole: `coaching.workout_digest`, which goes while the topic or anyone at all still wants it, and `coaching.invitation_accepted`, which goes once, before anyone could choose for that person. Offer a per-person choice on a connection only when the caller's `role` in it is listed (heart-api#416). An open vocabulary, like `role`.
- **Signing out** (or turning pushes off): `POST /devices/removals` with the token stops this device getting the account's pushes (heart-api#415).
- **Daily pushes** go out once in the person's evening, from 18:00 by the `utcOffsetMinutes` their most recently seen device sent with `POST /devices`. Without an offset the server can't place their evening.
- Stale tokens are dropped by the server after 270 days unseen.

## Device keys and key delivery for end-to-end encryption

App ticket heart-of-yours#555. Wire models: `CryptoDevice`, `CryptoDevices`, `OneTimeKeyCount`, `QueuedItem`, `QueuedItems`.

- **The server holds public keys and sealed items only.** It never has anything that opens a message, and it can't check that what it carries is ciphertext; the app is the only guard on that.
- **A device publishes its identity once** (`identityKey`, `signingKey`, `fallbackKey`, all base64), optionally vouched by another device of the same person (`vouchedBy` and `signature`, both or neither). The device's `id` is its own; a removed device can't come back under the same id (`403 device_removed`). A device that published unvouched can be vouched for later (`PUT …/vouch`), once. Adding a device (publishing it again adds nothing and sends nothing), removing one, or vouching for one sends `security.devices_changed` to everyone sharing keys with that person, and to the person's own devices, so another phone of theirs can trust a new key or flag one they didn't add (`userId` is their own). At most ten devices with keys per account: an eleventh is `409 device_limit` until one is removed, a beta guard rather than a promise.
- **Who can fetch keys:** the person's own devices, and anyone they have or had a connection with, under no block. That includes an ended connection, so a new phone can still open old history; the examples show claims and device lists still answering after the connection ended.
- **Single-use keys:** up to 50 held per device, sent as a list of `{id, key}`. Not a map of id to key: an id would be a field name, and the health guard refuses a body whose field names read like health data (`hrv`, `sleep`, … anywhere in the name, any case), which a random id can. A claim takes one from each of the person's devices, never handing the same one out twice, and the fallback once they run out. `GET …/one-time-keys` says how many are left. Claims are capped at 60 an hour per pair (`429 rate_limited`, with `retryAfter` seconds in the body).
- **The queue** carries small sealed items (≤ 1 KB, `kind` such as a session key) from one device to another device. `id` comes from the sender, so a retry delivers once. The recipient reads what's unconfirmed by `seq` and confirms by id; nothing is paged by cursor, so a late row can't be skipped. The server keeps order only for items sent one at a time: a sender that waits for each answer gets its order kept. At most 2,000 unconfirmed items per sender and recipient device (`400 queue_full`). Unconfirmed items go after 90 days. A block stops the queue both ways, including what was waiting. Each item names the account that sent it (`senderUserId`), as the server knows it, so the recipient checks the sending device against that account's devices without trusting what the item says.
- **Waking the recipient:** an item arriving sends a silent `security.queue_waiting` to the recipient's account, naming the device (`deviceId`) and nothing else. At most one a minute per recipient device: an item that arrives while another reached that device in the last minute sends none, and the app reads the queue on start and resume anyway. Push tokens belong to the account, not to a key device, so each of the person's apps hears it and the one whose device it names reads its queue.

## Messages, notes and reports

App ticket heart-of-yours#556. Wire models: `Thread`, `ThreadList`, `ThreadItem`, `CoachNote` (read a page of notes with `readEach`).

- **Content is ciphertext, always.** `content` (threads and notes) is a string of at most 16 KB that the server never parses, indexes or logs. Hard constraint, from the device-only health rule: words about a person's body may be in it, so it reaches the server only sealed. A body with a health-shaped key anywhere is refused (`400 health_data`).
- **One thread per connection,** opened by `POST /connections/:connectionId/thread` (idempotent). `GET /threads` is the inbox, one list, last arrival first, with `unread` per thread and in total.
- **Sending** needs `id` (UUIDv7 from the device: a retry answers 200 with the stored item and the other person is pushed again), `kind` (`message`, or `reaction` for a reaction to a message, with `subjectType: "message"` and its id: other kinds are refused with `400 invalid_kind`, and a reaction about anything else with `400 invalid_subject`; a reaction pushes nothing and isn't counted as unread, `docs/2026-11-08.reactions.md`), `content`, a 32-byte base64 `commitment`, `at` (when it was written), and optionally `subjectType`/`subjectId` naming a detail it's about (`workout`, `exercise_set`, `skip`, `program`, `session`, … — the server stores them in clear and doesn't check them, so they're references, never content). The answer adds the server's `tag`, `tagKey` and `createdAt`: the sender's proof the message was sent, which a report needs.
- **Order is the server's,** not `at` and not the id: a message written offline and stored later still comes after what a reader has seen. Each item carries a `cursor` (its place in that order); `?since=` reads what came after one, `?before=` reads older. `PUT …/read` moves the read position, and `unread` counts the other person's items after it.
- **Limits:** 60 messages a minute per sender (`429 rate_limited`, with `retryAfter` seconds in the body). A thread takes no new items once the connection ended or under a block (`403 thread_closed`); it stays readable. A paused connection still takes messages.
- **Deleting the conversation** (`DELETE …/items`) removes every item for both people, at once, with no agreement needed. The thread stays, with `clearedAt`/`clearedBy`, and the other person's app gets `coaching.thread_cleared`. A clear covers what had arrived before it; a retry or a send still in flight can land after it. A person the other blocked learns nothing of a clear.
- **Notes** are a coach's private writing about a connection: only that coach reads them, the student never learns they exist, and the last write wins. They outlive the connection.
- **Reports** (`POST /reports`) take the person, optionally the connection, a `reason` word, and for each reported message: the words in clear, the reporter's key for them, and what the server answered when it was sent (`commitment`, `tag`, `tagKey`, `createdAt`, sender, recipient). The server checks them in memory, stores them sealed to a key it doesn't hold, and alerts the owner. It always answers 204, whether or not the words check out. A retry files the report twice.
- **When messaging isn't turned on** in an environment, sending answers `501`.

## A coach's library and sending programs

App ticket heart-of-yours#557. Wire models: `CoachProgram`, `CoachProgramHolder(s)`, `ProgramDelivery`, `ProgramDeliveries`, and `Program` (now with `coachId`, `coachName`, `revision`, `sessionRevisions`).

- **Library programs are the coach's documents,** apart from their own training: they never appear in `/programs`, `/templates` or anywhere else a person's own things are listed. The body is the `POST /programs` shape; exercises are named by exercise id. Each save is a new `version`; the server gives every session, exercise and set an id.
- **Sending makes the copy on the server,** so the student can be offline. The copy is an ordinary program in the student's `/programs`, with ids of its own, `coachId` and `coachName` set, and sessions marked `assignedBy`. A coach's custom exercise reaches the student as their own exercise, matched by name or copied. A student's app finds a new copy on its next `/programs` fetch: no push announces it.
- **One send, many clients:** each connection comes back delivered (with `programId`) or not (with `reason`, e.g. `not_coaching`, `program_limit`, `unknown_exercise`); one refusal stops none. Sending a program a student already holds answers their copy.
- **A copy that would replace the student's current program waits** for a start date: `POST /programs/:id/start` starts it.
- **Holders** say which client holds which version, so a coach can see who is behind.
- A library program id that isn't the coach's is a 404 on every route. Deleting a library program leaves the copies with the students.

## Two people editing one program, its history, and target beside done

App ticket heart-of-yours#558. Wire models: `ProgramChange`, `ProgramChanges`, `CoachProgramView`, `WorkoutPlan`, and `Program.revision` / `Program.sessionRevisions`.

- **A copy is edited by both people,** the student through the routes they already use (`PUT /programs/:id`, `PUT /templates/:id` for a session), the coach under `/accounts/:userId/programs/…`. A coach's write needs a live connection; after it ends, 403.
- **Conflicts are per thing and only with the other person.** The program's own fields and each session have a `revision`. A write sends `baseRevision` (what it started from) and a device-made `changeId`. `409 program_changed` (with the current `revision`) means the other person changed that same thing since; one's own queued edits never conflict with each other. A retried write with the same `changeId` writes nothing again.
- **A session write replaces the session,** exercises included, as `PUT /templates/:id` always has: a body without `exercises` leaves it with none.
- **Builds that send no `baseRevision`** are accepted and recorded with `stale: true`, the overwritten version kept in `before`, so it can be put back.
- **History:** `…/changes?since=<cursor>` returns what changed, with `before`/`after` snapshots, who did it, and its `cursor`. Either person can put a change back (`…/revert`), which is itself a new change; a deleted session comes back under its own ids with its workouts and skips linked again. Reverting a change the other person has since built on is a 409. The other person's app is told by the silent `coaching.program_changed`.
- **Bringing copies up to date** (`POST /library-programs/:id/update`) rewrites each named copy to the current version through its id map, so sessions and slots the student trained keep their ids, their week and their bases; it overwrites the student's own edits as a recorded change; a copy already current is left alone. A connection that was never sent the program answers `not_sent`.
- **Target beside done:** the device sends what it planned for a workout (`PUT /workouts/:id/plan`), with `setId` for the set each planned set became. Only `exercises[].sets[].{setId, weight}` is read by the server; the first plan stays. A coach reads it back for a workout they can see. A workout with no plan has no comparison.

## The roster, the feed, and the daily push

App ticket heart-of-yours#559. Wire models: `ClientSummary`, `CoachFeedItem` (read a page with `readEach`).

- **One roster row per coaching connection** (someone coached in two domains appears twice): the program and the week they're in, recent training times, when they last trained, and `reasons` they may need a word. Everything is computed from what the coach can read, so a hidden workout leaves no trace. Those with reasons come first; `?reason=` filters, `?former=true` lists ended connections, paging by `cursor`.
- **`recent` is a list of times, not days:** the server has no time zone, and the app has the coach's.
- **`assistant`** says whether the client shares with the coach's assistant (added after the examples below were captured).
- **`reasons` is an open vocabulary:** `lighter` (trained lighter than planned, from the workout's plan), `note` (a workout note since review), `gap` (no training for a while), `ending` (the program is near its end) so far. A reason this build doesn't know is carried, not dropped.
- **Reviewed:** `PUT /coach/clients/:connectionId/reviewed` (optionally with `{"at": …}`) clears what came before; reasons count only what came after. Gaps and endings clear when they stop being true.
- **The feed** is workouts and skips of the coach's clients plus endings, newest first, with each item's `kind` (open vocabulary) and the client's name. It pages by an opaque `cursor`.
- **The daily push** (`coaching.workout_digest`) goes out once in the coach's evening if a client finished a workout that isn't hidden. Its setting is per topic and per person.
- Names are the profile's, as everywhere else, pushes included.

## Logging a workout for a client

App ticket heart-of-yours#560. Wire models: `Workout` (with `loggedBy` and `loggedByName`), `WorkoutPlan`.

- **A workout a coach logs is the student's:** in the student's history, deletable by the student, never public. It carries `loggedBy` (the coach's id) and `loggedByName` to the student and to that coach only; every other reader, a peer or another coach, gets the workout without them (heart-api#405). It needs a live coaching connection.
- **The body is the `POST /workouts` shape,** with `name` and `start` required. The id is the device's: a retry answers 200 with the stored workout; an id another person already used is `403 id_taken`.
- **A coach's custom exercise** in it reaches the student as their own, matched by name or copied, as when sending a program.
- **The base move is the device's job,** as for any program workout: the coach's device works it out with the same `heart_models` code and posts it to `POST /accounts/:userId/programs/:programId/bases`, idempotent per workout. Without it the student's later targets would be off. The student's app gets `coaching.program_changed`.
- **A plan** can be saved for it like any workout, so target beside done works for logged workouts too.

#### `POST /accounts/:userId/workouts`

A coach logs a workout that is the student's, in the `POST /workouts` body shape; `name` and `start` are required. It carries `loggedBy`. Idempotent by id; another person's id is `403 id_taken`. A coach's custom exercise is matched or copied to the student.

## Gaps

- **A program that arrives with an accepted invitation doesn't push.** The student is the one accepting,
  and the answer carries `programId`; their other devices find it on the next `/programs` fetch. A send
  pushes `coaching.program_received`.
- **The encryption scheme needs a qualified review before release** (the design's *Commitments and tags*).
- **`/me` has no coaching surface yet;** MCP has a coach's read tools (`2026-11-09.coach-assistant.md`).
