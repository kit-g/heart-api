# Goals about a pattern or a muscle

"Press twice a week", "12 sets of pull a week". Written from the code as it
stands (heart-api#196). It is the goal side of the pattern lens
(`docs/2026-10-11.pattern-lens.md` in heart-of-yours). Programs will derive
goals of this kind on the device.

## Why it exists

Every goal metric but `workouts` was tied to one exercise, so a goal couldn't
say "train chest twice a week". As before, the server stores the definition
and the app computes progress.

## The data model

Two metrics count what trained one **subject**:

| Metric     | Counts                                                       |
|------------|--------------------------------------------------------------|
| `sessions` | workouts that trained the subject                            |
| `sets`     | working sets on it; a muscle receives each set at its share  |

The subject is exactly one of:
- `exercise_id`: an exercise, as before.
- `pattern`: a movement pattern key from the exercise library, such as
  `horizontal_press`.
- `muscle`: a muscle id prefix (`triceps_brachii`) or a muscle group
  (`chest`), matched the way `MuscleTagging.shareOf` matches it
  (`docs/2026-10-12.muscle-shares.md`).

`goals_scope_check` holds it:
- `workouts` names no subject.
- `sessions` and `sets` name exactly one.
- Every other metric names an exercise and neither new column.

Pattern and muscle keys are library content and grow without a release, so
the schema and the input check only their spelling: snake_case, at most 64
characters. They are not checked against a list.

## Why new metrics, not a subject on the old ones

The compatibility floor. Mobile 1.13 reads goals one at a time and drops one
whose metric it doesn't know. A `sessions` goal is invisible to it: never
stored, never edited, never written back.

A `workouts` goal carrying a pattern would be a different story. 1.13 would
show "press twice a week" as "two workouts a week", and its full-replace `PUT`
would erase the pattern. That changes what an existing value means, which is a
breaking change. A subject therefore only ever appears on a metric that came
with it.

## The API surface

`POST /goals` and `PUT /goals/:goalId` take `pattern` and `muscle` beside
`exerciseId`. Every goal read returns them, left out when null. The rules
answer:
- `400 goal_scope` when the subject doesn't fit the metric.
- `400 invalid_subject` when a key is misspelled.

The MCP `list_goals` tool shows the keys as they are stored, and the
description tells the assistant what they mean.

## heart_models (2.18.0)

- `GoalMetric.sessions`, `GoalMetric.sets`, and `countsSubject`. Neither has
  a `chart`.
- `Goal.pattern`, `Goal.muscle`, and `Goal.subject`, a sealed `GoalSubject`
  (`ExerciseSubject`, `PatternSubject`, `MuscleSubject`) for an exhaustive
  switch.

## Gaps

- **A pattern best.** "The best estimated one-rep max among a pattern's
  exercises" (pattern lens, rule 5) is a goal on an existing metric with a
  pattern subject, so it needs a metric of its own when it comes. It would
  take the same path as this change.
- **Nothing checks that a key exists in the library.** A goal on a pattern the
  library later drops keeps its key. Showing it is the app's call.
- **Coaches** see these goals through the connection read
  (`GET /accounts/:id/goals`) like any other, with the key as stored.
